# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Project Ezra** ("Managing Chaos, Effortlessly") — an AI-managed personal task system for iOS. SwiftUI + Core Data, single app target. The current product direction lives in a single consolidated spec, `docs/PRD.md` — vision & boundaries, the three data dimensions (Status/Priority/Flags), Capture/Intent/Correction/ChangeLog + the action table, and the **Today sequence** (Recap → Docket → Capacity → Plan) with deterministic ranking + capacity personalization. Read it before changing product behavior. `prev-docs/` holds the superseded generation (lean PRD, strategy, design system, guardrails, household architecture, mock-data flows); the **design system** (`prev-docs/design-system-managing-chaos.md`), **product guardrails** (`prev-docs/product-guardrails.md`), and **household architecture** (`prev-docs/household-architecture.md`) remain in force except where the new docs override them (navigation, lanes, the Review tab, and the attention/retro layer are gone — replaced by the Today sequence).

## Toolchain — non-negotiable

- **Build with Xcode 27 (iOS 27 SDK).** The deployment target is iOS 27.0. Xcode 26 has no iOS 27 SDK and the build fails. Confirm with `xcodebuild -version` (expect 27.x). If it shows 26.x, the active toolchain is wrong: `sudo xcode-select -s /Applications/Xcode-beta.app/Contents/Developer`.
- Swift language mode is 5.0 (not Swift 6 strict concurrency), but `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` — types are main-actor isolated by default.
- **Host needs macOS Tahoe 26.4+** to run Xcode 27 at all; if Address Sanitizer fails to launch on the iOS 27 simulator, that's a known Xcode 27 beta issue on host toolchains older than **26.5** — update Xcode, not the code. Apple silicon only: Xcode 27 no longer builds Intel/`x86_64` by default (`ld64` is gone; `-ld_classic` is no longer an option).

## Build & run

```bash
# Build (iOS 27 simulator)
xcodebuild -project Project-Ezra.xcodeproj -scheme Project-Ezra \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro,OS=27.0' -configuration Debug build
```

```bash
# Run the unit tests (Swift Testing) on the iOS 27 simulator.
# -parallel-testing-enabled NO is REQUIRED: fixtures build Core Data managed objects in a
# single shared in-memory context (see PersistenceStack.scratch / TestStore), which has
# thread affinity — Swift Testing's default parallelism crashes it. Run tests serially.
xcodebuild test -project Project-Ezra.xcodeproj -scheme Project-Ezra \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro,OS=27.0' \
  -parallel-testing-enabled NO
```

Prefer the `/run-sim` skill for the full install + launch + screenshot loop. A clean build is sufficient to consider a change done (launching the sim is optional, not required). Tests live in `Project-EzraTests/` (Swift Testing, `@testable import Project_Ezra`) and cover the pure AI/ranking logic — `AutonomyPolicy`, `HeuristicEngine`, `IntentResolver`, `CorrectionProfile`, `TaskRanking`, `BrainSweeps`, the Today pipeline (`TodayQueriesTests`, `CapacityBaselineTests`, `DeterministicPlanTests`, `PlanSanitizeTests`, `PlanRoutingTests`, `TodayPlanStoreTests`), plus the `RambleEvalTests` accuracy harness; add cases there when you touch those.

**Known test-runner flake (environmental, not a code bug):** the whole suite passes (all cases green) but the run occasionally ends `TEST FAILED` via `Restarting after unexpected exit` — a *bare* crash of the test host with **zero** Core Data exceptions in the log, always alongside the iOS 27 simruntime warning `objc[…] Class UIAccessibilityLoaderWebShared is implemented in both WebCore.axbundle and WebKit.axbundle … may cause … mysterious crashes`. That's the Xcode 27 beta simulator's own accessibility-bundle conflict, not our code (diagnosed: the correct single-context test architecture throws no CoreData exceptions; only broken multi-coordinator variants did). If a run flips to failed with no `✘` cases and no `NSInvalidArgumentException`, just re-run (or use a freshly-booted sim).

## Project layout & Xcode gotcha

- The target uses a **PBXFileSystemSynchronizedRootGroup** (`Project-Ezra/`): any `.swift` file added under that folder is compiled automatically. **Do not hand-edit `project.pbxproj` to add/remove files** — just create or delete them. (Editing the pbxproj is only warranted for build settings.)
- Source is feature-organized: `Design/` (design system), `Models/` (Core Data `NSManagedObject` models incl. `CapacityLog` + `CapacityBaseline` + `PersistenceStack` + pure ranking), `AI/` (engine layer + the Today plan generators/service), `Features/<Screen>/` (`Today/`, `Tasks/`, `Capture/`, `Household/`, `Root/`), `Features/Components/`. Persistence is Core Data via `NSPersistentContainer` (`NSPersistentCloudKitContainer`-ready — flip `PersistenceStack.cloudKitContainerID` + add the iCloud entitlement to enable sync); models are constructed with the `in:` context convenience inits.
- `Item.swift` is a retired template stub — the real model is `Models/TaskItem.swift`.

## Architecture invariants

- **Four axes, never fused** (`docs/task-model.md`). (1) **Lifecycle** — `TaskStatus` (`.todo → .doing → .done | .canceled`), user-owned. **A `TaskItem` comes into existence at Confirm and never before**: the retired `.inbox` case was a ghost (every creation path confirmed in the same breath), so pre-Confirm state now lives on a parked `Capture` — raw text plus encoded drafts — which is explicitly *not* a task. `AppBrain.commit` IS the confirm; there is no `confirm()` mutation. `status.isLive` replaces the old `== .active` checks. (2) **Type** — `WorkIntent` (action/planning), AI-classified, cached, refreshable, human-correctable **at confirm (`ConfirmCreationCard.kindChip`) and in the detail**. It is **never nil at creation**: the on-device model classifies it, and off device (heuristic path, Apple Intelligence off/unavailable by region) `IntentResolver.inferredWorkIntent` backfills it lexically. That backfill **never reads `isJudgmentCall`/`needsDecision`**, which would re-fuse axes 2 and 3 (test-enforced by `IntentResolverTests.workIntentIgnoresJudgmentFlag`); its `.action` default is behaviourally identical to nil (same CTA verb, same capability set). Nil remains legal on the model (fixtures, a cleared value). The **Thinking Partner** is unlocked by the `needsDecision` flag OR choice-shaped wording (`DecisionShape`, the one decision lexicon) — never by this axis, which NEVER reads/writes `needsDecision`. **Three cases are retired:** `decision` (2026-08-08 — choosing is a capability the system brings, not a kind of work the user classifies; stored `"decision"` decodes as `.planning` via `WorkIntent.decode`, additively, no wipe), `waiting` duplicated the derived `blocked` flag, and `reference` existed only to be *excluded* — removing it collapsed `countsAsWorkload`, five gates, a bespoke heuristic detector, `MyTasksSectionKind`, and the `"reclassified"` verb. (3) **Attention flags** — Needs Decision (stored `needsDecision`), Blocked/Blocking/Overdue/Stale (derived on read, never stored). (4) **Signals** — `isUrgent`, human-declared, feeding a computed **system score** (`AttentionEngine` → persisted `AttentionMetadata`, 0–100 + contributors) that `TaskRanking` uses only to break ties WITHIN the hard bands. The score is NEVER a badge. **Persist-slow/compute-fast:** it reads only slow inputs (urgent, AI importance, effort shape, graph centrality) and never a fast fact, so "the AI never decides the band" holds by construction. Don't re-fuse these: adding a blocker must not move the status; high confidence must not auto-resolve a judgment call.

- **The row's leading marker is one slot with two residents.** `SignalMarker` renders **Needs Decision** (`decisionAccent`) or **Urgent** (`priorityUrgent`), decision winning when both are set, nothing when neither — the slot means "the one thing most demanding your attention", which is honest about being a composite. **This reverses the old "Needs Decision is detail-only, not on rows" rule, deliberately.** What must NOT appear there is the task's *type*: choice-shaped wording and `needsDecision` (axis 3) are different questions, and one glyph for both teaches the user they're the same thing. Type differentiates in the detail. Today (`TodayTaskRow`/`TaskCardView`) stays marker-free by design.

- **The primary CTA is one slot, or none** (`RecommendedAction` / `recommendedAction(among:in:)`, `docs/task-model.md` axis 1). It is **lifecycle-driven, not obstacle-driven** — the old ladder never surfaced `.doing`, so a `.todo` task read "Mark done" and skipped a state. The tree: resolved → Reopen · unowned → That's mine · **owned by someone else → nil** · blocked → Unblock · `.todo` → Start · `.doing` → Mark done. **The nil arm is the design** — someone else's task isn't yours to advance, so a button there is wrong by construction (and completing it would stamp *you* as attesting their work); its proxy moves live in `TaskMoreMenu`, and the empty slot is reserved for Nudge/Comment once `HouseholdSync.isLive` flips. **The verb never voices the type** — the intent-voiced verbs are all retired (`.planning`'s "Break it down" lied; `.decision`'s "Decide" retired with the type), so `.start` carries no associated value and always reads "Start" (or "Resume" on a task with a closed `.doing` visit). **Start does not dismiss the detail**: the button relabels to "Mark done" in place, which is how the lifecycle teaches itself. Only `.resolve` sets `dismissesDetail`. Claim precedes unblock. The one-tap fast path for trivial work stays in the **list** (`TaskRow` long-press + the leading glyph menu) — never a secondary button under the CTA.

- **Capabilities reduce friction; the type only biases which one is offered** (`TaskCapabilities`, `docs/task-model.md`). **Complexity** → Break this down · **Uncertainty** → Thinking Partner · **Inertia** → Unstick. That framing is load-bearing: because the breakdown reduces *complexity*, `BreakdownEligibility` triggers on size and shape (large effort → compound title → planning intent *above a lower bar*), **not** on `workIntent == .planning` — which would offer it to a 15-minute "plan birthday dinner" and withhold it from a multi-step "renew passport". Intent alone is never sufficient. **Unstick is the router, not a fourth module**: `StallDetector` diagnoses *why* a task stalled (blocked → resolve · too big → Break this down · reads as a choice → escalate it to a decision via `escalateToDecision()`, a human act · else → do/defer/let go), and a big-and-stalled task gets **one** card, because Unstick subsumes the breakdown and routes into it. **Every trigger is deterministic** — so eligibility works in the sim and with Apple Intelligence off; only the *content* needs the model, which is why the first two cards are absent off-device while **Unstick renders identically — minus voice** (`UnstickNarrationService` phrases the deterministic diagnosis over the task's facts, restate-only; the template headline is the always-there fallback). **The Start tap earns a kickoff line** (`KickoffService`): the one concrete first move, under the relabeled CTA, silence as the fallback — the execution system's activation-energy remover. **Every card service runs on a `CapabilityProfiles` session** (the `DynamicProfile` pattern proven by capture's `CaptureProfile`): per-capability temperature, reasoning level, and output caps — priors pinned by tests, re-tuned on the device pass. **`CapabilityMetrics` counts offered vs acted per card** (local-only, DEBUG footer `cards: tp 3/9 · …`) — the evidence stream every S4 threshold is tuned or pruned against. **Absence is a render-layer decision, never a trigger** (`modelAvailable` in `TaskDetailView`): the breakdown card is omitted whole off-device, while the decision section keeps its reason line and **Mark decided** and gates only the framing — those are human affordances. **`TaskCapabilities.available` returns `[]` for a resolved task** — the breakdown/stall triggers self-guard, but a resolved task keeps its choice-shaped title, so without that gate a completed "Should we move to Lisbon?" would still offer the Thinking Partner. **The Thinking Partner now recommends** (a recorded reversal): `DecisionFraming.groundedRecommendation` renders only when the model's pick names one of its own options verbatim, and `resolveDecision()` stays the only clearer — the human decides. And **every Unstick action must clear the stall that raised the card** (they all route through `touchHuman`, which resets `deferralCount`) — a card its own buttons can't dismiss is a scold. **Break this down is the one capability that commits**: accepting creates real children born `.todo` with `.parent` edges (`splitInto`), one reversible `"split"` entry whose undo spares any step the user has since touched, and a `currentRelevance` pull-down (`containerRecede`) so the umbrella recedes while it has open steps.

- **Ownership: every task is born owned.** `OwnerProposer` (`AI/OwnerProposer.swift`) is a pure, deterministic ladder — spoken name → graph adjacency (`childOf`/`duplicateOf` targets only; **never blockers**, which point the wrong way) → category affinity → **the capturer**. It is **total**: `applyOwnershipGate` and `ownerPending` are both retired, "unowned" is exactly `ownerID == nil`, and only a human hand-back produces it. **Load never selects an owner, only adjusts one** (demotes the overloaded, breaks ties). `.defaultSelf` carries **no reason and no ✦** — defaulting to you is not an inference, and claiming it was is worse than the abstention it replaced. `ownerOrigin` (`.human`/`.inferred`) is stored because the affinity denominator counts human-established ownership ONLY — otherwise rung 4's own output floods it and the rung is unreachable. `creatorID` (authorship) backs the "Created" tab, distinct from `ownerID`.

- **Confirm is the single publish boundary, and assignment side effects bind to it** — never to the owner field being populated (`AppBrain.publishAssignments`). Pre-Confirm a capture is single-player even when the inferred owner isn't you. **Target notification behavior is *notified*** (one per assignment, re-notify only on reassignment, copy that names the source); it is unimplementable until sync, so the interim is a silent publish. **`HouseholdSync.isLive`** (compile-time `false`) gates the proposer's *inferred* non-self rungs and Today's ownership filter — `.spoken` is not gated. Without it, a task could leave your briefing for someone with no device in the graph.

- **Undo-completeness.** A `ChangeLogUndo` arm restores *every field its action wrote*, not just the headline one. Worked example: `claim` stamps `ownerOrigin = .human`, so the `"assigned"` entry encodes `"<uuid>|<origin>"` (`TaskItem.encodeOwnership`) and the arm restores both — otherwise undoing a reassignment leaves an AI-inferred owner marked human and pollutes the affinity denominator.

- **Stack precedence lives in `Models/TaskRanking.swift`** (the Policy layer) and is a product invariant: Needs Decision forced top → Blocked sinks → **effective attention (desc)** primary → Blocking boost → Overdue boost. The band boosts are lexicographic sort-key components, never additive scores — the comparator must stay a strict weak ordering (property-tested in `TaskRankingTests`). The attention component is `attention.score + currentRelevance` — the ONE deliberate additive layer, *within* that component only: `currentRelevance` (live, never persisted, clamped ±25) is the decay fix — staleness (days since `lastHumanTouchAt`, NEVER `updatedAt`) and `deferralCount` pull down (that counter is **consecutive, not lifetime** — the day-rollover is the only site that raises it and `touchHuman` is the only site that clears it, so the penalty recovers the moment the user engages); a recent unblock, a freshly-gained dependent, a related due date approaching, or a **fresh start commitment** (`startedBoost`, `.doing` entered within `recentWindow`) pull up. **`.doing` may touch this layer and no other** — it is the fastest fact in the system, and the persisted score reads slow inputs only; the boost is a peer of `recentUnblockBoost` (12.0) rather than the clamp, since the clamp is a shared budget and a term that large would collapse the layer into a boolean. It is gated on the **current open visit** (`TaskItem.currentStateEnteredAt`), never `secondsIn(.doing)` (which sums every visit, so a resumed task would age out while genuinely fresh). It is **precomputed once per snapshot into `RankKey.effectiveAttention`** — never evaluated inside the comparator (graph terms + `now`-windows would be O(n²) and break the strict weak ordering). The hard bands stay fact-fed and the AI still never decides the band. (`RankBand`, renamed from the old `AttentionLayer`, is the internal sectioning band — never rendered.)
- **Always-confirm capture** (`docs/PRD.md`). Nothing is gated on confidence at capture: engines emit `TaskIntent`s (raw `dateExpression`/`personReference`, never resolved by the model), the deterministic `IntentResolver` produces drafts — which carry **no lifecycle position at all**, because a draft is not a task — and **backfills any metadata the engine left empty** (importance, effort, owner, **kind of work**, **due date**), so every field reaches the confirm card populated and editable. **Due dates are now proposed from a task's nature, not only from a spoken phrase** — a deliberate reversal of the old "an undated task stays honestly undated" rule, contained four ways: `IntentResolver.inferredDueDate` is a short explicit table (recurring bills → month end; renewals → +14; filings/deadlines → +7) rather than a general guess, it is **suppressed for any task carrying a blocker phrase** (a task that can't start is exactly where an invented date becomes a false Overdue — and the blocker's own words sit in the title), it returns a `TaskDraft.dueReason` rendered under the chip so the proposal explains itself while it is still one tap to clear, and it **never feeds `inferredImportance`** (which reads the SPOKEN date only, or a guess would inflate the attention score). Accepted cost: `TaskItem.isStale` only fires on undated tasks, so a proposed date takes the task out of stale detection. `IntentResolver.resolveDate`'s own vocabulary is wider than the phrase list suggests (relative offsets, month/day, week and month boundaries) and **its arm order is load-bearing** — overlapping phrases like "day after tomorrow"/"tomorrow" and "this weekend"/"this week" resolve by specificity, not list position. The Confirm-Creation glance ("Add N tasks" in `ComposerView`) is the single human-in-the-loop moment, and `AppBrain.commit` is what turns drafts into `TaskItem`s born `.todo` with `confirmedAt` stamped. Every field edited at confirm is diffed against `TaskDraft.aiOriginal` and written as a `Correction` row (write-only learning signal). One `Capture` row per capture event, raw text verbatim forever. **The auto-accept invariant:** capture-time inference is auto-accepted — no AI confidence value gates whether an inferred field is applied; the Confirm-Creation card is the only human-in-the-loop boundary, where inferred values become visible and editable. The single exception is inference that destroys or merges existing user data (the duplicate merge), which stays confidence-tiered (0.85/0.5). **The ≥0.85 tier now extends to EXISTING pairs** (`AI/DuplicateSweep.swift`, product decision 2026-08-07): a background sweep finds embedding-near + lexically-overlapping open pairs (both floors; the lexical floor IS `DraftMerge.retitleSimilarityFloor`), the on-device model judges each through `ModelRun` (`.duplicateSweep`, background deadline, hard caps: 20 pairs/5 judgments per hourly run), and ≥0.85 merges **kill-don't-delete** (older task wins, absorbs "Also captured: …", loser `kill`ed reversibly) with an Inbox-visible `"mergedPair"` entry whose Undo reopens the loser intact, strips the absorbed note, and writes a pair suppression so the pairing never re-proposes. A judgment call or open decision is never the loser; off-device the sweep is absent entirely. It deliberately lives OUTSIDE `BrainSweeps`' silent tier (its header names the exception) and shares only the hourly debounce. Every new inferred field inherits this rule.
- **The judgment-category rule is a permanent carve-out.** Values-laden decisions are always `.ask` tier (`AutonomyPolicy.tier`), carry `needsDecision` from birth, and — crucially — `confirm()` does NOT clear a judgment call's flag (confirming the task exists ≠ making the call); only `resolveDecision()` does. `BrainSweeps` never touches a judgment call or open decision. `autonomy` is DERIVED from tier, not stored.
- **Every status change funnels through `TaskItem.status`'s setter**, which calls `transition(to:now:)` to record the `StateVisit` timeline and bump `updatedAt`. Never write `statusRaw` directly; never expose `$task.status` as a two-way binding; callers with an authoritative timestamp call `transition(to:now:)` (see `complete(now:)`/`kill(now:)`). **Every mutation helper bumps `updatedAt`** — Stale detection and the auto-archive depend on that honesty (the detail sheet's `.onDisappear` bumps it for direct `@Bindable` edits).
- **Blocked is always derived, never written.** A task reads as blocked iff `activeBlockers(among:)` is non-empty; there is no `block()`. An Active task that gains a blocker STAYS Active. Blocking is the derived reverse edge (`isBlocking(among:)`) — never stored, never labeled. On an existing task the AI only ever authors `.task` blockers (origin `.inferred`); the one sanctioned AI-authored `.external` is a captured wait whose phrase matched no task at commit. **Storage:** blockers + parent edges live in ONE versioned `relationshipsData` blob as `[Relationship]` (`Models/Relationship.swift`, v2: kinds `.blocks`/`.parent`/`.related`, each with an `Origin` — `.human` or `.inferred(confidence:)`, so a human edge structurally can't carry a confidence). `blockers` and `parentTaskID` are READ-ONLY derived views; **every write funnels through the `TaskMutations` helpers** (the mutation choke point — never assign `relationships` from a view/engine). **Live edges are the only edges** — a rejected merge/link suggestion is a `RelationshipSuppression` in the pair-owned store (`Models/RelationshipSuppression.swift`), never a dismissed edge: capture-form keyed on (target, normalized DRAFT TITLE) so a "no" sticks across captures (a fresh draft id can't match a pair key), plus a pair form (duplicate: symmetric canonical key; parent: directional) for both-tasks-exist consumers; rows expire (`SuppressionStore.maxAge`) and orphaned rows prune lazily at load. Invariants are DEBUG-asserted on encode (`Relationship.validate`) and property-tested (`RelationshipTests`).
- **The Today briefing is AI-authored — the advisor selects, orders, and sizes it** (`docs/PRD.md` §8). This deliberately REVERSES the prior "model never ranks" rule *for the Today plan* (a documented product pivot). The model is now an expert advisor that returns an `AdvisorBriefing` (headline · chosen actions · tradeoffs · risks) — it picks which candidate tasks matter, their order, and how many. `TaskRanking` is demoted to two supporting jobs: it provides the capped candidate set handed to the advisor, and it is the deterministic **fallback** (sim / offline / on-device-off → top-N candidates by rank, fact-line lines, NO advisor voice). `GeneratedPlan.validated(against:)` is now only an **anti-hallucination guard** — drops ids that aren't real candidates, dedupes, backfills an empty line from facts, caps at `maxActions` (7); it does NOT reorder. The **capacity input is gone**: `CapacityLog` still logs daily throughput (vestigial `.steady`), and `CapacityBaseline(for: .steady)` is advisory *context only* (the advisor sizes). Tier routing is a simple ordered chain (`PlanRouting`: on-device → PCC → deterministic tail), so `AppBrain.todayPlan` never fails. Generation mutates zero task fields. **On-device resilience** (so a cold/slow model doesn't silently drop to the voiceless "Your day" fallback): the on-device deadline is **30s** (`onDeviceTimeoutSeconds`) with an output-token cap; `TodaySequenceModel.start` **prewarms** the model while the Recap cover plays; a deadline hit **salvages the last viable streamed partial** (headline + ≥1 action, via `PartialBox`) instead of discarding it; and a voiceless deterministic plan cached at the first open **self-heals** — a later same-day open re-generates in the background when on-device is available (`generate(preservePlan:)`, keeping the cached briefing on screen until the voiced one lands), rather than freezing plain for the day. Failures are no longer swallowed: `AppBrain.todayPlan`'s catch records a **typed** `PlanMetrics.lastError` + `lastTier` + `lastAvailability` (e.g. `timedOut` / `guardrailViolation` / `modelNotReady`), surfaced in the DEBUG diagnostics footer (`… · via <tier> · err <reason> · ai <availability>`) — the first thing to read when the advisor voice is missing on device. Cold-start Recap counts completions since **start-of-today** (`recapCutoff ?? startOfDay`).
- **`ChangeLogEntry` backs both Undo and the trail.** `initiatedBy` separates AI from human actions: the Activity Trail and the "AI handled N" count filter to `.ai` only. Every AI action is reversible and logged; `Metrics.acceptanceRate` counts AI entries only and **excludes `action == "planned"`** (a daily plan isn't a per-task action the user accepts — its undo clears the day cache).
- **Navigation is four tabs + a floating capture button.** `RootTabView`: Today (0, `TodayHomeView` wrapping `TodayView` + `TodaySequenceModel`), **Inbox** (1, `InboxView` — the household activity feed, absorbing the old AI Activity Trail: ALL change-log entries, avatar + action badge + unread dots + action-aware Undo), **My Tasks** (2, `TasksHomeView` — Linear-style "My issues": large title, `[search][…]` pill, a **Liquid-Glass** Assigned/Created pill (with a hairline separator before the filter icon; glass-merge via `glassEffectID`, flat-capsule fallback under Reduce Transparency), priority-bars + six-state status-glyph rows with **no dividers** (row height carries the rhythm), the chain stack kept; **Created** is flat + chain-stacked + newest-first via `MyTasksSlices.createdEntries`), and Household (3), plus a **circular Capture button** overlaid at the bottom-trailing corner **inline with the floating tab-bar capsule** (Linear's agent-button placement; its bottom inset is a tuned constant, not a pixel-lock — the bar geometry isn't public). Tapping a task opens the **full-screen Linear-style detail**, which is a **pager**: `TaskDetailPager` owns the chrome (nav bar, back chevron, "…" `TaskMoreMenu`, an "n of N" counter, the 20pt leading edge-swipe dismiss) and hosts a horizontally-paged `ScrollView`+`LazyHStack` of `TaskDetailView` pages (category kicker, big title, wrapping property chips, description, per-task Activity feed from the change log), so a **left/right swipe moves to the neighbouring task without leaving full screen**. What "neighbouring" means belongs to the PRESENTING surface, never to the detail: each call site hands `taskDetailSheet(_:peers:)` the ordered list it is currently rendering (`TaskDetailPeers.flatten` over My Tasks' sections/lane entries with chain stacks unrolled root-first; search results; the Today briefing's action order; Household's coordination/timeline feed), and the pager **snapshots it in `init`** so a live re-rank can't shuffle pages mid-swipe. Two invariants inside a page: it never dismisses itself on resolution — it calls `onResolved()`, and the pager advances to the next peer (dropping the resolved page) or dismisses when there is none; and anything with a cost or held state (model prewarm, keyboard focus) gates on `isActive`, because neighbours stay mounted (`.onDisappear` is NOT a reliable commit point, and `updatedAt` bumps must be scoped to `task.hasChanges`, never `context.hasChanges`). Screens jump to the Inbox via `\.openInbox`. **Today is a two-scene cinematic briefing:** Scene 1 = the **Recap** ("what you got done"), which doubles as the cover while the advisor reasons in the background; Scene 2 = the **advisor briefing** (headline · action plan · tradeoffs · risks), whose action steps are tappable and open the task. The **transition is data-driven, never timed** — it fires when generation completes AND the Recap entrance has played (via `withAnimation` completion, not `asyncAfter`). No Docket screen, no capacity input, no auto-advance timer, no progress bars. The briefing **plays once a day** — the reset is ONE swappable predicate, `TodayPlanStore.shouldReplay(now:)`; nothing else may test the date. Screens open the composer via `\.openCapture`, never their own sheet.

- **The app sends exactly ONE notification, and it is a named carve-out.** `BriefingReminder` (`Features/Today/BriefingReminder.swift`) posts a single daily "your briefing is ready" local notification: **off by default**, at a user-picked time, no badge/count/escalation, and it **never fires on a day the sequence already played** (`TodayPlanStore.sequencePlayedToday` feeds `BriefingSchedule.occurrences`, a pure rolling 3-day horizon of one-shot triggers — a `repeats: true` calendar trigger cannot skip a day, which is the whole point). This is an explicit exception to the **"notification-driven re-engagement"** refusal in `prev-docs/product-guardrails.md`, recorded there in full; **a second notification type is the signal the carve-out has been abused**, not a precedent. Two coupled invariants: permission is requested from the Settings toggle and NOWHERE else (never at launch), and a notification-originated foreground is **excluded from `Metrics.selfInitiatedOpens`** (`consumeCameFromNotification`) — an open the app solicited is not pull, and counting it would turn the one honest engagement metric into the vanity number the guardrails refuse.
- **Clean-break schema policy.** No migrations: `Project_EzraApp` keeps a `schemaGeneration` integer (UserDefaults, **currently 10** — 9→10 is the **four-axis model**: the lifecycle collapses to one field (`stageRaw` gone, `TaskDisplayStatus`/`TaskStage.swift` deleted, `statusRaw`'s vocabulary re-meaninged), `ownerPending` → `ownerOriginRaw`, `workIntentRaw` loses `waiting`, and `Capture` gains `draftsData`/`committedAt`. **This spends most of the remaining clean-break budget** — the wipe-on-mismatch escape hatch closes the day `HouseholdSync.isLive` flips, because a deployed CloudKit schema is additive-only with no server-side reset; treat everything after this as additive-in-practice and run a schema-freeze review gated to that flip. Earlier: **9** — 6→7 was the **attention substrate** (retires user-facing Priority for signals + a persisted score + the `relationshipsData` graph blob + `workIntentRaw`); 7→8 **retires the Pinned signal**; 8→9 is the **relevance + suppression substrate**: TaskItem gains `deferralCount`/`carriedOverCount`/`lastSurfacedAt`/`lastUnblockedAt`/`lastHumanTouchAt`, `relationshipsData` moves to v2 (`Origin`, no tombstones), and the `SuppressionRecord` + `EmbeddingCache` entities land) and destroys the store on mismatch — bump it whenever a change alters the *meaning* of stored data (renamed raw values, repurposed fields), not just its shape. The container-open self-heal remains as the backstop.

- **The store now holds real work, so a wipe is backed up and visible — and the model is versioned.** Three rules, all in force from the moment daily use began:
  1. **Never edit the current `.xcdatamodel` version in place.** `ProjectEzra.xcdatamodeld` is a versioned set (`ProjectEzra.xcdatamodel` + `ProjectEzra 2.xcdatamodel`, currently identical, `.xccurrentversion` pointing at the latter). Lightweight migration needs the OLD version to still exist in the bundle; editing the current one in place leaves the on-disk store with no source model, `loadPersistentStores` fails, and the self-heal destroys it — **with no `schemaGeneration` bump and, before this, no notice at all.** Always add a NEW version (Xcode ▸ Editor ▸ Add Model Version; hand-authoring the directory works too — the group is filesystem-synchronized, so `momc` picks it up with no `project.pbxproj` edit). `makeContainer` pins `shouldMigrateStoreAutomatically`/`shouldInferMappingModelAutomatically` explicitly for this reason. A **DEBUG tripwire** in `Project_EzraApp` compares `PersistenceStack.modelDigest` against the last launch's and asserts when the model moved without a generation bump.
  2. **Every reset takes a safety copy first.** `PersistenceStack.destroyStore(reason:)` requires a `StoreResetReason` and copies the sqlite + `-wal` + `-shm` into `backupsDirectory` (last 5 kept) before deleting. Restore path: Xcode ▸ Devices and Simulators ▸ Download Container. There is deliberately **no in-app restore** — it needs the store closed and the app relaunched.
  3. **Every reset is reported.** Both wipe paths write a `StoreResetRecord` (`Models/StoreResetRecord.swift`, UserDefaults-backed so it survives the store it describes), which `SettingsView` leads with until dismissed, ShareLink to the backup attached. Additionally, `DataExport` (`Models/DataExport.swift`) is a pure `Codable` snapshot of tasks/captures/change log/corrections/capacity/profile/members — readable JSON, no photo blobs, graph edges decoded — shared from Settings ▸ Data.
- **Design system is the single source of truth.** Use `Palette`, `Font` extensions, `Spacing`, `Radius`, and `LayoutMetrics` from `Design/`. Never hardcode colors, font sizes, spacing, or layout metrics in views (incl. `Font.heroNumeral`/`heroDisplay` and the `Motion` Today springs — never a raw 64/72 or inline spring; never a raw `28`/`44` glyph frame — use `LayoutMetrics.recordGlyphColumn`/`hitTarget`; never a raw `.system(size: 9/10/11)` chip label — use `Font.chipLabel`/`chipLabelTight` + `IconSize.micro`/`nano`). The cobalt→cyan `Palette.accentGradient` is for high-signal sites: the AI tag, **primary CTA buttons**, the Needs-Decision edge stroke, the composer's processing border, and the Today briefing's hero-action edge; use `Palette.accentFlat` elsewhere — **including the active tab, which renders flat via `.tint`, NOT the gradient.** **Attention hues are split, one meaning per token** — `priorityUrgent` (red, the Urgent `SignalMarker`/toggle/pill), `statusInProgress` (amber, the In-Progress status glyph only), `overdue` (orange, past-due markers), `householdAttention` (amber, Household surfaces); never reuse `warning` for these (the old amber-means-four-things collision). The one "judgment / your-call" blue is `Palette.decisionAccent` (used by ConfidenceRow `.ask`, AssessmentChip Needs-Decision, the confirm judgment flag, the detail decision banner) — never fork `accentStart`↔`accentFlat` for it again. Every editable metadata capsule routes through **`MetadataChip`** (`.standard` = bordered 44pt tap target; `.compact` = dense borderless), never an ad-hoc capsule. The Today backdrop's drifting glow (`Palette.backdropGlow`) is on-brand accent-family atmosphere, off under Reduce Transparency.
- **Liquid Glass is a design system, not per-view (`Design/Glass.swift`).** Route ALL app glass through `.glassChrome(in:tint:interactive:morph:)` / `.glassCapsule(...)` — never hand-roll `.glassEffect` in a view. Rules the modifier enforces: **glass is chrome, never content** (rows/cards/section headers/chain stacks are solid `Palette` surfaces — no `.blur`/material on content; that was the "muddy" anti-pattern); **glass never carries primary text** — Liquid Glass imposes a **vibrancy that desaturates foreground text** (a label on glass reads dimmer than one beside it, and NO scrim behind the text can rescue it — verified in-sim), so a **text-bearing selection chip uses a solid `elevatedSurface` surface + hairline, NOT glass** (see the Assigned↔Created pill in `TasksHomeView` — a solid chip with a `matchedGeometryEffect` morph); glass stays for **icon + press affordances** only; **neutral `.regular`** for plain chrome (a tint over the near-black list has nothing to refract and reads muddy) — an accent `tint` is passed ONLY by the signature AI tile (`HeldDepthView`); `.interactive()` on tappable glass; a **solid `secondarySurface`+border fallback under BOTH Reduce Transparency AND Increase Contrast**. The `GlassEffectContainer` lives at the **composite-region call site, never inside the modifier** — `glassEffectID` morphing needs one container spanning both endpoints. System chrome (tab bar, toolbars) is left to the OS; the Capture FAB is the one app-chrome exception (gradient CTA + interactive glass lens, no text). Blocked/inactive content recedes via `.recessed(_:)` (a contrast-aware dim, floor raised under Increase Contrast) + a `BlockedIndicator` `hourglass` marker — **never a blur** (superseded the old frost).

- **Every model call goes through one seam** (`AI/ModelDeadline.swift` · `ModelResult.swift` · `ModelRun.swift`). `ModelRun.perform(_:deadline:)` owns availability, the deadline, cancellation, error labelling, and metrics, so a service is only its prompt and its parsing. **Deadlines:** `cardSeconds` (20) for a card the user is watching, `backgroundSeconds` (10) for re-classification nobody is waiting on, `captureSeconds` (30) for the composer's live parse; unbounded calls are the bug this replaced — a cold model left a spinner the user could not escape. **Capture's deadline is not a failure threshold** — measured on device (`-CaptureDiagnostics`), a 648-char/13-item ramble finished at NEITHER 20s nor 30s (5 drafts → 11 drafts, both hitting the wall), because generation scales with how much was dumped and "dump it all" is unbounded. It is the point where we stop waiting for MORE: salvage costs completeness, never the capture, and the user watches candidates stream in and can confirm at any moment. So a deadline hit on a long ramble is the EXPECTED path, recorded as `.salvaged` (a served user) rather than `.timedOut` (a failure) — `Stats.served` is successes + salvaged. **If long captures ever need to be genuinely complete, chunk the input; do not raise the number.** `ModelResult` is the product vocabulary (`success`/`unavailable`/`timedOut`/`cancelled`/`failed(label)`) and keeps `LanguageModelSession.GenerationError` **out of SwiftUI**; `.unavailable` and `.cancelled` are deliberately NOT `isRetryable` (nothing to retry without a model; re-offering after the user left is nagging). **Cancellation keys on `isActive`, never `.onDisappear`** — the pager keeps neighbours mounted, so a swiped-past page never disappears. `TodayPlanService` delegates the race but **keeps throwing**: its tier chain falls through on `throws` and `errorLabel` maps `PlanGenerationError.timedOut` to the string the DEBUG footer reads. `FoundationModelsEngine`'s capture calls are deliberately excluded — capture has its own rolling parse cadence (debounce + max-wait + chain-on-completion) and a streaming partial contract. `ModelMetrics` (`AI/Metrics.swift`, the `PlanMetrics` pattern) records per-capability successes/timeouts/failures/latency **locally, never transmitted** — the guardrails refuse vanity metrics, and it exists so the deadline is tuned on evidence rather than argument.

## Two-engine AI

`AI/AIEngine.swift` defines the seam; `FoundationModelsEngine` (real on-device LLM, iOS 27) and `HeuristicEngine` (deterministic fallback) both conform and emit `[TaskIntent]` via `triage(rawText:context:onPartial:)`. `AppBrain` selects the engine at launch via `SystemLanguageModel.default.availability` and degrades to the heuristic on failure. **The simulator is NO LONGER guaranteed to be the heuristic path** — verified 2026-07-26 on Xcode 27 / iOS 27.0 sim, where the Inbox diagnostics footer reads `Apple Intelligence · on-device`, i.e. `availability == .available` and the sim runs the REAL on-device model. (It follows the host Mac's Apple Intelligence, so it varies by machine.) Two consequences: never assume a sim run exercised the heuristic — read the footer; and the sim can no longer verify off-device/absent-card behaviour, which now needs a device (or host) with Apple Intelligence off. **Unit tests are unaffected** — `onDeviceAvailable()` still hard-returns false under XCTest. Keep both engines behaviorally consistent — the shared derivation lives in `AutonomyPolicy.tier` + `IntentResolver` (including `applyRules`, the learned-correction half both engines get for free).

The ramble pipeline (see `docs/PRD.md`):
- **`TriageContext`** carries personal context per call: `personalization` (top-N learned corrections as instruction lines, built by `CorrectionProfile`), `roster` (value snapshots backing `ResolvePersonTool` — the tool attaches only when a roster exists; mind the beta tool-over-calling caveat below), and `candidates` — the **capture-graph candidate package** (`ContextRetrieval` ranks the open set against the capture: NLEmbedding + lexical + category + recency, cap 12; the `[uuid] title — facts` package is the ONLY valid ids the model may cite for duplicate/child/blocks). **Candidates RIDE THE CHAIN (audit A1)**: retrieval runs concurrently with generation, never ahead of it — the first parse of a burst prompts candidate-blind (proposals are refinements, not prerequisites), each parse's retrieval returns in its `TriageRun` and becomes the NEXT parse's prompt package, the final resolve of every parse sees prepared ∪ fresh, and a single-shot on-device capture gets ONE bounded enrichment re-parse (`suggestsEnrichment`) so duplicate detection still lands. Capture sessions are pooled (`CaptureSessionPool`, single-use, fingerprinted on instructions+roster, prewarmed with the REAL instruction prefix + prompt head — `ModelWarmup`'s anonymous session never covered it); a continuous session stays deferred. The resolver tiers the model's claims into `EdgeProposal`s **by destructiveness, not uniformly** (the auto-accept invariant): `duplicateOf` (a merge destroys data) keeps ≥0.85 accepted / 0.5–0.85 undecided / <0.5 suppressed; `childOf` (additive, reversible) is auto-accepted at ≥0.5 (`.undecided` is duplicate-only). Previously rejected pairings are dropped at the resolver via the suppression set (passed through `TriageContext.suppressions`). At commit an accepted duplicate **merges** (no new task, reversible "merged" entry that Undo resurrects), a rejected proposal writes `SuppressionRecord`s, an accepted child becomes a reversible `.parent` link. **The heuristic path lacks proposals + workIntent by design** (Apple Intelligence is assumed present; those features are simply absent in the sim, which exercises the heuristic).
- **Streaming**: on device, `onPartial` receives resolved partial candidates from `streamResponse` snapshots mid-generation; the heuristic ignores it (instant). **The composer's parse ROLLS** (`ComposerView.scheduleTriage`/`startParse`): a ~400ms debounce for quiet gaps, a max-wait (~1.2s) so continuous input — dictation's volatile deltas land faster than any debounce survives — still fires a parse, and **new input never cancels a running parse** (its partials are streaming onto the screen; a follow-up over the fuller text chains at completion, and only the newest-started parse's results apply via `parseEpoch`). Partial merges KEEP cards the snapshot hasn't reached yet (`DraftMerge.merge(keepingUnmatched:)`); only a completed parse may drop a card. Mid-session park writes are throttled (~2s, `force` on dismiss).
- **Low confidence is a visual state** (dimmed + "?" on the confirm card), never a held queue.
- **Eval harness**: `RambleEvalTests` scores the pipeline per-field over ~40 labeled rambles with regression floors — extend the fixture set when capture behavior changes, and re-calibrate floors only downward from observed numbers.

Guarded test seams in `RootTabView` (no effect in normal runs):

Use this to exercise all four beats.
- `-InitialTab N` — start on tab N (0 Today, 1 Inbox, 2 My Tasks, 3 Household).
- `-OpenTaskDetail [N]` — open the full-screen detail pager on the Nth row of My Tasks' visible list (default 0), so the paged surface is reachable without a tap. Pair with `-InitialTab 2`.
- `-OpenCapture ["text"]` — present the capture composer at launch (it only opens from a tap otherwise). With a text argument, the seam parks that text as a `Capture` and resumes it, which re-parses through the full live loop — the streaming/rolling parse becomes screenshot-observable without a keyboard.
- `-CaptureDiagnostics` — run a long ramble through the ACTIVE engine and print tier, wall-clock, draft shape, and the `ModelMetrics` tallies to **stdout**. Built for the one question only real hardware answers (on-device model behaviour), and readable headlessly: `xcrun devicectl device process launch --device <udid> --console --terminate-existing amanze-studios.Project-Ezra -- -CaptureDiagnostics`. Those numbers previously existed only as text on a DEBUG footer — i.e. only to a human holding the phone — which is why device-verify had been a checklist someone performed rather than a command. Deliberately does not commit, so it is safe to re-run. **Device runs are fully headless except the launch, which needs the phone unlocked** (build/sign/install all work over the cable); poll `devicectl process launch` until it stops erroring `Locked`.
- `-OnboardingResult` — on a **fresh install** (the arg only fires from the `.welcome` phase), parse the built-in sample dump and jump straight to onboarding's editable result scene. That screen is the product's first impression and was the one surface no launch arg could reach — every other screen has a seam, and synthetic taps are blocked on this host, so it could previously only be reviewed in code.

Synthetic UI taps via AppleScript are blocked by macOS Accessibility permissions here — use these launch args to reach a screen state instead of scripting clicks.

**Running on a physical device (iOS 27) with a launch arg:**
- Launch arguments are **only passed when Xcode launches the app via Run (⌘R)** — never on Build (⌘B), and never when you tap the app icon on the phone. Set the arg in the **shared** scheme: *Edit Scheme ▸ Run ▸ Arguments ▸ Arguments Passed On Launch* (tick the checkbox), pick the iPhone as the destination, then ⌘R.
- The Run action is **Debug** by default, so any `#if DEBUG` affordance is compiled in on device runs — e.g. the **plan-tier readout** (`plan: on-device N · pcc N · rules N · last Xms`) in the `InboxView` diagnostics footer (and `SettingsView`) that shows which Today-plan tier actually ran. It is stripped from Release/Archive.
- `-SeedTodayFixtures` **force-reseeds on every launch** (`TodayFixtures.reset` + `seed` in `RootTabView.seedTodayFixturesIfRequested`) — wipes prior tasks/CapacityLog + the Today day-cache first, so a used store still shows the set without deleting the app. The other seed args keep the empty-store guard.
- **PCC never runs on device until entitled:** `PrivateCloudComputeLanguageModel` *traps* (uncatchable) the instant it's constructed without the managed `com.apple.developer.private-cloud-compute` entitlement, so the PCC tier is gated behind the compile-time `PCCEntitlement.isGranted` (`TodayPlanService.swift`, currently `false`) — routing/generation both short-circuit before construction. Flip it only once the entitlement is provisioned in signing.

## Platform & design references (iOS 27 beta)

Target the iOS 27 SDK. Canonical, authoritative sources — consult these (not memory) for anything version-specific:
- Human Interface Guidelines — https://developer.apple.com/design/human-interface-guidelines
- Foundation Models — https://developer.apple.com/documentation/foundationmodels
- iOS & iPadOS 27 release notes — https://developer.apple.com/documentation/ios-ipados-release-notes/ios-ipados-27-release-notes
- Xcode 27 release notes — https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes

Verified specifics that affect how code is written here:

- **Liquid Glass.** The API is the same as iOS 26 (confirmed against the SDK's `SwiftUICore.swiftinterface`): `.glassEffect(_:in:)` with `Glass.regular` / `.clear` / `.identity`, `.tint(_:)`, `.interactive(_:)`, plus `GlassEffectContainer`, `.glassEffectID`, `.glassEffectUnion`, `.glassEffectTransition`. **iOS 27's improved diffusion of complex content is automatic** — there is no new parameter; you get it by putting real content behind a genuine `.glassEffect()`, not by faking a blur. Glass is for **chrome, not content**, and must adapt to Reduce Transparency / Increase Contrast — always provide a flat, non-glass fallback (see `HeldDepthView` in `Features/Components/HeldDepthView.swift`, and the Today capacity capsules' solid fallback).
- **Foundation Models** is iOS 26+ and unavailable on non-Apple-Intelligence devices — always gate on `SystemLanguageModel.default.availability` and keep the `HeuristicEngine` fallback working. (It is **not** reliably absent in the simulator any more — see the two-engine section above.) Use guided generation (`@Generable` + `@Guide`) rather than parsing JSON; consider use-case models (`SystemLanguageModel(useCase:)`) and streaming (`streamResponse`) where they fit. **Device-verify any `@Generable` schema change** — the sim cannot exercise it.
- **Guided-generation tool-calling bug (Xcode 27 beta, tracked in the iOS 27 release notes):** the on-device model can call tools excessively when guided generation is in play. `FoundationModelsEngine` doesn't use `Tool` yet, but if that's added (the personal-context tools are on the deferred list), tighten `instructions`/prompt wording first before assuming a code bug if triage output gets erratic or slow.
- **`#Preview` now runs on the main actor** (Xcode 27) — previews of main-actor-isolated views/view models no longer need workarounds for concurrency warnings. `PreviewProvider` is deprecated in favor of the `#Preview` macro; don't add new `PreviewProvider` conformances.
- **Instruments has a Foundation Models instrument** (traces instructions/prompts/responses/token usage) — reach for it over ad hoc logging when profiling `FoundationModelsEngine` latency or debugging odd triage output.
