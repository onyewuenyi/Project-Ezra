# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Project Ezra** ("Managing Chaos, Effortlessly") — an AI-managed personal task system for iOS. SwiftUI + Core Data, single app target. **The product spec is not in this repo** — it is *Ezra — Product Shape v6* (https://claude.ai/code/artifact/fbbfbae1-f7a5-4bdd-bd6f-19454dad89ad), and it is the source of truth for what the product is, what Ramble/Brief/Advisor are for, how the intelligence ladder is paid for, and what the MVP cuts. Read it before changing product behaviour; where this file or any doc disagrees with it, the artifact wins. What stays in the repo is architecture and craft: `docs/README.md` (the map), **`docs/task-model.md`** (the four axes — the deep reference this file points at rather than restating), **`docs/primitives.md`** (the durable core + the bloat-watch test), and three still-in-force files in `prev-docs/`: the **design system** (`design-system-managing-chaos.md` — design language in force, its screen inventory historical), the **product guardrails** (`product-guardrails.md`), and the **household architecture** (`household-architecture.md`). Nine superseded docs were deleted on 2026-08-24; `docs/README.md` lists them and why, so nobody goes looking.

## Posture — research preview, on purpose

**This is a single-developer research and development build, deliberately running on non-GA and beta software.** Xcode 27 beta, the iOS 27 SDK, Foundation Models' year-two APIs, and a branch-pinned Firebase AI Logic preview are all *intentional* choices, not risks to be managed down. The point of this project is to explore new platform capabilities early.

What follows from that, and what an agent working here must not undo:

- **Do not gate a capability on evidence that does not exist yet.** "Ship it once the benchmark proves it" is the wrong default here — turn it on, then measure. Evals (`AdvisorBenchmark`, `-CaptureDiagnostics`, `RambleEvalTests`) exist to *tune* what is running, never to grant permission for it to run.
- **Do not add "wait for GA" caveats.** Preview APIs reshaping before GA is expected and accepted. If an SDK breaks, fix it then.
- **Do not soften a capability to something safer without being asked.** Prefer the strongest available option and let a measurement argue it down.
- Two things this posture does **not** relax, because they protect the user rather than the schedule: **safe defaults for data** (the deterministic tail must always exist, `validated(against:)` still rejects untrusted model output, corrections still never leave the device) and **the guardrails in `docs/` about what the product refuses to do**. Explore capabilities freely; don't quietly change the product's promises.

## Toolchain — non-negotiable

- **Build with Xcode 27 (iOS 27 SDK).** The deployment target is iOS 27.0. Xcode 26 has no iOS 27 SDK and the build fails. Confirm with `xcodebuild -version` (expect 27.x). If it shows 26.x, the active toolchain is wrong: `sudo xcode-select -s /Applications/Xcode-beta.app/Contents/Developer`.
- Swift language mode is 5.0 (not Swift 6 strict concurrency), but `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` — types are main-actor isolated by default.
- **firebase-ios-sdk is pinned to the `wwdc26-preview` BRANCH, not a version — deliberately.** That branch is the only place `GeminiLanguageModel` exists (Firebase's bridge conforming Gemini to `FoundationModels.LanguageModel`), and it is the entire reason the cloud rung can be a `LanguageModelSession` like every other rung. A tagged release does not have it and `GeminiProvider` will not compile against one. Cost of a branch pin: every resolve pulls whatever is on it, so a broken upstream commit breaks the build with no version to blame — accepted, and the reason to check `Package.resolved`'s pinned commit first when a build breaks for no local reason. This is a deliberate preview dependency, not a debt to retire on a schedule.
- **Host needs macOS Tahoe 26.4+** to run Xcode 27 at all; if Address Sanitizer fails to launch on the iOS 27 simulator, that's a known Xcode 27 beta issue on host toolchains older than **26.5** — update Xcode, not the code. Apple silicon only: Xcode 27 no longer builds Intel/`x86_64` by default (`ld64` is gone; `-ld_classic` is no longer an option).

## Build & run

```bash
# Build (iOS 27 simulator)
xcodebuild -project Project-Ezra.xcodeproj -scheme Project-Ezra \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro,OS=27.0' -configuration Debug build
```

```bash
# Run the unit tests (Swift Testing) on the iOS 27 simulator.
# -parallel-testing-enabled NO is REQUIRED: fixtures build Core Data managed objects in a
# single shared in-memory context (see PersistenceStack.scratch / TestStore), which has
# thread affinity — Swift Testing's default parallelism crashes it. Run tests serially.
xcodebuild test -project Project-Ezra.xcodeproj -scheme Project-Ezra \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro,OS=27.0' \
  -parallel-testing-enabled NO
```

Prefer the `/run-sim` skill for the full install + launch + screenshot loop. A clean build is sufficient to consider a change done (launching the sim is optional, not required). Tests live in `Project-EzraTests/` (Swift Testing, `@testable import Project_Ezra`) and cover the pure AI/ranking logic — `AutonomyPolicy`, `HeuristicEngine`, `IntentResolver`, `CorrectionProfile`, `TaskRanking`, `BrainSweeps`, the Today pipeline (`TodayQueriesTests`, `CapacityBaselineTests`, `DeterministicPlanTests`, `PlanSanitizeTests`, `PlanRoutingTests`, `TodayPlanStoreTests`), plus the `RambleEvalTests` accuracy harness; add cases there when you touch those.

**Known test-runner flake (environmental, not a code bug):** the whole suite passes (all cases green) but the run occasionally ends `TEST FAILED` via `Restarting after unexpected exit` — a *bare* crash of the test host with **zero** Core Data exceptions in the log, always alongside the iOS 27 simruntime warning `objc[…] Class UIAccessibilityLoaderWebShared is implemented in both WebCore.axbundle and WebKit.axbundle … may cause … mysterious crashes`. That's the Xcode 27 beta simulator's own accessibility-bundle conflict, not our code (diagnosed: the correct single-context test architecture throws no CoreData exceptions; only broken multi-coordinator variants did). If a run flips to failed with no `✘` cases and no `NSInvalidArgumentException`, just re-run (or use a freshly-booted sim).

## Project layout & Xcode gotcha

- The target uses a **PBXFileSystemSynchronizedRootGroup** (`Project-Ezra/`): any `.swift` file added under that folder is compiled automatically. **Do not hand-edit `project.pbxproj` to add/remove files** — just create or delete them. (Editing the pbxproj is only warranted for build settings.)
- Source is feature-organized: `Design/` (design system), `Models/` (Core Data `NSManagedObject` models incl. `CapacityLog` + `CapacityBaseline` + `PersistenceStack` + pure ranking), `AI/` (engine layer + the Today plan generators/service), `Features/<Screen>/` (`Brief/`, `Tasks/`, `Capture/`, `Activity/`, `Household/`, `Root/`), `Features/Components/`. Persistence is Core Data via `NSPersistentContainer` (`NSPersistentCloudKitContainer`-ready — flip `PersistenceStack.cloudKitContainerID` + add the iCloud entitlement to enable sync); models are constructed with the `in:` context convenience inits.
- `Item.swift` is a retired template stub — the real model is `Models/TaskItem.swift`.
- Three utility seams worth knowing before you re-invent one: **`AI/SerialGate.swift`** (one-at-a-time execution for a resource that cannot be re-entered — `BriefSession` caches one `LanguageModelSession` per day and Foundation Models rejects a second concurrent `respond`; the rule it enforces is *the stored task must wrap the WORK, not the wait*, and it exposes `peakActive` so a test can assert the invariant rather than infer it from outputs). **`AI/CaptureProvenance.swift`** (the per-capture receipt — route, rung, winning arm, latencies, the full `[TaskDraft]` — as a JSON **file sidecar**, never Core Data, because *a diagnostic must never be able to cost the user their data*; follow that rule for any new diagnostic). **`AI/DeterministicReading.swift`** (rung 0's Advisor reading, so a worthy task is never a labelled empty surface).

## Architecture invariants

- **Four axes, never fused** (`docs/task-model.md`). (1) **Lifecycle** — `TaskStatus` (`.todo → .doing → .done | .canceled`), user-owned. **A `TaskItem` comes into existence at Confirm and never before**: the retired `.inbox` case was a ghost (every creation path confirmed in the same breath), so pre-Confirm state now lives on a parked `Capture` — raw text plus encoded drafts — which is explicitly *not* a task. `AppBrain.commit` IS the confirm; there is no `confirm()` mutation. `status.isLive` replaces the old `== .active` checks. (2) **Type** — `WorkIntent` (action/planning), **INTERNAL and system-owned since 2026-08-11**: no kind chip anywhere, no user-editing path (DEBUG-asserted in `markEdited`); the write chain is engine/backfill → `reclassify` only, its consumers are the Today advisor (`promptOnlyFacts`) and the breakdown bias, and its classifier is evaluated (`RambleEvalTests` kind floor) — trust through evaluation, not correction.workIntentChip`) — and there ONLY. The confirm card no longer renders it at all: the reveal shows the user-relevant consequence ("Needs a plan"), never the classifier, so the axis is internal until the task exists. It is **never nil at creation**: the on-device model classifies it, and off device (heuristic path, Apple Intelligence off/unavailable by region) `IntentResolver.inferredWorkIntent` backfills it lexically. That backfill **never reads `isJudgmentCall`/`needsDecision`**, which would re-fuse axes 2 and 3 (test-enforced by `IntentResolverTests.workIntentIgnoresJudgmentFlag`); its `.action` default is behaviourally identical to nil (same CTA verb, same capability set). Nil remains legal on the model (fixtures, a cleared value). The **Thinking Partner** is unlocked by the `needsDecision` flag OR choice-shaped wording (`DecisionShape`, the one decision lexicon) — never by this axis, which NEVER reads/writes `needsDecision`. **Three cases are retired:** `decision` (2026-08-08 — choosing is a capability the system brings, not a kind of work the user classifies; stored `"decision"` decodes as `.planning` via `WorkIntent.decode`, additively, no wipe), `waiting` duplicated the derived `blocked` flag, and `reference` existed only to be *excluded* — removing it collapsed `countsAsWorkload`, five gates, a bespoke heuristic detector, `MyTasksSectionKind`, and the `"reclassified"` verb. (3) **Attention flags** — Needs Decision (stored `needsDecision`), Blocked/Blocking/Overdue/Stale (derived on read, never stored). (4) **Signals** — `isUrgent`, human-declared, feeding a computed **system score** (`AttentionEngine` → persisted `AttentionMetadata`, 0–100 + contributors) that `TaskRanking` uses only to break ties WITHIN the hard bands. The score is NEVER a badge. **Persist-slow/compute-fast:** it reads only slow inputs (urgent, AI importance, effort shape, graph centrality) and never a fast fact, so "the AI never decides the band" holds by construction. Don't re-fuse these: adding a blocker must not move the status; high confidence must not auto-resolve a judgment call.

- **The row's leading marker is one slot with two residents.** `SignalMarker` renders **Needs Decision** (`decisionAccent`) or **Urgent** (`priorityUrgent`), decision winning when both are set, nothing when neither — the slot means "the one thing most demanding your attention", which is honest about being a composite. **This reverses the old "Needs Decision is detail-only, not on rows" rule, deliberately.** What must NOT appear there is the task's *type*: choice-shaped wording and `needsDecision` (axis 3) are different questions, and one glyph for both teaches the user they're the same thing. Type differentiates in the detail. Today (`TodayTaskRow`/`TaskCardView`) stays marker-free by design.

- **The primary CTA is one slot, or none** (`RecommendedAction` / `recommendedAction(among:in:)`, `docs/task-model.md` axis 1). It is **lifecycle-driven, not obstacle-driven** — the old ladder never surfaced `.doing`, so a `.todo` task read "Mark done" and skipped a state. The tree: resolved → Reopen · unowned → That's mine · **owned by someone else → nil** · blocked → Unblock · `.todo` → Start · `.doing` → Mark done. **The nil arm is the design** — someone else's task isn't yours to advance, so a button there is wrong by construction (and completing it would stamp *you* as attesting their work); its proxy moves live in `TaskMoreMenu`, and the empty slot is reserved for Nudge/Comment once `HouseholdSync.isLive` flips. **The verb never voices the type** — the intent-voiced verbs are all retired (`.planning`'s "Break it down" lied; `.decision`'s "Decide" retired with the type), so `.start` carries no associated value and reads "Start" (or "Resume" on a task with a closed `.doing` visit) — **with ONE deliberate, view-layer carve-out (2026-08-25): on a `.deciding`-shaped page, `.start` reads "Decide"** (`TaskDetailView.ctaTitle`), because there the work IS the choice and "Start" undersells it. The shape is derived from the human-owned flag, never wording, so this cannot re-fuse the type axis; `RecommendedAction` itself is untouched, and `.resolve` stays "Mark done" — it runs `completeAndResurface` and never touches `needsDecision`, so a "Mark decided" label there would report a decision nothing recorded (`resolveDecision()` is the only clearer, owned by the obligation block). **Start does not dismiss the detail**: the button relabels to "Mark done" in place, which is how the lifecycle teaches itself. Only `.resolve` sets `dismissesDetail`. Claim precedes unblock. The one-tap fast path for trivial work stays in the **list** (`TaskRow` long-press + the leading glyph menu) — never a secondary button under the CTA.

- **The Advisor is a judgment layer, not a feature catalog** (`TaskAdvisorStore` · `TaskAdvisorService` · `AdvisorView`, spec in `docs/task-model.md` — the 2026-08-12 S4→Advisor pivot; memory `task-advisor-pivot-2026-08-12`). The three capability cards (Thinking Partner · Breakdown · Unstick) collapsed into ONE ambient surface answering *"what would make this task easier right now?"* — an observation · guidance · next move, with the intervention type hidden metadata. **The pivot reverses "deterministic triggers decide which card"** the way the Today plan reversed "the model never ranks": the model judges the shape of help (`AdvisorMove`: `nothing/advise/decide/createSteps/openBlocker` — `start` is deliberately NOT a move; readiness is advice, the pinned CTA owns the lifecycle), while the deterministic system stays authoritative three ways — **sensors** (`StallDetector`/`BreakdownEligibility`/`DecisionShape` become FACT lines in `TaskAdvisorFacts` the model interprets but cannot invent or contradict), the **gate** (`TaskCapabilities.advisorWorthy` — documented as a *cost heuristic, never a semantic verdict*; must not calcify), and the **off-device fallback** (template diagnosis content; `.fallback` is an execution path, not a judgment). **Rung 0 always has an answer, and that is a promise the ladder makes** (`AI/DeterministicReading.swift`, 2026-08-24). The no-model path used to render `StallDiagnosis.headline`, which exists for exactly ONE of the gate's nine worthy reasons — `.decisionFlag` is excluded by a guard inside `diagnose`, and `.blocked`/`.doing`/`.overdue` are the non-stalled residue by construction — so a device run measured `stalled: 0` against 12 worthy tasks, i.e. **every one of them drew the ADVISOR kicker over an empty box**. A labelled empty box is worse than either honest outcome: silence is a judgment and renders as *nothing*. `DeterministicReading.make(from:)` now returns a `ValidatedReading` built from facts alone (so the existing renderer is reused, not duplicated), `.advise` almost everywhere because rung 0 must never fabricate options or steps to earn a button, and nil where there is nothing factual to say. **`.timedOut` and `.failed` degrade to it too** — §07's rule is *cloud fails → on-device → facts*, and the last arm was missing: the model can report `.available` and still fail (an empty model catalog, a 429), which shipped as "That didn't finish. Try again." — an error string offering a retry that cannot succeed. `.failed` survives only where rung 0 is also empty, so the retry seam still exists for that case. It is **not counted as an `offer`** (a fallback is an execution path, and folding it into the move stats would put model-free readings in the denominator progression lift is measured against). **The floor never restates the spine (2026-08-25):** `DeterministicReading` is shape-aware (`TaskShape.of(facts)` — legal because shape ⊆ fingerprint) and returns nil for the fact the page's spine already renders — a purely blocked task's floor is silent (the waiting spine names the wait), a bare flag is the obligation block's to state (that ladder arm is deleted — the block renders whenever the flag is set, so the sentence was always the block repeated in prose), and a container's step-progress line yields to the steps spine; the same facts stay ADDITIVE on other shapes (a flagged blocked task's floor still names the blocker). `-AdvisorCoverage` prints `rung-0 floor: N/M worthy tasks speak`, where "speaks" counts spine OR diagnosis template OR floor — counting only the floor would report the suppression rule as a regression when it moved the fact to a better surface. **External waits were invisible to every rung until this landed**: `activeBlockerTasks` resolves `taskID`, so a `.externalWait` blocker ("waiting on the landlord") was dropped before it reached the facts — the task read as blocked to the gate and unblocked to everything else, *including the prompt*. `TaskAdvisorFacts.externalWaits` now carries them into the prompt, the evidence, and the fingerprint (they have no id for `blockerIDs` to hash, so without that a new wait would never re-judge). **Every task detail has an Advisor; its judgment is usually silence** — `.quiet(.gate)` (free, deterministic) and `.quiet(.model)` (the model's honest `nothing`) are both first-class judgments occupying zero visual attention. **The loop must actually close** (2026-08-13 fix): `ACTION → task state changes → Advisor re-evaluates` shipped documented and untrue — `ensure` ran only at mount and on `isActive` flips, so a reading survived the action that invalidated it. Two hooks close it: `onChange(of: task.updatedAt)` (every mutation helper bumps it, so one hook covers advisor actions, chip edits and status changes) and `onChange(of: openedBlocker)` on return (resolving a blocker changes the BLOCKER's state, invisible to the first). The **golden scenarios** (`TaskAdvisorGoldenTests`) are the product acceptance gate, run against an injected judge — `TaskAdvisorStore.init(judge:isModelAvailable:)`, because `ModelRun` AND `AppBrain.onDeviceModelAvailable()` are both hard-false under XCTest and would otherwise hide the loop behind a gate tests can't open. **What the loop closes TO is usually silence, and that is correct**: a task normally stops being advisor-worthy the moment the user acts, and "you're unblocked now" is the Advisor narrating the user's own action back at them (work still `.doing` stays worthy and does get the closing read). **The facts fingerprint is the calm invariant** (fields pinned in `TaskAdvisorFactsTests`; the raw staleness clock deliberately excluded): same task + same meaningful context → same reading — *continuously understanding ≠ continuously generating* — and `AdvisorRevealGate` structurally refuses a second reveal per fingerprint (the `Interpretation` lesson), so the reading arrives as a single thought and never churns. **Dismiss binds to the fingerprint** (the Advisor had an opinion; the human declined — counted, never resurfaced until facts change). **Model output is untrusted transport; `ValidatedReading` is the contract** (`validated(against:)` drops/degrades, never substitutes: options 2–4 with the verbatim grounded-recommendation rule kept from the Thinking Partner; steps 2–5 clamped, committing through `splitInto` + Corrections; `openBlocker` requires a real blocker; unknown moves degrade to `advise` — the forward-tolerance seam for research/draft/schedule/delegate later). **A flagged decision keeps its reason line and Mark decided unconditionally** — `resolveDecision()` is the only clearer. **Every advisor action routes through `advisorActed`** — the acted metric (recording the status it acted FROM) + `touchHuman` while a stall diagnosis is present (a card its own buttons can't dismiss is a scold). **The Advisor never competes with the task's primary action**: `accentGradient` on a full-width capsule belongs to the pinned CTA alone (the shipped flagged-decision card broke this with a second gradient "Mark decided"; it is now a bordered secondary, and the Advisor's own controls never exceed that). **The reading renders CONTAINERLESS and LABEL-LESS (2026-08-25)** — an interpretation belongs in the task's own body rhythm, not a bolted-on AI card, and the "ADVISOR" kicker is deleted: no badge tells the user which sentences came from a model, the observation renders in secondary text (the intelligence is the sentence being right, not the frame around it), and a failed generation renders NOTHING (`RetryLine` deleted; `AdvisorView.isVisible` excludes `.failed`, the floor already spoke wherever there was a fact to state, and the re-judge loop is the retry — an error string taught the user the Advisor can fail and offered a retry that often could not succeed). Only the flagged-decision block keeps card chrome + the Needs-Decision stroke, because that is a standing human obligation rather than an interpretation — and it now renders ABOVE the reading, since a standing duty outranks an interpretation of it. On a `.decide` reading the evidence surfaces INLINE as up to three "what matters" fact lines (no disclosure tap before a choice); everywhere else "Why this?" stays collapsed. One hairline separates understanding from action ("everything above = what I noticed, everything below = what you can do"), there is at most ONE button, and a `decide` with no grounded recommendation gets NO button at all — when the system doesn't know the user's preference the options themselves are the action. **"Why this?" shows EVIDENCE, never reasoning** (`TaskAdvisorFacts.userVisibleEvidence` → `ValidatedReading.evidence`, bound to the reading so it can't drift): deterministic fact lines only, the model contributes nothing, and `workIntent` is excluded because axis 2 must never become accidental UI. Loading is reserved rhythm — no spinner, no hairline, no "analyzing" copy. **The quality signal is progression LIFT, not AI activity** — v5 sharpened this from "% of advised tasks that moved", which reads like evidence and isn't: the Advisor speaks on SELECTED tasks (the stuck, decision-shaped, repeat-deferred ones), so 62% could mean the interventions work or that hard tasks move anyway, and the number cannot tell those apart. A metric that cannot fail cannot support the claim the product rests on. `AdvisorMetrics.progression(among:)` now compares the advised cohort against a CONTROL of tasks the Advisor **looked at and judged silence on** (`SilentEvent`, recorded only for model-judged `.nothing` — gate skips are trivial by construction, so using them would measure task difficulty and call it Advisor quality). A task in both cohorts counts as advised; the footer prints `lift +31pt` **signed always** (a negative lift is the most important reading this footer can show) and `lift n/a` when either cohort is empty, because "no difference measured" and "no measurement possible" are different claims. : `AdvisorMetrics` (local-only, DEBUG footer `advisor: gated 12 · zip 6 · adv 1/4 · …` + `moved 62% · re-int 1.3`) tracks offered/acted/dismissed per move plus % of advised tasks that later moved; **gate skips are counted apart from judged silence** ("are we skipping too much?" and "does the Advisor know when to shut up?" are different questions, and gate skips accumulate on every fingerprint change of every trivial task); the acceptance test is the `-AdvisorDiagnostics` judgment eval (curated task states → expected moves, run on device). **Latency is a product budget PER RUNG** (`ModelDeadline.advisorSeconds(rung:presenceTime:)`): on-device keeps `cardSeconds` (20s); a PRECOMPUTED deep read gets the generous budget (60s — nobody is waiting, so correctness beats speed and the only risk is a hung call); a PRESENCE-TIME deep read gets a tighter one (25s), because a wait the user is watching should end in a cheaper answer rather than a longer wait. A single deadline for every rung shipped as a silent bug — 20s is right for a local read and far too short for deep reasoning, so the paid rung would have timed out routinely while the code, the tests and the docs all said it worked. **A timed-out deep read salvages DOWN A RUNG** rather than surfacing `.failed`: running out of time doesn't prove there is nothing to say, only that this rung couldn't say it in the time available (guarded on `.cloud` so it cannot recurse). **V1 is otherwise deliberately call-shaped** (`ModelRun.perform(.taskAdvisor, …)`, `CapabilityProfiles.taskAdvisor` prior 0.5/`.moderate`/500; the move is constrained at the DECODER via `@Guide(.anyOf(AdvisorMove.allCases…))` — the first `.anyOf` in the codebase — while the field stays a `String` behind `lenient:` so the app keeps an escape hatch the model can no longer need) — tool calling, streaming+salvage, and per-task sessions are each deferred behind a named tripwire (context-starved readings · device timeout counts · the evolving-loop wanting continuity). Naming: `AI/BriefSession.swift` is the daily BRIEF session (renamed from `AdvisorSession` in the v2 collapse, so "Advisor" names one thing); everything per-task is `TaskAdvisor*`. **The Start tap still earns a kickoff line, and rung 0 answers before the model may (2026-08-26)**: a CONTAINER's first move is already stored — `TaskItem.nextOpenStep(among:)`, the one derivation the spine's pointer and the kickoff line both read, so they cannot disagree and the line lands instantly with no generation; a DECIDING task gets NO kickoff at all (the options are the move, and a generated "first step" under a Decide button answers a question nobody asked); everything else still asks `KickoffService`, silence as the fallback. **The primary CTA is pinned** (`safeAreaInset(edge: .bottom)`, solid surface, hidden while editing) with the kickoff line riding in the bar and re-fetching on revisit of a `.doing` task. **The umbrella can't be finished before its steps, and that fact is DERIVED — never a stored wait** (`TaskItem.openSteps`/`stepProgress` → `StepProgress`). Writing it as a `.blocks` edge on the parent was tried and REVERSED (2026-08-11): it fuses the two graphs `children(among:)` warns about. The split writes exactly one edge per step, ON the step, so deleting the step is the whole undo. **A container is not stuck, so it never renders as Blocked**: the row shows `StepProgressIndicator` ("1/3"), the detail shows a read-only Steps section, `containerRecede` keeps the umbrella out of its steps' way, and closing it early is allowed but never silent (`UndoNotice.resolution(steps:)`). **`TaskChainGrouping.prerequisites(of:within:)` is where the two graphs meet**, and the ONLY place they do: for display order, blockers and open steps answer the same question, so a breakdown renders as one chain stack with its steps in front.

- **Ownership: every task is born owned.** `OwnerProposer` (`AI/OwnerProposer.swift`) is a pure, deterministic ladder — spoken name → graph adjacency (`childOf`/`duplicateOf` targets only; **never blockers**, which point the wrong way) → category affinity → **the capturer**. It is **total**: `applyOwnershipGate` and `ownerPending` are both retired, "unowned" is exactly `ownerID == nil`, and only a human hand-back produces it. **Load never selects an owner, only adjusts one** (demotes the overloaded, breaks ties). `.defaultSelf` carries **no reason and no ✦** — defaulting to you is not an inference, and claiming it was is worse than the abstention it replaced. `ownerOrigin` (`.human`/`.inferred`) is stored because the affinity denominator counts human-established ownership ONLY — otherwise rung 4's own output floods it and the rung is unreachable. `creatorID` (authorship) backs the "Created" tab, distinct from `ownerID`.

- **Confirm is the single publish boundary, and assignment side effects bind to it** — never to the owner field being populated (`AppBrain.publishAssignments`). Pre-Confirm a capture is single-player even when the inferred owner isn't you. **Target notification behavior is *notified*** (one per assignment, re-notify only on reassignment, copy that names the source); it is unimplementable until sync, so the interim is a silent publish. **`HouseholdSync.isLive`** (compile-time `false`) gates the proposer's *inferred* non-self rungs and Today's ownership filter — `.spoken` is not gated. Without it, a task could leave your briefing for someone with no device in the graph. **The gate is now INJECTABLE at every behavioural reader, and its live side is tested** (`SyncGateTests`): `OwnerProposer` already took `syncIsLive:`, and `BriefSequenceModel.candidates(from:currentUserID:syncIsLive:now:)` (lifted out as a pure static) plus `AppBrain.handedOffAssignments(_:in:syncIsLive:)` now do too. The reason is the Phase 5 promise itself — *a surface to build, not a migration to survive* — which only holds if the substrate has actually RUN in the live configuration; before this, flipping the constant would have shipped the ownership filter's and the publish boundary's first ever execution to real users on the same day sync did. **Flipping it remains a one-way door and a deliberate act**: it turns on the inferred ownership rungs, the Brief's ownership filter and the publish boundary together, ships with the iCloud entitlement + `PersistenceStack.cloudKitContainerID`, and closes the wipe-on-mismatch schema escape hatch permanently (a deployed CloudKit schema is additive-only with no server-side reset). Never flip it speculatively.

- **Undo-completeness.** A `ChangeLogUndo` arm restores *every field its action wrote*, not just the headline one. Worked example: `claim` stamps `ownerOrigin = .human`, so the `"assigned"` entry encodes `"<uuid>|<origin>"` (`TaskItem.encodeOwnership`) and the arm restores both — otherwise undoing a reassignment leaves an AI-inferred owner marked human and pollutes the affinity denominator.

- **Stack precedence lives in `Models/TaskRanking.swift`** (the Policy layer) and is a product invariant: Needs Decision forced top → Blocked sinks → **effective attention (desc)** primary → Blocking boost → Overdue boost. The band boosts are lexicographic sort-key components, never additive scores — the comparator must stay a strict weak ordering (property-tested in `TaskRankingTests`). The cobalt→cyan `Palette.accentGradient` is for high-signal sites: the provenance tag, **primary CTA buttons**, the Needs-Decision edge stroke, the composer's processing border, and the Today briefing's hero-action edge; use `Palette.accentFlat` elsewhere — **including the active tab, which renders flat via `.tint`, NOT the gradient.** **Attention hues are split, one meaning per token** — `priorityUrgent` (red, the Urgent `SignalMarker`/toggle/pill), `statusInProgress` (amber, the In-Progress status glyph only), `overdue` (orange, past-due markers), `householdAttention` (amber, Household surfaces); never reuse `warning` for these (the old amber-means-four-things collision). The one "judgment / your-call" blue is `Palette.decisionAccent` (used by ConfidenceRow `.ask`, AssessmentChip Needs-Decision, the confirm judgment flag, the detail decision banner) — never fork `accentStart`↔`accentFlat` for it again. Every editable metadata capsule routes through **`MetadataChip`** (`.standard` = bordered 44pt tap target; `.compact` = dense borderless), never an ad-hoc capsule. The Today backdrop's drifting glow (`Palette.backdropGlow`) is on-brand accent-family atmosphere, off under Reduce Transparency.
- **Visible thinking has exactly TWO scales, and the customer never hears "AI"** (product shape v5). Scale one is the full-screen `RambleOrb` — the capture arc's signature moment, which earns its cost because that whole beat is about waiting well. Scale two is **`ThinkingMark`/`ThinkingLine`** (`Features/Components/`): one small monochrome dotted mark meaning exactly *"Ezra is thinking"*. **One glyph, one meaning** — per-activity states ("analyzing…", "searching…") narrate the model's internals, which is chain-of-thought theater dressed as feedback, and this codebase already deleted one version of that (the live parse's streaming cards). It is deliberately NOT progress-shaped (no track, arc, or percentage) and strictly monochrome, so the two-hue rule holds by construction and it can't compete with the primary CTA's gradient. **Exactly ONE placement (2026-08-25), an exception rather than a default:** the Brief's mid-day recomposition. The Advisor's presence-time placement was removed with the shape-driven detail pass — `AdvisorState.loading` lost its `deliberate:` payload and every rung renders reserved rhythm (`Color.clear`, height `Spacing.lg`): the page appears in its deterministic form, space is reserved, the reading settles in when it lands, nothing reflows. A second placement returning is the tripwire that the no-spinner rule is eroding. **Never**: on the capture canvas (zero AI presence by contract), as a standing "AI is here" badge, for rungs 0–2 (their reserved-rhythm invisibility is the shipped decision — latency must never become a product event), or as a Ramble-orb replacement. **The customer-facing vocabulary drops "AI" and every provider name entirely**: Settings' "AI Engine" card became **`DataBoundary`'s three sentences** under "What leaves this device" (`Models/DataBoundary.swift` — one idea per line, state-aware so a device that transmits nothing doesn't warn about transmission, and test-pinned to name no vendor, model, token, credit or quota). The engine readout and the cloud-budget line live in the DEBUG diagnostics card, where internal numbers belong. Intelligence is a property of Ezra — the felt experience is "this thing understands my life", never "look at this AI feature", and **a user shown a budget is a user who starts managing it** (principle 10: never make the user manage Ezra).

- **Liquid Glass is a design system, not per-view (`Design/Glass.swift`).** Route ALL app glass through `.glassChrome(in:tint:interactive:morph:)` / `.glassCapsule(...)` — never hand-roll `.glassEffect` in a view. Rules the modifier enforces: **glass is chrome, never content** (rows/cards/section headers/chain stacks are solid `Palette` surfaces — no `.blur`/material on content; that was the "muddy" anti-pattern); **glass never carries primary text** — Liquid Glass imposes a **vibrancy that desaturates foreground text** (a label on glass reads dimmer than one beside it, and NO scrim behind the text can rescue it — verified in-sim), so a **text-bearing selection chip uses a solid `elevatedSurface` surface + hairline, NOT glass** (see the Assigned↔Created pill in `TasksHomeView` — a solid chip with a `matchedGeometryEffect` morph); glass stays for **icon + press affordances** only; **neutral `.regular`** for plain chrome (a tint over the near-black list has nothing to refract and reads muddy) — an accent `tint` is passed ONLY by the signature AI tile (`HeldDepthView`); `.interactive()` on tappable glass; a **solid `secondarySurface`+border fallback under BOTH Reduce Transparency AND Increase Contrast**. The `GlassEffectContainer` lives at the **composite-region call site, never inside the modifier** — `glassEffectID` morphing needs one container spanning both endpoints. System chrome (tab bar, toolbars) is left to the OS; the Capture FAB is the one app-chrome exception (gradient CTA + interactive glass lens, no text). Blocked/inactive content recedes via `.recessed(_:)` (a contrast-aware dim, floor raised under Increase Contrast) + a `BlockedIndicator` `hourglass` marker — **never a blur** (superseded the old frost).

- **Every model call goes through one seam** (`AI/ModelDeadline.swift` · `ModelResult.swift` · `ModelRun.swift`). `ModelRun.perform(_:deadline:)` owns availability, the deadline, cancellation, error labelling, and metrics, so a service is only its prompt and its parsing. **Deadlines:** `cardSeconds` (20) for a card the user is watching, `backgroundSeconds` (10) for re-classification nobody is waiting on, `captureSeconds` (30) for the composer's live parse; unbounded calls are the bug this replaced — a cold model left a spinner the user could not escape. **Capture's deadline is not a failure threshold** — measured on device (`-CaptureDiagnostics`), a 648-char/13-item ramble finished at NEITHER 20s nor 30s (5 drafts → 11 drafts, both hitting the wall), because generation scales with how much was dumped and "dump it all" is unbounded. It is the point where we stop waiting for MORE: salvage costs completeness, never the capture, and the user watches candidates stream in and can confirm at any moment. So a deadline hit on a long ramble is the EXPECTED path, recorded as `.salvaged` (a served user) rather than `.timedOut` (a failure) — `Stats.served` is successes + salvaged. **If long captures ever need to be genuinely complete, chunk the input; do not raise the number.** `ModelResult` is the product vocabulary (`success`/`unavailable`/`timedOut`/`cancelled`/`failed(label)`) and keeps `LanguageModelSession.GenerationError` **out of SwiftUI**; `.unavailable` and `.cancelled` are deliberately NOT `isRetryable` (nothing to retry without a model; re-offering after the user left is nagging). **Cancellation keys on `isActive`, never `.onDisappear`** — the pager keeps neighbours mounted, so a swiped-past page never disappears. `TodayPlanService` delegates the race but **keeps throwing**: its tier chain falls through on `throws` and `errorLabel` maps `PlanGenerationError.timedOut` to the string the DEBUG footer reads. `FoundationModelsEngine`'s capture calls are deliberately excluded — capture has its own rolling parse cadence (debounce + max-wait + chain-on-completion) and a streaming partial contract. `ModelMetrics` (`AI/Metrics.swift`, the `PlanMetrics` pattern) records per-capability successes/timeouts/failures/latency **locally, never transmitted** — the guardrails refuse vanity metrics, and it exists so the deadline is tuned on evidence rather than argument.

- **Rung 3 is a slot, not a branch** (`AI/CloudModelProvider.swift`). The cloud provider was always the part of the AI stack most likely to change, so it became a seam before there was a second thing to put in it — every provider is the same shape, a `LanguageModelSession` over a different model, so the swap is one line: **`CloudModel.provider`**. That claim is now tested rather than asserted: the provider moved from Private Cloud Compute to **Gemini via Firebase AI Logic** (`AI/GeminiProvider.swift`, `gemini-3.7-flash`) and **no caller changed** — `TodayPlanService` / `TaskAdvisorService` / `FoundationModelsEngine` still cannot name a provider at all. **PCC is gone, not dormant**: Ezra does not use Private Cloud Compute, and `PCCProvider` / `PCCEntitlement` were deleted rather than left as a second inert conformance, because the one-slot rule means a spare provider is just a thing to get out of sync. `PlanTier.pcc` became **`.cloud`** and `PlanRouting.decide` takes `cloudAvailable:` for the same reason. **`isAvailable` must never construct the model, and must never go to the network** — the rule was written for PCC's uncatchable trap and outlives it for a duller reason with the same shape: it is asked on the routing path, so a check costing a round trip makes every routing decision wait on the network. `GeminiProvider.isAvailable` is therefore `FirebaseApp.app() != nil`, a local dictionary lookup. **ONE provider, per Challenge 5**: two cloud tiers means two privacy stories and two failure modes behind one slot, and `PlanTier.allCases.filter { $0.rung == .cloud }.count == 1` is test-pinned. The DEBUG readout names the PROVIDER (`via cloud(gemini-flash)`) because that is the only level at which "which model answered" is a legitimate question — never UI copy. The identifier is the model FAMILY (`gemini-flash`), not `modelName`, so a version bump doesn't split its own metrics history in two.

- **The Advisor's router asks for a REASONING BUDGET, not a model** (`AI/ReasoningBudget.swift`, v5). The question is *"how much cognition does this judgment deserve?"* — `ReasoningBudget` (`none`/`shallow`/`deep`) — and rung selection merely IMPLEMENTS the answer. This replaced a router that asked "is this hard enough to pay for", which is a procurement question dressed as a product one: it starts from the price list and works backwards, so the answer is always a percentage somebody chose. **Ezra decides the budget, never the model** (a model asked how hard to think about itself has an unbounded appetite), and the mapping is swappable without touching policy — when a cheaper rung starts matching the ceiling, `rung(for:)` changes and the budget assignments don't. `depthReason` carries the three hypotheses (`.decision` — framing options is the reasoning the local model lacks · `.multiStep` — blockers + open steps ≥ 2, a graph to hold rather than a fact, so ONE blocker deliberately isn't enough · `.repeatDeferred` — `deferralCount >= 3`, consecutive, so a high number is live evidence the obvious advice already failed). It is called only AFTER the gate opened and the cache missed, so it never decides *whether* anything happens. Depth is **not length** — see the guardrail below.

- **Routing is DISCOVERED, not decreed** (`AI/AdvisorBenchmark.swift`, `-AdvisorBenchmark`). The gold-standard-first method: the strongest reachable rung establishes the CEILING on the hard corpus, and cheaper rungs **earn** cases by matching it — move equality plus abstention equality, deliberately NOT text similarity (scoring prose would reward the model that writes more, which is the exact failure the depth guardrail exists to prevent). **The routing percentage is an OUTPUT, printed as one**: never "cloud should be 10%", always "these N cases measurably need depth". `depthReason`'s three reasons are therefore falsifiable hypotheses — the report names **`OVER-CLAIMED`** (claimed deep, cheap rung matched anyway → narrow the band) and **`UNDER-CLAIMED`** (routed shallow, diverged from the ceiling → widen it; rarer and worse, because over-claiming costs money while under-claiming costs the product's promise). Answers are MODAL across repeats, sharing `-AdvisorRepeats` with the judgment eval — the eval already returned 5/8, 6/8, 7/8, 6/8 on byte-identical binaries, so comparing one sample per rung would attribute coin flips to capability. It shares `AdvisorDiagnostics.fixtures` on purpose: one corpus, two questions (*does the active path agree with a human?* vs *which rung is enough?*); two corpora would drift and the neglected one would be the one nobody was watching. **The cost target is not minimum cloud spend — it is maximum reduction in required attention per dollar of reasoning.** If deep reasoning writes better prose but buys no progression, don't pay.

- **Deep judgments run OFF the open-moment** (`TaskAdvisorStore.precompute`, Challenge 9). The Advisor is the one deep-thinking surface with no cover: Ramble hides behind the orb, the Brief behind the Recap, and the Advisor's user is standing in the task detail looking at the task. An in-place 30-second thinking state would make it the first surface where the user waits while watching — and would collide with the shipped decision that the Advisor's loading state is invisible. The architecture already solved it: because a judgment is cached against the facts fingerprint, **it doesn't have to be computed while the user watches — it has to be right when they look.** Escalation signals fire generation in the background, it validates and caches, and the reveal is instant. **`BriefSequenceModel.primeAdvisorForPlannedWork` is the first signal** — the Brief's chosen actions are the day's highest-precision prediction of what the user is about to open, and priming only those (never the whole candidate set) keeps a speculative pass over sixty tasks from becoming the runaway the cap exists to catch. Speculative work is capped three ways: `.shallow` judgments are skipped entirely (no wait worth removing), a degraded-to-on-device deep read is skipped (same reason), and `CloudBudget.allowsPrecompute` gives it **half** the daily ceiling so a bet on a task being opened can never starve a certainty that one already was. **Presence-time deep still runs** (bounded at 25s, salvaging down a rung on timeout) but is no longer *marked*: `.loading` renders identically at every rung, so a presence-time deep read is an invisible bounded wait into which the reading settles — and the floor guarantees the wait can only ever end in content or true silence, never an error string.

- **Generated is not offered; SEEN is offered.** Precompute's metric-integrity half, and easy to get wrong in a way that quietly destroys the north star: `offered` is the denominator of acted/offered, dismissed/offered, and the honesty denominator for silence. Counting a precomputed judgment at generation time would fill that denominator with readings no human ever saw, and every ratio built on it would drift downward for reasons unrelated to quality. So a speculative judgment parks its move in `Entry.pendingOffer` and is counted on the first user-facing look.

- **One dumb daily cap, and deliberately not a governor** (`CloudBudget`, same file). `dailyCallCap` (**500**) is a runaway backstop sized well above a projected heavy day, not a ration — and it is **loud in DEBUG when it degrades**, because an eval that silently stops exercising the rung it is evaluating reports the cap's opinion as the model's; it reads `IntelligenceLedger.cloudCallsToday` and **degrades to Rung 2 silently**. The silence is a product decision, not a shortcut: telling a user "you have used your AI budget" converts an invisible cost control into an anxiety and an engagement hook in one move, and what they actually get is a real reading from a cheaper rung. The proposed eligibility → recency → rate governor stays UNBUILT until the counters show a real distribution problem — the capture-deadline precedent, applied to spend. If `CloudBudget.statusLine` is never seen approaching the ceiling, the cap is correctly inert and that is the answer we want.

- **Meter first, cap second, govern on evidence** (`AI/IntelligenceLedger.swift`). **The number that matters is cloud calls per user per day AFTER routing, not AI interactions per day** — 25 Advisor encounters resolving as 15 facts/cache + 8 on-device + 2 cloud is 25 intelligent experiences for two paid generations, and a metric counting "interactions" would report 25 and imply a bill that doesn't exist. The ledger counts `IntelligenceRung` (facts · memory · onDevice · cloud) × `IntelligenceWorkload` (ramble · advisor · brief · sweeps), plus **`cloudCallsToday`** (day-rollover on WRITE; reads stay pure so a footer nobody looked at can't discard yesterday's count). Local-only, never transmitted, same charter as `ModelMetrics` — which it does NOT replace: that answers *did the model work*, this answers *how often did we have to ask one*. It is written **where the routing decision lands, not where a model returns**, because the gate skip and the cache hit are the two outcomes with no call attached and the two the economics turn on (`TaskAdvisorStore.ensure` IS the Advisor's rung ladder; `CaptureRoute.rung`; `PlanTier.rung`). Sweeps record `.onDevice` and **must never reach the cloud rung** — background work nobody is waiting on has no business costing money. This exists so the budget governor is built on measurements rather than argument (the capture-deadline precedent); the daily cap is Phase 3 and reads `cloudCallsToday`.

## Two-engine AI

`AI/AIEngine.swift` defines the seam; `FoundationModelsEngine` (real on-device LLM, iOS 27) and `HeuristicEngine` (deterministic fallback) both conform and emit `[TaskIntent]` via `triage(rawText:context:onPartial:)`. `AppBrain` selects the engine at launch via `SystemLanguageModel.default.availability` and degrades to the heuristic on failure. **The simulator is NO LONGER guaranteed to be the heuristic path** — verified 2026-07-26 on Xcode 27 / iOS 27.0 sim, where the Inbox diagnostics footer reads `Apple Intelligence · on-device`, i.e. `availability == .available` and the sim runs the REAL on-device model. (It follows the host Mac's Apple Intelligence, so it varies by machine.) Two consequences: never assume a sim run exercised the heuristic — read the footer; and the sim can no longer verify off-device/absent-card behaviour, which now needs a device (or host) with Apple Intelligence off. **Unit tests are unaffected** — `onDeviceAvailable()` still hard-returns false under XCTest. Keep both engines behaviorally consistent — the shared derivation lives in `AutonomyPolicy.tier` + `IntentResolver` (including `applyRules`, the learned-correction half both engines get for free).

The ramble pipeline:
- **`TriageContext`** carries personal context per call: `personalization` (top-N learned corrections as instruction lines, built by `CorrectionProfile`), `roster` (value snapshots backing `ResolvePersonTool` — the tool attaches only when a roster exists; mind the beta tool-over-calling caveat below), and `candidates` — the **capture-graph candidate package** (`ContextRetrieval` ranks the open set against the capture: NLEmbedding + lexical + category + recency, cap 12; the `[uuid] title — facts` package is the ONLY valid ids the model may cite for duplicate/child/blocks). **Candidates RIDE THE CHAIN (audit A1)**: retrieval runs concurrently with generation, never ahead of it — the first parse of a burst prompts candidate-blind (proposals are refinements, not prerequisites), each parse's retrieval returns in its `TriageRun` and becomes the NEXT parse's prompt package, the final resolve of every parse sees prepared ∪ fresh, and a single-shot on-device capture gets ONE bounded enrichment re-parse (`suggestsEnrichment`) so duplicate detection still lands. Capture sessions are pooled (`CaptureSessionPool`, single-use, fingerprinted on instructions+roster, prewarmed with the REAL instruction prefix + prompt head — `ModelWarmup`'s anonymous session never covered it); a continuous session stays deferred. The resolver tiers the model's claims into `EdgeProposal`s **by destructiveness, not uniformly** (the auto-accept invariant): `duplicateOf` (a merge destroys data) keeps ≥0.85 accepted / 0.5–0.85 undecided / <0.5 suppressed; `childOf` (additive, reversible) is auto-accepted at ≥0.5 (`.undecided` is duplicate-only). Previously rejected pairings are dropped at the resolver via the suppression set (passed through `TriageContext.suppressions`). At commit an accepted duplicate **merges** (no new task, reversible "merged" entry that Undo resurrects), a rejected proposal writes `SuppressionRecord`s, an accepted child becomes a reversible `.parent` link. **The heuristic path lacks proposals + workIntent by design** (Apple Intelligence is assumed present; those features are simply absent in the sim, which exercises the heuristic).
- **INSTANT CAPTURE — the deterministic read renders first, the model upgrades it in place.** `AppBrain.provisionalDrafts` (no model, no Core Data, no await: `Segmentation` → `HeuristicEngine.intent` → `IntentResolver` → `proposeOwners`, deliberately with NO open tasks and NO candidates) paints cards on every text change, leading-edge coalesced at 80ms. The model parse keeps its rolling cadence and upgrades those cards via `DraftMerge` **Pass C**, which matches a model retitle against the CLAUSE the provisional card was cut from (`TaskDraft.provisionalSource`, optional so parked payloads still decode; `isProvisional` is derived from it) using stemmed containment — word overlap between the two TITLES is under the retitle floor, so Passes A/B structurally miss. `mergeProvisional` is additive-only (a provisional pass can never downgrade a model card) and `RemovedDraftSet` remembers source clauses so a deleted card can't resurrect under a rewritten title. A completed parse only drops cards it actually read (`keepingUnmatched: textMoved`). Time-to-first-card, its producer, the provisional pass's cost and the commit's are all in the DEBUG footer.
- **Streaming is internal.** On device `onPartial` receives resolved partial candidates from `streamResponse` snapshots mid-generation — and **the user never sees them**. The product rule is **model reasoning streams internally; the user receives ONE final interpretation**. Streaming is still exploited for latency, salvage at the deadline, and metrics; it is simply never rendered as user truth. (The rolling cadence this bullet used to describe — a 400ms debounce, a 1.2s max-wait, `parseEpoch`, `scheduleTriage`/`startParse` — is gone, along with those functions.) Mid-session park writes are throttled (~2s, `force` on dismiss).
- **Low confidence is a visual state** (dimmed + "?" on the confirm card), never a held queue.
- **Eval harness — the floors live in the APP target, not the test** (`AI/RambleEvalSet.swift`: fixtures + scoring body + **`RambleEval.Floors`**). `RambleEvalTests` and the `-RambleEval` device seam both read `Floors.standard`, so every arm is held to the SAME numbers by the same code. They used to be `#expect` literals inside the test, which meant only CI could fail them — and CI exercises the deterministic path, because the Foundation Models path only exists on hardware. The floors were held by the FALLBACK while the front door went unmeasured, and an unstructured spoken blob failed to segment on device with every number green. The test is now ONE assertion over `Report.failures(against:)` plus a guard pinning the field count, because an enumerated list of eight `#expect`s is a place for a field to be measured and quietly left unheld. **`-RambleEval` runs EVERY arm available on the host** (heuristic always; the DEGRADED-OFFLINE on-device arm when there is one; cloud when a provider is configured), each printing a per-field PASS/FAIL table plus a `settled p90` latency row — the baseline a cloud arm must beat has to be measured on the same hardware in the same run, never inherited from CI. **Every model arm proves a model ANSWERED**: the seam takes a `ModelMetrics` delta across the run and reports an arm that served **fewer than 90% of its calls** as DEGRADED rather than as a pass — a RATIO, not a zero test, because an arm serving 2 of 52 printed "ALL FLOORS HELD" with numbers identical to the fallback's; the banner also names the recorded error, so it can say WHY rather than only how often — see the availability-vs-catalog trap below, which this seam hit on its very first run. Extend the fixture set when capture behavior changes, and re-calibrate floors only downward from observed numbers.

Synthetic UI taps via AppleScript are blocked by macOS Accessibility permissions here — use these launch args to reach a screen state instead of scripting clicks.

**Running on a physical device (iOS 27) with a launch arg:**
- Launch arguments are **only passed when Xcode launches the app via Run (⌘R)** — never on Build (⌘B), and never when you tap the app icon on the phone. Set the arg in the **shared** scheme: *Edit Scheme ▸ Run ▸ Arguments ▸ Arguments Passed On Launch* (tick the checkbox), pick the iPhone as the destination, then ⌘R.
- The Run action is **Debug** by default, so any `#if DEBUG` affordance is compiled in on device runs — e.g. the **plan-tier readout** (`plan: on-device N · pcc N · rules N · last Xms`) in the `SettingsView` diagnostics card that shows which Today-plan tier actually ran. It is stripped from Release/Archive.
- `-SeedTodayFixtures` **force-reseeds on every launch** (`TodayFixtures.reset` + `seed` in `RootTabView.seedTodayFixturesIfRequested`) — wipes prior tasks/CapacityLog + the Today day-cache first, so a used store still shows the set without deleting the app. The other seed args keep the empty-store guard.
- **The cloud rung is inert until Firebase is configured:** `GeminiProvider.isAvailable` is `FirebaseApp.app() != nil`, so the rung activates when `AppDelegate` calls `FirebaseApp.configure()` at launch and stays dormant everywhere it doesn't — notably the **unit-test host, which deliberately skips configuration**, so a suite can never issue live billable Gemini calls while pretending to test routing. `GoogleService-Info.plist` needs no pbxproj entry: it sits inside the synchronized root group and is bundled automatically. **App Check is not wired, and has a hard deadline: 2026-11-02.** Until that date Firebase AI Logic accepts unattested requests and this build deliberately sends them — fewest moving parts between here and a working call. On 2026-11-02 enforcement turns on automatically, **cannot be un-enforced**, and any request without a valid App Check token is blocked. Wiring it is ~2 lines plus the `FirebaseAppCheck` SPM product: install the factory BEFORE `FirebaseApp.configure()` (afterwards silently leaves the default in place), `AppCheckDebugProviderFactory` behind `#if DEBUG` with its printed token registered once per simulator in the console, App Attest for anything shipping.
- **Historical (PCC, removed):** the ancestor of the rule above was `PrivateCloudComputeLanguageModel`, which *traps* (uncatchable) the instant it's constructed without the managed `com.apple.developer.private-cloud-compute` entitlement — gated behind a compile-time `PCCEntitlement.isGranted`. PCC is no longer used and both types are deleted; the "never construct the model to answer `isAvailable`" rule it taught is now a documented requirement of `CloudModelProvider`, binding on every provider.

## Platform & design references (iOS 27 beta)

Target the iOS 27 SDK. Canonical, authoritative sources — consult these (not memory) for anything version-specific:
- Human Interface Guidelines — https://developer.apple.com/design/human-interface-guidelines
- Foundation Models — https://developer.apple.com/documentation/foundationmodels
- iOS & iPadOS 27 release notes — https://developer.apple.com/documentation/ios-ipados-release-notes/ios-ipados-27-release-notes
- Xcode 27 release notes — https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes

Verified specifics that affect how code is written here:

- **Liquid Glass.** The API is the same as iOS 26 (confirmed against the SDK's `SwiftUICore.swiftinterface`): `.glassEffect(_:in:)` with `Glass.regular` / `.clear` / `.identity`, `.tint(_:)`, `.interactive(_:)`, plus `GlassEffectContainer`, `.glassEffectID`, `.glassEffectUnion`, `.glassEffectTransition`. **iOS 27's improved diffusion of complex content is automatic** — there is no new parameter; you get it by putting real content behind a genuine `.glassEffect()`, not by faking a blur. Glass is for **chrome, not content**, and must adapt to Reduce Transparency / Increase Contrast — always provide a flat, non-glass fallback (see `HeldDepthView` in `Features/Components/HeldDepthView.swift`, and the Today capacity capsules' solid fallback).
- **A capability being AVAILABLE does not mean a profile modifier is USABLE — verified the hard way, 2026-08-17.** `SystemLanguageModel.default.availability == .available` says an on-device model exists; it says nothing about what that model can be asked to do. Two shipped features were dead on device and green in CI at the same time, because **the simulator cannot exercise the capability check**:
  1. **Reasoning levels are not an on-device capability.** The Task Advisor asked for `.moderate` and the Today session for `.deep`; the device reports `capabilities.contains(.reasoning) == false`, so every generation failed `unsupportedCapability` — the Advisor had never once produced a reading on real hardware, and Today silently fell through to its deterministic tail every day. `.light`/`.moderate`/`.deep` belong to reasoning-capable paths, not to the on-device model. **A bigger model is not the fix** (the constraint is 100% on-device): stop asking. **The cloud rung is reasoning-capable and the dial is ON.** `GeminiLanguageModel` advertises `.reasoning` / `.toolCalling` / `.vision` / `.guidedGeneration`, so `CapabilityProfiles.taskAdvisor` and `.briefPlan` ask for `reasoningLevel: .deep` and `CapabilityProfiles.supported(_:capabilities:)` degrades that away on the on-device arm. This is gold-standard-first expressed as a config: the strongest rung states what the feature actually wants, cheaper rungs run the same profile minus what they cannot serve. **Ramble's depth is decided per-ramble, not per-feature** (`CaptureRoute.captureDepth`) — the one place a `CapabilityProfiles` constant could not express the policy. Which MODEL answers a capture was already settled and is unchanged: `CaptureRoute.route` sends every ambiguous ramble to `.cloud`, and the cloud is Gemini. What varies is whether *this* dump is hard enough to think harder about. Short captures — the corpus median is 71 characters — run reasoning-free, because the front door is the most latency-sensitive surface in the product. Long or many-intent dumps (≥400 chars **or** ≥6 items; the ramble that actually failed segmentation on device was 648 chars / 13 items) get `.moderate`. Floors are grounded in `RambleEvalSet`'s real distribution, which clusters under ~150 chars and then jumps 365 → 507, so they separate two populations rather than cutting through one. `.moderate` not `.deep`: capture is Level 2–3 semantic parsing, not the multi-step judgment `.deep` exists for. **Open question for `-CaptureDiagnostics`, not for argument:** these long rambles are the same ones already hitting the capture deadline, so depth may buy cleaner segmentation or may just reach salvage sooner with fewer drafts banked. If the numbers say the latter, raise the floors or return nil — never raise the deadline. `CapabilityProfiles.session` now degrades an unsupported level rather than sending it — capability-AWARE, not a blanket ban, because a reasoning-capable cloud tier should still get what it was configured with.
  2. **`.toolCallingMode(.allowed)` is unusable on this build even though `toolCalling` reports TRUE.** It failed every Today generation with `Unrecognized system-instruction prefix ID: com.apple.fm_api.tool_calls_override … invalidClientData` — the framework could not apply the override the modifier installs, so the request was rejected as malformed. Tool calling itself works; the MODE MODIFIER does not. It is the documented default anyway, so stating it bought nothing.
  4. **A per-call `GenerationOptions` silently overrides the session profile — 2026-08-22, fourth instance of the same class.** `CapabilityProfiles.briefPlan` asked for `.deep` reasoning, and Gemini 3.x counts THINKING tokens against `maxOutputTokens`, so the Brief's cloud tier returned `finishReason: MAX_TOKENS` with 573 thought tokens and 12 answer tokens — no briefing, silent fall-through to the deterministic tail, on every cloud attempt. `supported(_:capabilities:)` now adds `thinkingHeadroom(for:)` on top of the answer budget when the rung will actually reason (and still strips the level when it cannot), so `maximumResponseTokens` means the ANSWER everywhere. **Fixing the profile did nothing at first**, because `TodayPlanSession.generate` passed `GenerationOptions(maximumResponseTokens: 600)` per call and a per-call option wins. Two caps, one capability-aware and one not, is not redundancy — it makes the capability-aware one dead code. The tell was measurement: the same ~586-token ceiling across two runs with different prompt sizes, when a config-driven limit would have moved.

  3. **`availability == .available` does not mean a model will ANSWER — 2026-08-18, third instance of the same class.** On a simulator whose model catalog is empty (`ModelManagerError … "There are no underlying assets (neither atomic instance nor asset roots) … for asset set com.apple.modelcatalog"`), `SystemLanguageModel.default.availability` still reports `.available` and `AppBrain.status` still reads `Apple Intelligence · on-device` — while **every** generation throws. Capture degrades to the heuristic (correct, by design: capture must never fail) and the Today plan falls through to its deterministic tail. The failure mode is that everything downstream looks fine: the first version of the two-arm `-RambleEval` seam scored 49 model calls, 0 served, and printed *"on-device: ALL FLOORS HELD"* — the exact "a green suite proved the fallback, not the front door" failure, reproduced inside the instrument built to catch it. **Availability is a claim that a model EXISTS; only a served call is evidence one ANSWERED.** Any harness that attributes results to a model arm must prove it with a `ModelMetrics` delta and report a zero-served arm as DEGRADED. This also qualifies CLAUDE.md's own "the sim is no longer guaranteed to be the heuristic path": the footer can say on-device and the calls can still all fail — read the served count, not the label.
  The rule: **`capabilities.contains(...)` gates a capability, but only a device run gates a profile MODIFIER.** Apple's own docs say models differ in what they support and `contains()` exists to be checked first — that check is necessary and, as (2) shows, not sufficient. Two different faults in one day, each invisible to the simulator and to a green suite; one of them was pinned *as correct* by `CapabilityProfilesTests`.
  Consequence for design: **Advisor quality cannot be bought with a reasoning dial.** It has to come from context, constrained decisions, decomposition and app-side logic — which is what `guidedGeneration` and `toolCalling` (both true on device) actually offer. `-AdvisorDiagnostics` prints the live capability set for this reason.
- **Foundation Models** is iOS 26+ and unavailable on non-Apple-Intelligence devices — always gate on `SystemLanguageModel.default.availability` and keep the `HeuristicEngine` fallback working. (It is **not** reliably absent in the simulator any more — see the two-engine section above.) Use guided generation (`@Generable` + `@Guide`) rather than parsing JSON; consider use-case models (`SystemLanguageModel(useCase:)`) and streaming (`streamResponse`) where they fit. **Device-verify any `@Generable` schema change** — the sim cannot exercise it.
- **Guided-generation tool-calling bug (Xcode 27 beta, tracked in the iOS 27 release notes):** the on-device model can call tools excessively when guided generation is in play. `FoundationModelsEngine` doesn't use `Tool` yet, but if that's added (the personal-context tools are on the deferred list), tighten `instructions`/prompt wording first before assuming a code bug if triage output gets erratic or slow.
- **`#Preview` now runs on the main actor** (Xcode 27) — previews of main-actor-isolated views/view models no longer need workarounds for concurrency warnings. `PreviewProvider` is deprecated in favor of the `#Preview` macro; don't add new `PreviewProvider` conformances.
- **Instruments has a Foundation Models instrument** (traces instructions/prompts/responses/token usage) — reach for it over ad hoc logging when profiling `FoundationModelsEngine` latency or debugging odd triage output.

Recorded here (the product spec's §11 carries the phase order). **The cloud rung ships as Gemini 3.7 Flash via Firebase AI Logic** (`AI/GeminiProvider.swift`; unconfigured Firebase reads as unavailability → falls through to the deterministic tail).
