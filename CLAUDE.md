# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Project Ezra** ("Managing Chaos, Effortlessly") — an AI-managed personal task system for iOS. SwiftUI + Core Data, single app target. The current product direction lives in a single consolidated spec, `docs/PRD.md` — vision & boundaries, the three data dimensions (Status/Priority/Flags), Capture/Intent/Correction/ChangeLog + the action table, and the **Today sequence** (Recap → Docket → Capacity → Plan) with deterministic ranking + capacity personalization. Read it before changing product behavior. `prev-docs/` holds the superseded generation (lean PRD, strategy, design system, guardrails, household architecture, mock-data flows); the **design system** (`prev-docs/design-system-managing-chaos.md`), **product guardrails** (`prev-docs/product-guardrails.md`), and **household architecture** (`prev-docs/household-architecture.md`) remain in force except where the new docs override them (navigation, lanes, the Review tab, and the attention/retro layer are gone — replaced by the Today sequence).

## Toolchain — non-negotiable

- **Build with Xcode 27 (iOS 27 SDK).** The deployment target is iOS 27.0. Xcode 26 has no iOS 27 SDK and the build fails. Confirm with `xcodebuild -version` (expect 27.x). If it shows 26.x, the active toolchain is wrong: `sudo xcode-select -s /Applications/Xcode-beta.app/Contents/Developer`.
- Swift language mode is 5.0 (not Swift 6 strict concurrency), but `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` — types are main-actor isolated by default.
- **Host needs macOS Tahoe 26.4+** to run Xcode 27 at all; if Address Sanitizer fails to launch on the iOS 27 simulator, that's a known Xcode 27 beta issue on host toolchains older than **26.5** — update Xcode, not the code. Apple silicon only: Xcode 27 no longer builds Intel/`x86_64` by default (`ld64` is gone; `-ld_classic` is no longer an option).

## Build & run

```bash
# Build (iOS 27 simulator)
xcodebuild -project Project-Ezra.xcodeproj -scheme Project-Ezra \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro,OS=27.0' -configuration Debug build
```

```bash
# Run the unit tests (Swift Testing) on the iOS 27 simulator.
# -parallel-testing-enabled NO is REQUIRED: fixtures build Core Data managed objects in a
# single shared in-memory context (see PersistenceStack.scratch / TestStore), which has
# thread affinity — Swift Testing's default parallelism crashes it. Run tests serially.
xcodebuild test -project Project-Ezra.xcodeproj -scheme Project-Ezra \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro,OS=27.0' \
  -parallel-testing-enabled NO
```

Prefer the `/run-sim` skill for the full install + launch + screenshot loop. A clean build is sufficient to consider a change done (launching the sim is optional, not required). Tests live in `Project-EzraTests/` (Swift Testing, `@testable import Project_Ezra`) and cover the pure AI/ranking logic — `AutonomyPolicy`, `HeuristicEngine`, `IntentResolver`, `CorrectionProfile`, `TaskRanking`, `BrainSweeps`, the Today pipeline (`TodayQueriesTests`, `CapacityBaselineTests`, `DeterministicPlanTests`, `PlanSanitizeTests`, `PlanRoutingTests`, `TodayPlanStoreTests`), plus the `RambleEvalTests` accuracy harness; add cases there when you touch those.

**Known test-runner flake (environmental, not a code bug):** the whole suite passes (all cases green) but the run occasionally ends `TEST FAILED` via `Restarting after unexpected exit` — a *bare* crash of the test host with **zero** Core Data exceptions in the log, always alongside the iOS 27 simruntime warning `objc[…] Class UIAccessibilityLoaderWebShared is implemented in both WebCore.axbundle and WebKit.axbundle … may cause … mysterious crashes`. That's the Xcode 27 beta simulator's own accessibility-bundle conflict, not our code (diagnosed: the correct single-context test architecture throws no CoreData exceptions; only broken multi-coordinator variants did). If a run flips to failed with no `✘` cases and no `NSInvalidArgumentException`, just re-run (or use a freshly-booted sim).

## Project layout & Xcode gotcha

- The target uses a **PBXFileSystemSynchronizedRootGroup** (`Project-Ezra/`): any `.swift` file added under that folder is compiled automatically. **Do not hand-edit `project.pbxproj` to add/remove files** — just create or delete them. (Editing the pbxproj is only warranted for build settings.)
- Source is feature-organized: `Design/` (design system), `Models/` (Core Data `NSManagedObject` models incl. `CapacityLog` + `CapacityBaseline` + `PersistenceStack` + pure ranking), `AI/` (engine layer + the Today plan generators/service), `Features/<Screen>/` (`Today/`, `Tasks/`, `Capture/`, `Household/`, `Root/`), `Features/Components/`. Persistence is Core Data via `NSPersistentContainer` (`NSPersistentCloudKitContainer`-ready — flip `PersistenceStack.cloudKitContainerID` + add the iCloud entitlement to enable sync); models are constructed with the `in:` context convenience inits.
- `Item.swift` is a retired template stub — the real model is `Models/TaskItem.swift`.

## Architecture invariants

- **Three data dimensions, never fused** (`docs/PRD.md`). A task carries (1) **Status** — `TaskStatus` (`.inbox → .active → .done | .killed`), user-owned lifecycle; the AI proposes `.inbox` at creation (always — see always-confirm below) and never moves the status again except the reversible stale auto-archive. (2) **Attention** — the retired user-facing Priority is now a three-layer architecture (**Facts → Reasoning → Policy**): one USER **Signal** (`isUrgent`, user-owned, AI proposes it at capture) feeds a computed **system score** (`AttentionEngine` → persisted `AttentionMetadata`, 0–100 + explaining contributors), which `TaskRanking` (Policy) uses only to break ties WITHIN the hard bands. (`isPinned` was a second Signal and is **retired** — a manual float-to-top override competed with the score it was meant to complement.) On the RECORD surfaces the Signal renders as a **leading `SignalMarker`** (Urgent, or nothing — zero footprint) on My Tasks `TaskRow` + the detail urgent chip; **Today (`TodayTaskRow`/`TaskCardView`) stays signal-free by design** — the advisor's curated voice. The score is NEVER a badge. **Persist-slow/compute-fast:** the score reads only slow inputs (urgent, AI importance, effort shape, graph centrality) and NEVER a fast fact (overdue/blocked/blocking/needsDecision) — those stay live comparator components, so "the AI never decides the band" holds by construction. (3) **Flags** — Needs Decision (stored `needsDecision`, surfaced in the full-screen detail's decision section, not on rows), Blocked/Blocking/Overdue/Stale (all derived on read, never stored). Don't re-fuse these: adding a blocker must not move the status; high confidence must not auto-resolve a judgment call. A separate **`WorkIntent`** (action/decision/planning/waiting/reference) is a computed/cached/refreshable classification (heuristic path leaves it nil) — its `.decision` value (or the `needsDecision` flag) unlocks the detail's **Thinking Partner** (`TaskCapabilities`), and it NEVER reads/writes `needsDecision`. **`TaskStage`** (`Models/TaskStage.swift`, backlog/todo/inProgress/inReview) is a **user-owned sub-state of `.active`, never AI-written** — the AI proposes `.inbox` (reads as Backlog); `confirm()` stamps `.defaultOnConfirm` (Todo) once. The six Linear display states (`TaskDisplayStatus`) are **derived** from `(status, stage)` via the one mapping table — the row glyph, the detail picker, and My Tasks sectioning all read `displayStatus` and write back through the single `applyDisplayStatus` seam. Stage drives *sectioning*, never `TaskRanking.stackOrder` (the comparator invariant is untouched). A separate **`creatorID`** (authorship) backs the My Tasks "Created" tab, distinct from `ownerID` (who it's *for*).
- **Stack precedence lives in `Models/TaskRanking.swift`** (the Policy layer) and is a product invariant: Needs Decision forced top → Blocked sinks → **effective attention (desc)** primary → Blocking boost → Overdue boost. The band boosts are lexicographic sort-key components, never additive scores — the comparator must stay a strict weak ordering (property-tested in `TaskRankingTests`). The attention component is `attention.score + currentRelevance` — the ONE deliberate additive layer, *within* that component only: `currentRelevance` (live, never persisted, clamped ±25) is the decay fix — staleness (days since `lastHumanTouchAt`, NEVER `updatedAt`) and `deferralCount` pull down; a recent unblock, a freshly-gained dependent, or a related due date approaching pull up. It is **precomputed once per snapshot into `RankKey.effectiveAttention`** — never evaluated inside the comparator (graph terms + `now`-windows would be O(n²) and break the strict weak ordering). The hard bands stay fact-fed and the AI still never decides the band. (`RankBand`, renamed from the old `AttentionLayer`, is the internal sectioning band — never rendered.)
- **Always-confirm capture** (`docs/PRD.md`). Nothing is gated on confidence at capture: engines emit `TaskIntent`s (raw `dateExpression`/`personReference`, never resolved by the model), the deterministic `IntentResolver` produces drafts that ALL land `.inbox` — and **backfills any metadata the engine left empty** (priority, effort; never a due date without a time signal), so every field reaches the confirm card populated and editable. The Confirm-Creation glance ("Add N tasks" in `ComposerView`) is the single human-in-the-loop moment — it calls `confirm()` per task. Every field edited at confirm is diffed against `TaskDraft.aiOriginal` and written as a `Correction` row (write-only learning signal). One `Capture` row per capture event, raw text verbatim forever. **The auto-accept invariant:** capture-time inference is auto-accepted — no AI confidence value gates whether an inferred field is applied; the Confirm-Creation card is the only human-in-the-loop boundary, where inferred values become visible and editable. The single exception is inference that destroys or merges existing user data (the duplicate merge), which stays confidence-tiered (0.85/0.5). Every new inferred field inherits this rule.
- **The judgment-category rule is a permanent carve-out.** Values-laden decisions are always `.ask` tier (`AutonomyPolicy.tier`), carry `needsDecision` from birth, and — crucially — `confirm()` does NOT clear a judgment call's flag (confirming the task exists ≠ making the call); only `resolveDecision()` does. `BrainSweeps` never touches a judgment call or open decision. `autonomy` is DERIVED from tier, not stored.
- **Every status change funnels through `TaskItem.status`'s setter**, which calls `transition(to:now:)` to record the `StateVisit` timeline and bump `updatedAt`. Never write `statusRaw` directly; never expose `$task.status` as a two-way binding; callers with an authoritative timestamp call `transition(to:now:)` (see `complete(now:)`/`kill(now:)`). **Every mutation helper bumps `updatedAt`** — Stale detection and the auto-archive depend on that honesty (the detail sheet's `.onDisappear` bumps it for direct `@Bindable` edits).
- **Blocked is always derived, never written.** A task reads as blocked iff `activeBlockers(among:)` is non-empty; there is no `block()`. An Active task that gains a blocker STAYS Active. Blocking is the derived reverse edge (`isBlocking(among:)`) — never stored, never labeled. On an existing task the AI only ever authors `.task` blockers (origin `.inferred`); the one sanctioned AI-authored `.external` is a captured wait whose phrase matched no task at commit. **Storage:** blockers + parent edges live in ONE versioned `relationshipsData` blob as `[Relationship]` (`Models/Relationship.swift`, v2: kinds `.blocks`/`.parent`/`.related`, each with an `Origin` — `.human` or `.inferred(confidence:)`, so a human edge structurally can't carry a confidence). `blockers` and `parentTaskID` are READ-ONLY derived views; **every write funnels through the `TaskMutations` helpers** (the mutation choke point — never assign `relationships` from a view/engine). **Live edges are the only edges** — a rejected merge/link suggestion is a `RelationshipSuppression` in the pair-owned store (`Models/RelationshipSuppression.swift`), never a dismissed edge: capture-form keyed on (target, normalized DRAFT TITLE) so a "no" sticks across captures (a fresh draft id can't match a pair key), plus a pair form (duplicate: symmetric canonical key; parent: directional) for both-tasks-exist consumers; rows expire (`SuppressionStore.maxAge`) and orphaned rows prune lazily at load. Invariants are DEBUG-asserted on encode (`Relationship.validate`) and property-tested (`RelationshipTests`).
- **The Today briefing is AI-authored — the advisor selects, orders, and sizes it** (`docs/PRD.md` §8). This deliberately REVERSES the prior "model never ranks" rule *for the Today plan* (a documented product pivot). The model is now an expert advisor that returns an `AdvisorBriefing` (headline · chosen actions · tradeoffs · risks) — it picks which candidate tasks matter, their order, and how many. `TaskRanking` is demoted to two supporting jobs: it provides the capped candidate set handed to the advisor, and it is the deterministic **fallback** (sim / offline / on-device-off → top-N candidates by rank, fact-line lines, NO advisor voice). `GeneratedPlan.validated(against:)` is now only an **anti-hallucination guard** — drops ids that aren't real candidates, dedupes, backfills an empty line from facts, caps at `maxActions` (7); it does NOT reorder. The **capacity input is gone**: `CapacityLog` still logs daily throughput (vestigial `.steady`), and `CapacityBaseline(for: .steady)` is advisory *context only* (the advisor sizes). Tier routing is a simple ordered chain (`PlanRouting`: on-device → PCC → deterministic tail), so `AppBrain.todayPlan` never fails. Generation mutates zero task fields. **On-device resilience** (so a cold/slow model doesn't silently drop to the voiceless "Your day" fallback): the on-device deadline is **30s** (`onDeviceTimeoutSeconds`) with an output-token cap; `TodaySequenceModel.start` **prewarms** the model while the Recap cover plays; a deadline hit **salvages the last viable streamed partial** (headline + ≥1 action, via `PartialBox`) instead of discarding it; and a voiceless deterministic plan cached at the first open **self-heals** — a later same-day open re-generates in the background when on-device is available (`generate(preservePlan:)`, keeping the cached briefing on screen until the voiced one lands), rather than freezing plain for the day. Failures are no longer swallowed: `AppBrain.todayPlan`'s catch records a **typed** `PlanMetrics.lastError` + `lastTier` + `lastAvailability` (e.g. `timedOut` / `guardrailViolation` / `modelNotReady`), surfaced in the DEBUG diagnostics footer (`… · via <tier> · err <reason> · ai <availability>`) — the first thing to read when the advisor voice is missing on device. Cold-start Recap counts completions since **start-of-today** (`recapCutoff ?? startOfDay`).
- **`ChangeLogEntry` backs both Undo and the trail.** `initiatedBy` separates AI from human actions: the Activity Trail and the "AI handled N" count filter to `.ai` only. Every AI action is reversible and logged; `Metrics.acceptanceRate` counts AI entries only and **excludes `action == "planned"`** (a daily plan isn't a per-task action the user accepts — its undo clears the day cache).
- **Navigation is four tabs + a floating capture button.** `RootTabView`: Today (0, `TodayHomeView` wrapping `TodayView` + `TodaySequenceModel`), **Inbox** (1, `InboxView` — the household activity feed, absorbing the old AI Activity Trail: ALL change-log entries, avatar + action badge + unread dots + action-aware Undo), **My Tasks** (2, `TasksHomeView` — Linear-style "My issues": large title, `[search][…]` pill, a **Liquid-Glass** Assigned/Created pill (with a hairline separator before the filter icon; glass-merge via `glassEffectID`, flat-capsule fallback under Reduce Transparency), priority-bars + six-state status-glyph rows with **no dividers** (row height carries the rhythm), the chain stack kept; **Created** is flat + chain-stacked + newest-first via `MyTasksSlices.createdEntries`), and Household (3), plus a **circular Capture button** overlaid at the bottom-trailing corner **inline with the floating tab-bar capsule** (Linear's agent-button placement; its bottom inset is a tuned constant, not a pixel-lock — the bar geometry isn't public). Tapping a task opens the **full-screen Linear-style detail**, which is a **pager**: `TaskDetailPager` owns the chrome (nav bar, back chevron, "…" `TaskMoreMenu`, an "n of N" counter, the 20pt leading edge-swipe dismiss) and hosts a horizontally-paged `ScrollView`+`LazyHStack` of `TaskDetailView` pages (category kicker, big title, wrapping property chips, description, per-task Activity feed from the change log), so a **left/right swipe moves to the neighbouring task without leaving full screen**. What "neighbouring" means belongs to the PRESENTING surface, never to the detail: each call site hands `taskDetailSheet(_:peers:)` the ordered list it is currently rendering (`TaskDetailPeers.flatten` over My Tasks' sections/lane entries with chain stacks unrolled root-first; search results; the Today briefing's action order; Household's coordination/timeline feed), and the pager **snapshots it in `init`** so a live re-rank can't shuffle pages mid-swipe. Two invariants inside a page: it never dismisses itself on resolution — it calls `onResolved()`, and the pager advances to the next peer (dropping the resolved page) or dismisses when there is none; and anything with a cost or held state (model prewarm, keyboard focus) gates on `isActive`, because neighbours stay mounted (`.onDisappear` is NOT a reliable commit point, and `updatedAt` bumps must be scoped to `task.hasChanges`, never `context.hasChanges`). Screens jump to the Inbox via `\.openInbox`. **Today is a two-scene cinematic briefing:** Scene 1 = the **Recap** ("what you got done"), which doubles as the cover while the advisor reasons in the background; Scene 2 = the **advisor briefing** (headline · action plan · tradeoffs · risks), whose action steps are tappable and open the task. The **transition is data-driven, never timed** — it fires when generation completes AND the Recap entrance has played (via `withAnimation` completion, not `asyncAfter`). No Docket screen, no capacity input, no auto-advance timer, no progress bars. The briefing **plays once a day** — the reset is ONE swappable predicate, `TodayPlanStore.shouldReplay(now:)`; nothing else may test the date. Screens open the composer via `\.openCapture`, never their own sheet.
- **Clean-break schema policy.** No migrations: `Project_EzraApp` keeps a `schemaGeneration` integer (UserDefaults, **currently 9** — 6→7 was the **attention substrate** (retires user-facing Priority for signals + a persisted score + the `relationshipsData` graph blob + `workIntentRaw`); 7→8 **retires the Pinned signal**; 8→9 is the **relevance + suppression substrate**: TaskItem gains `deferralCount`/`carriedOverCount`/`lastSurfacedAt`/`lastUnblockedAt`/`lastHumanTouchAt`, `relationshipsData` moves to v2 (`Origin`, no tombstones), and the `SuppressionRecord` + `EmbeddingCache` entities land) and destroys the store on mismatch — bump it whenever a change alters the *meaning* of stored data (renamed raw values, repurposed fields), not just its shape. The container-open self-heal remains as the backstop.
- **Design system is the single source of truth.** Use `Palette`, `Font` extensions, `Spacing`, and `Radius` from `Design/`. Never hardcode colors, font sizes, or spacing in views (incl. `Font.heroNumeral`/`heroDisplay` and the `Motion` Today springs — never a raw 64/72 or inline spring). The cobalt→cyan `Palette.accentGradient` is for high-signal sites: AI tag, active tab, **primary CTA buttons**, Needs Decision edge-glow, and the Today briefing's hero-action edge; use `Palette.accentFlat` elsewhere. The Today backdrop's drifting glow (`Palette.backdropGlow`) is on-brand accent-family atmosphere, off under Reduce Transparency.
- **Liquid Glass is a design system, not per-view (`Design/Glass.swift`).** Route ALL app glass through `.glassChrome(in:tint:interactive:morph:)` / `.glassCapsule(...)` — never hand-roll `.glassEffect` in a view. Rules the modifier enforces: **glass is chrome, never content** (rows/cards/section headers/chain stacks are solid `Palette` surfaces — no `.blur`/material on content; that was the "muddy" anti-pattern); **neutral `.regular`** for plain chrome (a tint over the near-black list has nothing to refract and reads muddy) — an accent `tint` is passed ONLY by the signature AI tile (`HeldDepthView`); `.interactive()` on tappable glass; a **solid `secondarySurface`+border fallback under BOTH Reduce Transparency AND Increase Contrast**. The `GlassEffectContainer` lives at the **composite-region call site, never inside the modifier** — `glassEffectID` morphing needs one container spanning both endpoints (see the Assigned↔Created pill in `TasksHomeView`). System chrome (tab bar, toolbars) is left to the OS; the Capture FAB is the one app-chrome exception (gradient CTA + interactive glass lens). Blocked/inactive content recedes via `.recessed(_:)` (a contrast-aware dim, floor raised under Increase Contrast) + a `BlockedIndicator` `hourglass` marker — **never a blur** (superseded the old frost).

## Two-engine AI

`AI/AIEngine.swift` defines the seam; `FoundationModelsEngine` (real on-device LLM, iOS 27) and `HeuristicEngine` (deterministic fallback) both conform and emit `[TaskIntent]` via `triage(rawText:context:onPartial:)`. `AppBrain` selects the engine at launch via `SystemLanguageModel.default.availability` and degrades to the heuristic on failure. Foundation Models is unavailable in the simulator, so **the sim always exercises the heuristic path.** Keep both engines behaviorally consistent — the shared derivation lives in `AutonomyPolicy.tier` + `IntentResolver` (including `applyRules`, the learned-correction half both engines get for free).

The ramble pipeline (see `docs/PRD.md`):
- **`TriageContext`** carries personal context per call: `personalization` (top-N learned corrections as instruction lines, built by `CorrectionProfile`), `roster` (value snapshots backing `ResolvePersonTool` — the tool attaches only when a roster exists; mind the beta tool-over-calling caveat below), and `candidates` — the **capture-graph candidate package** (`ContextRetrieval` ranks the open set against the capture: NLEmbedding + lexical + category + recency, cap 12; the `[uuid] title — facts` package is the ONLY valid ids the model may cite for duplicate/child/blocks). The resolver tiers the model's claims into `EdgeProposal`s **by destructiveness, not uniformly** (the auto-accept invariant): `duplicateOf` (a merge destroys data) keeps ≥0.85 accepted / 0.5–0.85 undecided / <0.5 suppressed; `childOf` (additive, reversible) is auto-accepted at ≥0.5 (`.undecided` is duplicate-only). Previously rejected pairings are dropped at the resolver via the suppression set (passed through `TriageContext.suppressions`). At commit an accepted duplicate **merges** (no new task, reversible "merged" entry that Undo resurrects), a rejected proposal writes `SuppressionRecord`s, an accepted child becomes a reversible `.parent` link. **The heuristic path lacks proposals + workIntent by design** (Apple Intelligence is assumed present; those features are simply absent in the sim, which exercises the heuristic).
- **Streaming**: on device, `onPartial` receives resolved partial candidates from `streamResponse` snapshots mid-generation; the heuristic ignores it (instant). The composer's debounce (~400ms, generation-counted cancellation) remains the trigger.
- **Low confidence is a visual state** (dimmed + "?" on the confirm card), never a held queue.
- **Eval harness**: `RambleEvalTests` scores the pipeline per-field over ~40 labeled rambles with regression floors — extend the fixture set when capture behavior changes, and re-calibrate floors only downward from observed numbers.

Guarded test seams in `RootTabView` (no effect in normal runs):
- `-SeedSampleData` — runs a sample brain-dump through the active engine, auto-confirms the confident filings, and skips onboarding, so screens have real data.

**Running on a physical device (iOS 27) with a launch arg:**
- Launch arguments are **only passed when Xcode launches the app via Run (⌘R)** — never on Build (⌘B), and never when you tap the app icon on the phone. Flip it only once the entitlement is provisioned in signing.

## Platform & design references (iOS 27 beta)

Target the iOS 27 SDK. Canonical, authoritative sources — consult these (not memory) for anything version-specific:
- Human Interface Guidelines — https://developer.apple.com/design/human-interface-guidelines
- Foundation Models — https://developer.apple.com/documentation/foundationmodels
- iOS & iPadOS 27 release notes — https://developer.apple.com/documentation/ios-ipados-release-notes/ios-ipados-27-release-notes
- Xcode 27 release notes — https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes

Verified specifics that affect how code is written here:

- **Liquid Glass.** The API is the same as iOS 26 (confirmed against the SDK's `SwiftUICore.swiftinterface`): `.glassEffect(_:in:)` with `Glass.regular` / `.clear` / `.identity`, `.tint(_:)`, `.interactive(_:)`, plus `GlassEffectContainer`, `.glassEffectID`, `.glassEffectUnion`, `.glassEffectTransition`. **iOS 27's improved diffusion of complex content is automatic** — there is no new parameter; you get it by putting real content behind a genuine `.glassEffect()`, not by faking a blur. Glass is for **chrome, not content**, and must adapt to Reduce Transparency / Increase Contrast — always provide a flat, non-glass fallback (see `HeldDepthView` in `Features/Components/HeldDepthView.swift`, and the Today capacity capsules' solid fallback).
- **Foundation Models** is iOS 26+ and **unavailable in the simulator** (and on non-Apple-Intelligence devices) — always gate on `SystemLanguageModel.default.availability` and keep the `HeuristicEngine` fallback working. Use guided generation (`@Generable` + `@Guide`) rather than parsing JSON; consider use-case models (`SystemLanguageModel(useCase:)`) and streaming (`streamResponse`) where they fit. **Device-verify any `@Generable` schema change** — the sim cannot exercise it.
- **Guided-generation tool-calling bug (Xcode 27 beta, tracked in the iOS 27 release notes):** the on-device model can call tools excessively when guided generation is in play. `FoundationModelsEngine` doesn't use `Tool` yet, but if that's added (the personal-context tools are on the deferred list), tighten `instructions`/prompt wording first before assuming a code bug if triage output gets erratic or slow.
- **`#Preview` now runs on the main actor** (Xcode 27) — previews of main-actor-isolated views/view models no longer need workarounds for concurrency warnings. `PreviewProvider` is deprecated in favor of the `#Preview` macro; don't add new `PreviewProvider` conformances.
- **Instruments has a Foundation Models instrument** (traces instructions/prompts/responses/token usage) — reach for it over ad hoc logging when profiling `FoundationModelsEngine` latency or debugging odd triage output.
