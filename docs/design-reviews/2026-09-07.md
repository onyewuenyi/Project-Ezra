## Cross-cutting

1. **Two fully-built views are reachable from nowhere.** `Features/Components/TaskCardView.swift` (302 lines) and `Features/Components/HeldDepthView.swift` (101 lines) are never instantiated anywhere in the target (`grep -r "TaskCardView(\|HeldDepthView(" Project-Ezra` returns zero call sites). Both describe UI for surfaces the codebase's own history removed: `TaskCardView`'s comments reference "Today", "Inbox", and a "Tasks board" — all retired in the v2 tab collapse (2026-08-18) and the Brief cut (2026-09-02); `HeldDepthView`'s header says it renders "below the plan once the AI has handled something" — the plan is the Brief, which no longer exists. Last touched 2026-08-08 and 2026-08-24 respectively, both before the Brief cut. `CLAUDE.md` names a specific list of files still owed removal after that cut (`Features/Brief/`, `AI/BriefSession.swift`, etc.) — these two are not on it, so they're an undocumented remnant rather than a tracked follow-up. Severity: drift.

2. **Design-token discipline is unusually strong** and worth stating plainly rather than padding this report with nitpicks: a repo-wide grep for raw hex literals, `.white`/`.black` opacity, and hardcoded `.system(size: 9/10/11)` chip fonts turns up nothing outside `Theme.swift` and the two documented, deliberate exceptions in `RambleOrb.swift` (the two-hue mesh gradient, which is explained inline). Every card, chip, and button routes through `Palette`/`Spacing`/`Radius`/`MetadataChip`/`.glassChrome`. This is the opposite of the common "inline color literals everywhere" failure mode.

3. **One destructive action skips the app's own undo contract.** `HouseholdRosterView.remove(_:)` (`Project-Ezra/Features/Household/HouseholdRosterView.swift:262-265`) soft-deletes a household member with no confirmation dialog and no undo notice — it's a `Menu` item with `role: .destructive`, which only colors the label red; SwiftUI does not gate a `Menu` button behind a confirmation. Every other destructive action in the app — cancel task, discard a capture, clear all tasks — gets either a `confirmationDialog` or an `UndoNotice` pill (often both), and `UndoNoticeView.swift`'s own header states the product's rule in so many words: "the user can Undo anything." Removing a person is one menu tap with no recovery path in the UI. Severity: drift (it functions — soft-delete keeps attribution — but it's the one place the trust contract the rest of the app enforces rigorously just isn't there).

4. **Inconsistent handling of a dropped save.** Every other save-failure site in the app (`TaskDetailView`, `ComposerView`, `OnboardingView`) shows an alert with "Try Again." `TaskRow.applyDirect`/`toggleUrgent` (`Project-Ezra/Features/Tasks/TaskRow.swift:283-304`) instead sets `saveFailed.toggle()`, whose only consumer is `.sensoryFeedback(.error, trigger: saveFailed)` — a haptic buzz with no visual explanation and no retry. A user who taps a status change from the list, on a dropped write, gets a vibration that could as easily read as the normal completion tap and no way to know the change didn't persist. Severity: drift.

## Per flow

### Tasks (`TasksHomeView` / `TaskRow` / `TaskLaneList` / `TaskChainStackView`)

Reconstruction: a large "My Tasks" title, a fixed-height header row (ownership tabs when a household exists, always a filter capsule), a quiet "unfinished capture" row when one is parked, then a scrollable, chain-aware list of dense rows (`[signal mark | status glyph | title | due label | avatar]`, 52pt min height, no dividers). Tap opens the detail; leading swipe performs the row's own recommended action; trailing swipe cancels; long-press opens a full status menu.

- **Silent save failure on the row** — see cross-cutting #4. File: `TaskRow.swift:283-304`.
- **The row's tap-to-open carries no press feedback.** Every button in the app wears `.pressable`/`.pressableProminent` (a scale or dim on press, per `PressableStyle` in `Motion.swift`), but `TaskRow`'s whole-row tap uses a bare `.onTapGesture` (`TaskRow.swift:155`) with no visual acknowledgment before the full-screen cover presents — only the long-press precursor (`isPressingForMenu`) gets a highlight. A quick tap on the app's single most common target has no touch-down feedback at all. Severity: polish.
- **Reconstructed correctly, no complaint on hierarchy/consistency**: the header's "two independent dimensions, one row" rule (ownership tabs vs. filter) is enforced structurally and the empty states differentiate "nothing here" from "no matches," each with the right CTA. This flow is in good shape.

### Task Detail (`TaskDetailPager` / `TaskDetailView` / `DetailActivityTimeline`)

Reconstruction: a horizontally-paged, full-screen stack. Each page: title + category kicker, a shape-driven "spine" (waiting/container/deciding/plain), a wrapping property-chip row, description, and a collapsed "Details" disclosure (provenance + activity). A pinned bottom bar carries the one primary CTA plus an Advisor line that opens a chat sheet.

- **This is the most heavily-engineered surface in the app** and it shows: shape-driven layout, a single derived `TaskShape` gating which spine renders, one CTA slot that's either present or genuinely absent (never disabled), states for waiting/container/deciding/plain all implemented with read/write coverage. No blocking or drift findings survived a close read.
- **Polish-level only**: the `Details` disclosure bundles two different kinds of content (AI provenance and the human edit history) behind one toggle with one hint ("N changes"), which slightly undersells that the same row change-count includes both AI actions and manual edits. Not worth a structural change, but worth naming if the disclosure ever needs to scale further.

### Capture / Ramble (`ComposerView` / `RambleOrb` / `ConfirmCreationCard` / `RevealEntrance`)

Reconstruction: a four-phase arc (listening → capture/canvas → understanding → confirm), each phase a single `NavigationStack` body swap, with a `matchedGeometryEffect`-driven orb that becomes the field and then the card composition. The confirm page shows the transcript (editable) above a staggered list of `TaskDraft` cards.

- **`ConfirmCreationCard`'s `.hero` presentation doesn't do what its own comment says it does.** The doc block above `Presentation` (`ConfirmCreationCard.swift:142-146`) explains `.hero` exists because a single-task capture "has vertical room to show every field at once instead of hiding most of them behind a horizontal scroller." But `@State private var expanded = false` (line 155) and every gate that reads it (`hasEssentialChips || expanded`, `if expanded { detailChips }`) are identical for `.listRow` and `.hero` — `.hero` only changes the title's font size. A single-task capture — the fast path this mode exists for — still hides category and effort behind a "Details" tap exactly like a five-card batch does. Severity: drift.
- **The onboarding result screen (the very first AI-drafted-task review a new user sees) doesn't carry the same-day fix the composer's identical flow got.** `ConfirmCreationList.remove` (`ConfirmCreationCard.swift:116-122`) offers an undo pill for a removed card — this is called out in `CLAUDE.md` as one of the "2026-09-04 nine small honesties." `OnboardingView.resultRow`'s remove button (`OnboardingView.swift:416-429`) is the structurally identical action — same gesture, same "reviewing AI-drafted tasks and dropping the wrong one" moment — but just does `drafts.removeAll { ... }` with no way back. A mis-tap on the product's first impression is unrecoverable in a way the main capture flow explicitly fixed two weeks prior. Severity: drift.
- **The orb's engineering discipline is genuinely excellent** (frame-interval budgets, Reduce Motion coverage, the listening→thinking swap handled as a single switch branch specifically to avoid a re-mount) — inferred from source, not observed; the file's own commentary shows this was tuned against actual device video, which is the right method for this kind of motion work.

### Advisor & Chat (`AdvisorView` / `TaskAdvisorChatView` / `HouseholdChatView` / `ChatComponents`)

Reconstruction: one shared vocabulary (bubble for the user, containerless for Ezra, `ThinkingLine` for a pending reply, cited-task rows carrying the list's own swipes) powers both the per-task chat and the household "Ask" sheet. The Advisor's reading renders as the chat's opener rather than a separate card.

- No findings survived — this is a well-consolidated system (one `AdvisorView`, one `ChatComponents` file, explicit `showsObligation`/`showsReading` flags rather than two divergent copies) and the "silence renders nothing, a failure renders nothing" rule is enforced structurally via `AdvisorView.isVisible`, not by convention.

### Activity (`ActivityView` / `ActivityDetailView`)

Reconstruction: a day-grouped feed, each row an actor avatar + action glyph + summary + inline Undo, tap opens a developer-facing provenance screen (route/rung/cost/drafts).

- No findings. The row-level Undo-beside-the-unread-dot layout is explicitly reasoned about in the file's own comments (why it's not a swipe-only affordance), and the provenance screen is honestly gated: "not recorded" prints and stops rather than fabricating a plausible-looking run for pre-instrumentation captures.

### Household (`HouseholdRosterView`)

Reconstruction: a photo + optional family name header, then a card of rows (you, each member, "Add someone"), each row a photo picker, name field, and relationship menu.

- **Destructive removal has no confirmation or undo** — see cross-cutting #3. File: `HouseholdRosterView.swift:262-265`.
- **Two raw `44×44` frames bypass the design token.** `HouseholdRosterView.swift:214` (the "…" menu) and `:230` (the "Add someone" glyph) hardcode `.frame(width: 44, height: 44)` where `CLAUDE.md`'s own rule is explicit: "never a raw `28`/`44` glyph frame — use `LayoutMetrics.recordGlyphColumn`/`hitTarget`." Every comparable control elsewhere in the app (Settings' buttons, the composer's controls) routes through `LayoutMetrics.hitTarget` or `.minimumHitTarget()`. Severity: polish.

### Settings (`SettingsView`)

Reconstruction: profile card, a three-sentence "what leaves this device" card, data export/clear, and a DEBUG-only diagnostics card.

- No findings. This screen is a good model for the rest of the app's destructive-action pattern (one shared `confirmationDialog` driven by an enum scope, receipts read from a durable log rather than view state) — worth naming as the contrast to the Household roster's gap above.

### Onboarding (`OnboardingView`)

Reconstruction: name → paste-your-mess text editor → a settling animation → an editable, category-grouped result list with a CTA that adapts its own label/color as the last row is removed.

- **No-undo removal** — see the Capture section above; same file family, same day's fix missing here.
- **Forces dark mode regardless of system setting** (`.preferredColorScheme(.dark)`, `OnboardingView.swift:68`). The rest of the app is built on a fully adaptive `Color.adaptive(light:dark:)` system; a light-mode user's first screen is dark, then the app snaps to their actual theme the moment onboarding completes. This may be a deliberate stylistic choice for "the one screen that earns dramatic, extended motion," but it's worth confirming that's intentional rather than inherited from an earlier dark-only pass — inferred from source, not observed. Severity: polish.

## Systems lens

Duplication is close to a non-issue here: one avatar pipeline (`AvatarView`, with every other "avatar" type a thin typed initializer over it), one glass recipe (`Glass.swift`), one chip primitive (`MetadataChip`), one swipe-action modifier (`TaskSwipeActions`) reused identically by the record list, the chain stack, and both chats' cited rows. That's the right shape for a system this size, and it's clearly the product of deliberate consolidation passes rather than an accident — the file headers document several "this used to be two copies and they drifted" corrections.

Where "simplicity is earned" breaks down is narrow but real: `TaskRow`'s missing save-failure UI (cross-cutting #4) is a genuinely unfinished branch in an otherwise state-complete app — loading, empty, no-match, and error states are implemented almost everywhere else, which makes this one silent path stand out rather than blend in. The household-removal gap (cross-cutting #3) is the same shape of problem at the "making things true" layer: the essential quality of this app, stated repeatedly in its own doctrine, is that every consequential action is either reversible or confirmed — and this is the one destructive action that's neither, sitting one menu tap away in a screen most users will visit exactly once to add a family member and forget about. Layered complexity is handled well overall (`TaskDetailView`'s shape-driven spine is a strong example of "common case by default, depth behind a second layer"), and the confirm-card and onboarding-result screens are close cousins that should be sharing more than they currently do — the `.hero` presentation gap and the missing onboarding undo are really one root cause (two structurally identical review-and-remove UIs built at different times) surfacing in two places.

## Top fixes

1. **`HouseholdRosterView.remove(_:)` has no confirmation or undo** — `HouseholdRosterView.swift:262-265`. Severity: drift. Add a `confirmationDialog` (matching the pattern already in `SettingsView`) or an `UndoNotice` pill (matching `TaskLaneList.cancelTask`).
2. **`ConfirmCreationCard`'s `.hero` presentation doesn't change disclosure behavior**, contradicting its own doc comment — `ConfirmCreationCard.swift:142-155`. Either implement the stated intent (default `expanded = true` for `.hero`) or correct the comment.
3. **Onboarding's result-row removal has no undo**, unlike the composer's identical flow — `OnboardingView.swift:416-429` vs. `ConfirmCreationCard.swift:116-122`. Port the same `UndoNotice` pattern.
4. **`TaskRow`'s save failure is haptic-only**, with no visible error or retry — `TaskRow.swift:283-304`. Match the alert pattern used in `TaskDetailView`/`ComposerView`.
5. **Two fully-built views are unreachable dead code** (`TaskCardView.swift`, `HeldDepthView.swift`) left over from the Brief/Tasks-board cut. Either delete them or add them to `CLAUDE.md`'s tracked removal list.
