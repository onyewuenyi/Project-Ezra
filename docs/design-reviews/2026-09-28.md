## Cross-cutting

- **`.readableWidth()`, the app's own iPad-column rule, is adopted on 3 of ~10 full-screen surfaces.** Grep confirms the modifier appears only in `TaskDetailView.swift:245,1467` and `TasksHomeView.swift:176`. `TaskAdvisorChatView`, `HouseholdChatView`, `ActivityView`, `ActivityDetailView`, `HouseholdRosterView`, `InviteViews`' link sheet, and `SettingsView` all render full-bleed on the widths this rule exists for. This is the same regression class the design system already named and fixed once (2026-09-18, on the list/detail pair) — it just never reached the newer surfaces built after that fix.
- **Two components are dead code, and both hallucinate a reachable path through a navigation surface that no longer exists.** `TaskCardView.swift` (297 lines) duplicates `TaskRow`'s layout with its own bespoke swipe gesture and accessibility text — a second implementation of the same row, not a variant. `HeldDepthView.swift`'s doc comment claims it's reached "from the Today resting state" via "the Brief's held-depth tile" — but CLAUDE.md itself states the Brief was cut 2026-09-02 and navigation is "ONE surface… no tab bar." Two independent files pointing at the same dead nav concept is a pattern, not a coincidence — worth a pass for anything else still describing the Brief.
- **A small tap-target under 44pt recurs at three unrelated sites, each next to a correctly-sized sibling in the same file**: `HouseholdRosterView`'s "Invite" button (text-only, no frame) beside its own row's `.frame(width: 44, height: 44)` "…" menu; `SettingsView`'s "Privacy policy"/"Get help" links (no frame) beside every other control in the same file, which does get `.frame(minHeight: LayoutMetrics.hitTarget)`; `OnboardingView`'s result-row remove button, fixed at 32×32pt with no `.minimumHitTarget()`, on a row whose sibling card controls elsewhere in the app get the treatment by default. The token (`LayoutMetrics.hitTarget`) and the wrapper (`.minimumHitTarget()`) exist and are used correctly the majority of the time — this reads as an unenforced convention, not a missing one. (One reported instance of this pattern — the confirm-card's seven metadata chips — was checked and is **not** a defect: they route through `MetadataChip(density: .compact)`, which already wraps `.frame(minHeight: LayoutMetrics.hitTarget)` for both densities. Noted here so the correction is visible.)
- **Raw `.font(.system(size:))` glyph literals bypass the `Font.glyph*` token family** at `SignalMarker.swift:68,73`, `ActivityRow.swift:112,157`, and four sites in `AvatarView.swift` — all in the shared `Features/Components/` layer, so each instance ships everywhere its row appears. `StatusGlyphView`, sitting right beside `SignalMarker` in the same row column, does this correctly via a tier-lookup — the pattern to copy is a few lines away in every case.
- **Nav-title / concept-count scan is clean**: "My Tasks"/"Our Tasks", "Manage household", "Activity", "Details", "Settings", "Ask", `task.title`, "Search" — no model-type name (`WorkIntent`, `TaskShape`, `RankKey`…) leaks into user-facing copy anywhere.
- **What's genuinely solid, repo-wide**: no `.navigationBarBackButtonHidden` anywhere (zero hits) — edge-swipe-back is never killed. `.ignoresSafeArea` has exactly two real call sites (onboarding background, the undo toast), both scoped and defensible. `PhotosPicker` is out-of-process at all three call sites (no `photoLibrary:` argument anywhere). `Palette.success` is never used as a steady-state badge color, matching its "transient completion motion only" contract. `MetadataChip` and `BlockerPicker` are exactly what the "primitive, not patch" rule asks for — one shell each, used everywhere they apply, no forked copies. The reveal-finality contract (`Interpretation.propose`/`.reopen`) is enforced at every call site traced in the capture flow — no path lets a late model result silently overwrite a revealed card set.

## Per flow

### Capture / Ramble

**Reconstruction.** The composer opens straight into listening: a full-bleed orb (85% of the screen's short side), a status word, and a silence countdown — no live transcript by design. `.understanding` swaps the status word for a "making sense of it" line. `.confirm` is one scrollable page: an editable raw-transcript field, a staggered stack of `ConfirmCreationCard`s (one per draft, each an editable title + a row of AI-inferred metadata chips + a collapsed Details disclosure), an optional "Group as one outcome" row, and a pinned gradient "Create N tasks" button.

**States implemented.** Loading (`.understanding`, photo/dictation busy states), empty (nothing-actionable canvas, "keep as one task" fallback), error (save-failed retry, photo/OCR-failed alerts, mic-denied → Settings deep link) — all confirmed with copy. Offline has no explicit surfaced state in this slice; the cloud route degrades silently at the routing layer, one level below these files.

**Findings.**

1. **The Create button can contradict the row directly above it once a duplicate merge is accepted inside a grouped set.** `Features/Capture/ComposerView.swift:1604` shows `groupRow` ("Grouped as "X"") whenever `interpretation.drafts.count >= 2` — the *raw* draft count. `Features/Capture/ComposerView.swift:1986-2010` computes the CTA from `created = drafts.count − mergedCount`, and only speaks the group framing `if let group, created >= 2`. Group 3 drafts, then accept 2 as duplicate merges: `groupRow` still reads "Grouped as "X"", the button reads "Create 1 task · merge 2" with no mention of the group at all. Verified by tracing both conditions against the same input. **Severity: drift** — nothing breaks or loses data, but it's a direct contradiction of the file's own stated principle, quoted in its own comment two lines above the bug: "The CTA says what pressing it DOES."
2. **The "Re-read" chip stays enabled and does nothing after the transcript is emptied.** `rereadButton` (`ComposerView.swift:1920-1935`) shows whenever `transcriptEdited` is true (`ComposerView.swift:1915-1918`, `text != parsedText`) and calls `reread()` → `interpretation.reopen(); submit()` (`ComposerView.swift:1941-1946`). `submit()` returns silently on an empty trimmed string (`guard !captured.isEmpty else { return }`, `ComposerView.swift:1603-1604`). Select-all-delete the transcript and the visibly-enabled "Re-read" chip produces no error, no haptic, no state change. **Severity: drift.**
3. **`urgentChip` is the one toggle in this card that skips the app's press-feedback system.** `ConfirmCreationCard.swift:773` uses `.buttonStyle(.plain)` where every sibling control in the same file (`remove`, `Details` disclosure) uses `.pressable*`. **Severity: polish.**

**Correction to a reported finding**: the confirm card's seven metadata chips (duplicate/child/category/due/owner/urgent/effort) were reported as missing `.minimumHitTarget()`. Verified false — all seven route through a local `pill()` helper (`ConfirmCreationCard.swift:821-823`) that is `MetadataChip(density: .compact)`, which already applies `.frame(minHeight: LayoutMetrics.hitTarget)` (`MetadataChip.swift:56`). The file's own comment at `ConfirmCreationCard.swift` even documents this explicitly. No action needed.

### Tasks Home / Detail / Deck

**Reconstruction.** `TasksHomeView` is a `NavigationStack` with one header row (ownership pills + a width-measured filter menu), then `ParkedCapturesRow`/`GroupProposalRow`, then sectioned-by-status or flat lists of `TaskRow`. `TaskRow` is `[SignalMarker | StatusGlyphView | title+subtitle | blocked/step-progress | due label | owner avatar]`, tap opens detail, leading swipe performs the one recommended action, trailing swipe cancels, long-press opens a menu. `TaskDetailPager` wraps a horizontal pager of `TaskDetailView` pages (chrome constant, only the shape-driven spine slot varies); a pinned bar carries one CTA and one Advisor line, both absent rather than duplicated when there's nothing to say.

**States implemented.** Empty (three copy variants: solo, household, filtered/search), error (save-failure alert + haptic, no inline banner), no loading state (Core Data fetches are synchronous), offline delegated out of this slice to `SyncHealth`.

**Findings.**

1. **`TaskCardView.swift` is 297 lines of dead code duplicating `TaskRow`.** Confirmed by grep: zero instantiations of `TaskCardView(` anywhere in the app target or the test target. It re-implements its own completion swipe, its own due-date formatting, its own accessibility-text builder — a second, divergent copy of a card the app stopped using. **Severity: drift.** (Also surfaced independently in the systems pass; see Cross-cutting.)
2. **`SignalMarker` — the row's one load-bearing leading-marker slot — uses raw `.font(.system(size:))` instead of the `Font.glyph*` token its neighbor `StatusGlyphView` uses correctly.** `Features/Components/SignalMarker.swift:68,73`. Mitigated by a `@ScaledMetric` multiplier, so it isn't fully frozen, but two adjacent glyphs in the same column now scale on two different curves. **Severity: polish.**
3. **The "…" menu's proxy-completion action for someone else's task ("Mark done for X") has no distinct confirmation and resolves immediately, one menu-tap deep — softer friction than the row's own long-press menu, which correctly hides "Mark Done" entirely for a task that isn't yours.** `Features/Detail/TaskDetailPager.swift:330-353`. The code's own comment names the tension ("should be a considered choice, not the biggest button on screen") and answers it by demoting to a menu — a legitimate, documented tradeoff, not an oversight. **Severity: polish**, flagged because it's the one place the "not yours to advance" invariant is soft rather than absent, worth a product owner's explicit sign-off rather than a silent pass.

### Advisor Chat / Household Ask Chat / Activity

**Reconstruction.** Both chats (`TaskAdvisorChatView`, `HouseholdChatView`) share one implementation via `ChatComponents.swift` (opener line, user/Ezra bubbles, cited-task rows with the list's two swipes, composer bar, starter chips) — genuine reuse, not parallel bespoke code. `ActivityView` is a day-grouped list of change-log rows (avatar, glyph badge, summary, byline, unread dot, inline + swipe Undo); tap pushes `ActivityDetailView`, a label/value provenance dump with an explicit "Not recorded." fallback when there's nothing to show.

**States implemented.** Loading (`ThinkingLine`, no spinner), empty (starter chips, a distinct "nothing to ask yet" copy variant), failed (`.failed(retryable)` retry line, or a dead-end redirect to floor questions when there's no model on the phone at all), a `.stopped` state distinct from failure. `AdvisorView`'s failed-generation state renders nothing at all (`AdvisorView.swift:136,190-193`) — confirmed, matching the documented "a failed generation renders nothing" rule exactly.

**Findings.**

1. **All four full-screen surfaces in this flow skip `.readableWidth()`.** `TaskAdvisorChatView.swift:210`, `HouseholdChatView.swift:175`, `ActivityView.swift:88`, `ActivityDetailView.swift:55` — confirmed by grep, the modifier appears nowhere in this flow. **Severity: drift.** (Part of the cross-cutting pattern above; called out per-flow because this flow accounts for 4 of the 7 missing surfaces.)
2. **`ActivityRow`'s badge glyphs are fixed-size, not Dynamic-Type-scaled**, at `ActivityRow.swift:112` (the actor sparkle) and `:157` (the action badge, `size: 8`). Because `ActivityRow` is the shared component for both the Activity feed and the task-detail timeline, the bug ships in both places at once. **Severity: polish.**
3. **`HeldDepthView.swift` is dead code whose doc comment describes a second Activity entry point that doesn't exist.** Zero instantiations anywhere; its header comment claims reachability from "the Today resting state," a surface CLAUDE.md itself says was cut. **Severity: drift.** (Cross-cutting — see above.)

**What's solid**: the "keyboard stays down while there's a reading to read" rule is correctly implemented on both chats (via two independently-shaped conditionals rather than one shared predicate — works today, worth a shared helper if the two ever need to change together). The flagged-decision "I've decided" control correctly stays off the chat surface (`showsObligation: false` passed explicitly). The Advisor is correctly containerless and glass-free in chat, matching its "never wears the gradient, never a container" rule.

### Household Roster/Invite, Settings, Onboarding

**Reconstruction.** `HouseholdRosterView` is a bordered card: editable family photo/name, then per-member rows (photo, name, relationship, invite status caption, Invite button, "…" menu). `InviteViews` holds `InviteLinkSheet` (prepare → ShareLink/copy → retry-on-error) and `IdentityLinkSheet` ("which one is you?" — pick a roster candidate or name yourself). `SettingsView` is a card stack: profile, digest toggle, a "what leaves this device" privacy card, data export, two destructive clears behind one shared confirmation dialog, and a `#if DEBUG`-only diagnostics card. `OnboardingView` runs welcome → paste/OCR intro → a settling animation → an editable result list.

**States implemented.** Household: normal roster, per-member invite status (none/pending/joined), add-person via native alert. Settings: reset-receipt present/absent, clear pending → confirmed → cleared/failed, export present/absent. Onboarding: found-nothing, took-too-long, screenshot-read-failed, settling-escape, save-failed, empty vs populated result.

**Findings.**

1. **`IdentityLinkSheet` locks the user in with no way out.** `.interactiveDismissDisabled()` at `Features/Household/InviteViews.swift:199`, and the view body (`:109-198`) has no Cancel, no "not now," no back — only "pick a roster name" or type one and tap Join. Confirmed directly: there is no control anywhere in this file that resolves `pending` without providing a name. **Severity: blocking** — this is a supported configuration (opening an invite link, or landing on this sheet without being ready to claim an identity) with no exit.
2. **Onboarding's remove (✕) button on result rows is 32×32pt with no `.minimumHitTarget()`**, on the one screen the code's own comment calls "one ✕ from gone" — an irreversible delete, no confirmation, smaller than every sibling control in the app. `Features/Onboarding/OnboardingView.swift:658-670` (frame at `:666`). **Severity: drift** (it still works — a mis-tap is more likely, not impossible — but the combination of under-target, irreversible, and zero-friction on a new user's first screen makes this the highest-priority drift finding in this audit).
3. **Onboarding forces `.preferredColorScheme(.dark)` for the whole flow** (`OnboardingView.swift:88`), overriding the system light/dark preference on the one screen guaranteed to be a new user's first impression. The design system names onboarding's documented carve-out as *motion* only (`onboardSettle`/`onboardReveal`) — forced appearance isn't part of that, and reads as a second, undocumented liberty riding on the first. **Severity: drift** — flagged as a product decision, not a pure bug: if this is intentional (a "moment" the product wants to own visually), it should say so beside the motion carve-out; if not, it should follow the system.

**Passed** (checked, not just restated): the Diagnostics card is `#if DEBUG`-gated at both the call site and internally — the named 2026-09-18 regression has not recurred. Both destructive clears route through one shared `.confirmationDialog`, never fire on a bare tap, and the forbidden `context.delete` loop / `refreshAllObjects()` calls are absent — the documented rebuild-not-refresh fix holds. The onboarding paste screen's privacy line is parameterized on live `CloudModel.isAvailable` reachability, not a static string. All three `PhotosPicker` sites in this flow are out-of-process.

**Two smaller findings, not in the top three per sub-flow but worth a line**: Settings' export `ShareLink` silently disappears with no message when `DataExport.writeTemporaryFile` fails (`try?` swallows the error, `SettingsView.swift:553-566`) — every other failure path on the same screen speaks a sentence; this one doesn't. Settings' "Reset everything" — the *heavier* of the two clear actions — has a plain, non-destructive-role trigger button while the lighter "Clear all tasks" correctly uses `role: .destructive` (`SettingsView.swift:598-617`); the confirmation dialog itself is correct for both, but the row that opens it undersells the bigger action.

## Systems lens

The component layer is mostly doing its job: `MetadataChip` absorbed three drifting ad-hoc chip implementations into one shell with two intentional densities, `BlockerPicker` is one picker shared by the inbox decision bar and the detail sheet, `AvatarView` is a genuine single pipeline that `OwnerAvatarBadge` thinly wraps rather than re-implements, and `ChatComponents.swift` keeps the two chat surfaces in lockstep rather than letting them drift into "the same" behavior implemented twice. Where the system breaks down is not inside the shared layer — it's at its edges, in code that predates or sits beside it: `TaskCardView` is what a card looked like before `TaskRow` won, left in place instead of deleted; `HeldDepthView` is an entry point built for a navigation model (the Brief) that was cut out from under it. Both are symptoms of the same failure mode — a surface gets replaced, and the losing implementation isn't removed, only stopped being called. Grep is cheap; a periodic "what has zero call sites" pass would have caught both before they had `docs/design-reviews` written about them.

The 44pt tap-target rule shows the opposite pattern: not a system that's missing, but one that's real and unenforced. `LayoutMetrics.hitTarget` and `.minimumHitTarget()` exist, are well-named, and are used correctly at the majority of call sites this audit sampled — which makes the exceptions (an Invite button, two footer links, a delete-with-no-undo control) look like plain oversights rather than a missing concept. This is exactly the kind of property a lint rule or a `ButtonStyle`-level default could close permanently, the same way `PressableStyle` already closed "does this button confirm the touch was heard" for the whole app.

Concept count is genuinely tight: the user-facing noun surface is small (Tasks, Activity, Household, Ask, Settings, and per-task Owner/Due/Effort/Category as editable facts) and none of it leaks an internal model name. The Advisor stays true to "prominence implies supervision" — it never gets a container, never gets the gradient, renders nothing on failure rather than escalating its own visibility to cover for a bad answer. That restraint is the single most consistently-applied idea in the codebase, and it shows in the audit's own findings list: nothing in this pass is an AI surface trying to look more certain than it is. The failures here are conventional iOS craft gaps (hit targets, Dynamic Type glyph tokens, an iPad width rule not yet universal) sitting inside an unusually disciplined AI-product shell, not the AI product shell itself misbehaving.
