# Design Review — 2026-09-21

## Scope

First full audit of this repo — `docs/design-reviews/` did not exist before this
run, so there is no "still open" carry-forward. Read in full: all 38 SwiftUI view
files (`grep -rlE 'struct \w+: View|class \w+: UIViewController'`), the design
token files (`Design/Theme.swift`, `Design/Typography.swift`, `Design/Glass.swift`,
`Design/LayoutMetrics.swift`, `Design/Motion.swift`), `Models/TaskShape.swift`,
`Project_EzraApp.swift`, and the two product-governance docs
(`prev-docs/product-guardrails.md`, `prev-docs/design-system-managing-chaos.md`)
for the rules the code is checked against. Repo is 281 Swift files, 51 commits,
all dated within the last ~3 weeks (2026-08-29 to 2026-09-21) — a fast-moving,
single-developer R&D build, and it reads like one: the design system is unusually
disciplined for this stage (see Systems lens).

Flows traced from the root (`Project_EzraApp.swift` → `ContentView` →
`RootTabView`): Tasks (My Issues), Capture/Ramble, Task Detail (pager), Advisor +
Household Ask chat, Activity feed, Household roster/invite, Settings, Onboarding.
`ContentView.swift` is a one-line pass-through to `RootTabView()` — reachable, not
dead, but pure indirection with no behavior of its own.

Skipped: the AI/ engine internals, Core Data model files, and eval harnesses — out
of scope for a UI/UX critique. `ActivityRow.swift` was read only where it's
actually used (`ActivityView.swift`), not from the Tasks flow, which imports it in
comments only.

## Cross-cutting

**A dead 302-line view duplicates and diverges from the app's real row.**
`Project-Ezra/Features/Components/TaskCardView.swift` is never instantiated
anywhere in the codebase — confirmed by grep (zero call sites outside its own file
and `#Preview`) and by git history (added once, `b555c6b`, 2026-09-11, never
touched since). It reimplements swipe-to-complete, drag, and accessibility
logic that `TaskRow.swift` already owns as the shipped pattern, and it has
already drifted: it reads its own due-date text (`TaskCardView.swift:262-279`)
instead of the `DueLabel` the rest of the app centralized specifically so two
formatters couldn't disagree (`TaskRow.swift:112-114`'s own comment). A second,
similarly dead block sits in `ConfirmCreationCard.swift:374-393`
(`chipContent`, never referenced, contradicts the file's current "only show
what's known" chip rule). Neither is reachable by a user, which is exactly the
audit procedure's definition of a finding (§3: "views reachable from nowhere are
a finding") — but a shadow implementation that quietly disagrees with the real
one is worse than dead weight, because the next person who greps for "the task
card" has a 50/50 chance of editing the wrong file. **Severity: drift.**

**Row-level navigation buttons systematically skip the touch-target discipline
the rest of the app enforces.** The app has a real, working pattern for the
44pt HIG floor — `LayoutMetrics.hitTarget` / `.minimumHitTarget()`, applied
consistently to status glyphs, chips (`MetadataChip.swift:44,56`), toolbar
icons, and most buttons. But every *custom text row that behaves like a button*
skips it: `TaskDetailView.swift:851-880` (`stepRow`), `:1136-1197`
(`spineStepRow`), `:970-1037` (`spineBlockerRow`'s open and remove controls),
`:903-936` (`dependentsSection` row); `TaskDeckView.swift:173-179` ("N
waiting"); `GroupProposalRow.swift:42-47,123-143`; `TasksHomeView.swift:363-392`
(the Mine/Everyone/Created tab pill, `minHeight: 32` with no
`.minimumHitTarget()` while its sibling filter capsule on the same row has
one); `InviteViews.swift:60-68,75-78,158-162` (Copy link / Try again / Join);
`UndoNoticeView.swift:91-99` (the Undo button, arguably the single
highest-trust control in the whole resolve flow). This is the same gap
appearing eight-plus times across five unrelated files — a missing shared
modifier for "a text row that acts like a button," not eight separate
oversights. **Severity: drift**, but systemic.

**A CTA-height literal (52 or 54) is copy-pasted across the app with no
backing token.** `ComposerView.swift:1271,1418,1921` (Ramble, End listening,
Create), `TaskDetailView.swift:1409` (the pinned primary CTA),
`OnboardingView.swift:156,295,430`, `InviteViews.swift:55` — eight sites, two
slightly different magic numbers, and no `LayoutMetrics`/`Spacing` entry for
either. The Create button's own label is dynamic
(`createTitle(created:merged:group:)`, `ComposerView.swift:1946-1960`, e.g.
`Create "Trip to Lagos" · 4 steps · merge 2`) inside a fixed-height capsule
with no `lineLimit` guard — the one primary action most likely to need the
extra room at large Dynamic Type sizes has none. **Severity: drift.**

**The same small component gets reimplemented instead of shared, at least
three times.** Mic/photo capsule buttons in `ComposerView.swift:2229-2255` and
`:2342-2371` are ~20-line near-duplicates of each other; the group/keep-as-one
buttons at `:1660-1679`/`:1693-1714` repeat the same secondary-capsule shape
again. `SettingsView.swift:106-123` reimplements `HouseholdRosterView`'s
`PhotoPickerButton` (`:307-329`) inline because the original is declared
`private` to the wrong file. `TaskAdvisorChatView.swift` and
`HouseholdChatView.swift` share ~150 lines of near-identical toolbar,
scroll-to-bottom, and send-handler glue that was copy-pasted rather than
factored into one chat scaffold (detailed under Advisor & Chat below). None of
these are bugs today; all of them are places where the next edit is likely to
land in only one copy and silently diverge the two surfaces the app promises
read identically. **Severity: drift** (Lens 3 — missing primitive, not a
one-off patch).

**One real, unmitigated destructive-action gap.** Every other destructive
action in the app (Settings' two data-clears, the task pager's Cancel, the
composer's Discard, `ParkedCapturesRow`'s discard) is confirmed —
`.confirmationDialog` or `.alert`. `HouseholdRosterView.swift:244` is the one
exception: `Button("Remove from household", role: .destructive) { remove(member)
}` sits inside a `Menu`, directly beneath "Invite to share this household" in
the same menu, and fires `remove(member)` — which sets `member.deletedAt =
Date()` and saves immediately (`:297-300`) — on a single tap, with no dialog
and no visible undo on this screen. This is a real person's household
membership, in a two-caretaker shared-plan product, one menu-tap away from a
mis-fire next to its own "Invite" sibling. **Severity: blocking** — not a
crash, but the one place in the app where the product's own "nothing
destructive fires without confirmation" pattern, applied everywhere else, was
skipped on the highest-stakes target in the flow.

## Per flow

### Tasks ("My Issues")

The home screen: a header row with two independent dimensions (ownership tabs
Mine/Everyone/Created; a filter capsule, always present) over a status-sectioned
or flat list of dense one-line `TaskRow`s — signal marker, status glyph, title,
due label, trailing avatar, no dividers. A capture orb floats bottom-trailing;
Ask, search, and a "…" menu live in the toolbar. Broken-down chains render as a
horizontally-paged `TaskDeckView` card stack instead of a vertical fan.

1. **`TaskSearchView.swift:61` reintroduces dividers the rest of the app
   deliberately removed.** `if index > 0 { TaskRowDivider() }` between search
   results directly contradicts `TaskRow.swift`'s own header comment
   ("Dividers are gone in My Tasks — Linear parity") and `TaskLaneList.swift`'s
   matching comment on both its list variants. Search is the one place in the
   Tasks flow that doesn't look like the rest of the Tasks flow. **Drift.**
2. **The ownership-tab pill is the one primary control in this header missing
   the touch-target treatment its sibling has.** `TasksHomeView.swift:363-392`
   frames the Mine/Everyone/Created button at `minHeight: 32` with no
   `.minimumHitTarget()`; the filter capsule two lines away in the same
   `headerRow` calls it correctly (`:512`). **Drift**, covered under
   Cross-cutting.
3. **Error state is haptic-only.** A dropped save on complete/cancel/status
   change (`TaskRow.swift:97,248`) fires `.sensoryFeedback(.error, ...)` and
   nothing visible — no banner, no alert. It satisfies CLAUDE.md's "a dropped
   save must leave a trace" to the letter, but the trace is inaudible to
   anyone with haptics off and invisible to everyone. **Polish**, but worth a
   second look given how central "did my tap save" is to a task manager.

### Capture / Ramble

A voice-first sheet: `.listening` (an orb reflecting mic level, nothing else)
→ `.understanding` (same orb, a "Making sense of it" label) → `.confirm`
(editable transcript, one card per draft, a pinned "Create N tasks" CTA), with
`.capture` as the typed escape hatch. This flow's two signature product rules
— "a revealed interpretation is final" and "no live transcript, the orb
reflects reception not interpretation" — were verified directly against the
code, not just the comments, and both hold structurally: `Interpretation.propose`
is a hard no-op once `reveal()` has run, and `RambleOrb` has no text-rendering
path at all. This is the strongest-built flow in the app.

1. **The Create button — the one CTA whose label is dynamic — sits in a
   fixed-height capsule with no line-limit guard.** `ComposerView.swift:1921`,
   height 52, label built from `createTitle(created:merged:group:)`
   (`:1946-1960`), which can read `Create "Trip to Lagos" · 4 steps · merge 2`.
   At larger accessibility text sizes this is a real clipping risk on the
   screen's only primary action. **Drift**, covered under Cross-cutting.
2. **Network failure during cloud capture produces no distinct signal.** A
   slow or failed cloud parse silently falls back to the deterministic local
   read (`runParse`, `:962-966`) — consistent with the documented "capture
   never blocks" rule, but the user genuinely can't tell a degraded local
   read from the cloud one. Flagging as **by-design, not a defect** — but
   worth an explicit product call, since every *other* failure mode in this
   flow (mic denied, save failed, OCR failed, photo import failed) gets its
   own named alert, and this is the one silent exception.
3. **Two near-duplicate secondary-capsule buttons, twice.** Mic/photo
   (`:2229-2255`/`:2342-2371`) and group/keep-as-one (`:1660-1679`/`:1693-1714`)
   — four call sites, two shapes, zero shared component. **Drift**, covered
   under Cross-cutting.

### Task Detail

A full-screen pager (`TaskDetailPager`, peers snapshotted at open, custom
20pt-edge-swipe dismiss since `fullScreenCover` has no native interactive
dismiss) over `TaskDetailView`, whose layout is derived from one of four
mutually exclusive shapes (`Models/TaskShape.swift`: deciding / waiting /
container / action) — never stored, computed fresh from the task's own state.
Chrome — title, property card, description, Details disclosure, pinned CTA,
Advisor line — is shared across all four; only the "spine" (blocker rows or
step rows) and the CTA label change.

1. **The spine rows are the one place in this file that doesn't get the
   file's own touch-target treatment.** `stepRow` (`:851-880`),
   `spineStepRow` (`:1136-1197`), `spineBlockerRow`'s open and remove controls
   (`:970-1037`), and `dependentsSection`'s row (`:903-936`) are all driven by
   14pt text with 8pt spacing and no `.minimumHitTarget()` — roughly an 18-20pt
   effective tap height, next to a page that otherwise enforces 44pt
   religiously (chips, glyphs, the Details disclosure). **Drift**, covered
   under Cross-cutting.
2. **Two independently-maintained step-row implementations, where the
   equivalent blocker case is already unified.** `blockerChipRow` (:819-821)
   correctly forwards to `spineBlockerRow` — one implementation, two call
   sites. `stepRow` and `spineStepRow` don't get the same treatment: two
   separate ~30-line row builders that differ only in the "next step" pointer
   and the effort label. The DRY fix the file already applied to blockers
   wasn't applied to steps. **Drift.**
3. **Task titles inside the spines truncate hard, with no scale-down.**
   `:916,866,1157,1003,1018,535` all set `.lineLimit(1)` on user-authored
   titles with no `.minimumScaleFactor` — a real cost specifically because
   this app's own capture pipeline worries about near-duplicate titles
   elsewhere; two similarly-named tasks are exactly the case where a
   mid-word truncation matters. The main editable title field gets this
   right (no line limit); the spine rows don't. **Drift.**

### Advisor & Chat

Two chats sharing one vocabulary (`ChatComponents.swift`): a per-task advisor
sheet and a household "Ask" sheet, each a `ScrollView` thread (opener →
messages → follow-up chips) with a pinned composer bar. The Advisor's own
reading (`AdvisorView.swift`) is containerless, label-less, and renders
nothing on a failed generation — verified directly in code
(`:136-137,190-193`), not just asserted. Both chats correctly keep the
keyboard down whenever there's a reading or a day-answer to read
(`TaskAdvisorChatView.swift:165`, `HouseholdChatView.swift:106-127`), and
cited task rows carry identical swipe actions in both, backed by one shared
modifier (`TaskSwipeActions`, `TaskLaneList.swift:144-185`).

1. **"Clear conversation" is destructive with no confirmation, in both
   chats.** `TaskAdvisorChatView.swift:128-133` and
   `HouseholdChatView.swift:88-93` both give it `role: .destructive` inside a
   `Menu` — red label, no dialog — and it fires on tap. The same file already
   has the confirm pattern in hand (`showDecisionPrompt`'s `.alert`,
   `TaskAdvisorChatView.swift:151-160`); it just wasn't applied here.
   **Drift**, and the second of the audit's two unconfirmed-destructive-action
   findings (the first is Household remove — see Cross-cutting).
2. **`AdvisorView.swift:658` strokes the obligation card with
   `accentGradient`**, which reads as a literal violation of "the Advisor
   never wears `accentGradient`" as that rule is stated in CLAUDE.md. The
   in-file comment argues a real distinction — the gradient marks the
   *obligation* (a flagged decision), not *the reading* itself — and every
   other Advisor control correctly uses the flat/bordered treatment
   (`secondaryButton`, `:672-690`). Likely an intentional, undocumented
   carve-out rather than drift. **Flagging for a human call**: either the
   rule's written text should name this exception, or the stroke should move
   to `accentFlat`.
3. **~150 lines of scaffold — toolbar, scroll-to-bottom, the `send()` guard,
   a `byID` dictionary built three separate times — are duplicated between
   the two chats** rather than factored into one shared chat-screen
   component. Detailed under Cross-cutting. **Drift.**

### Activity, Household, Settings, Onboarding

Four small, mostly clean surfaces. Activity is a sheet with a native
`List`/`Section` grouped by day, an unread accent dot, and a swipeable/inline
Undo. Household is a custom roster card (photo, name, relationship menu,
"…" menu) plus an invite-link sheet and an identity-link sheet. Settings is
genuinely sparse — a reset notice, a profile card, one digest toggle, a
data-boundary card, and an export/clear card behind two confirmed dialogs.
Onboarding is four phases ending on editable draft cards. `ContentView.swift`
is real (wired from `Project_EzraApp.swift`) but adds nothing of its own.

1. **`HouseholdRosterView.swift:244` — remove-member fires with no
   confirmation.** The audit's one blocking-severity finding; full detail
   under Cross-cutting.
2. **The relationship menu's label is plain text, not a `MetadataChip`.**
   `HouseholdRosterView.swift:224-227` uses `Text().metadataStyle()` for an
   editable value where the design system's own rule ("every editable capsule
   is a MetadataChip") is followed correctly one screen over, in Onboarding's
   category menu (`OnboardingView.swift:463-469`). **Drift.**
3. **`InviteLinkSheet` and `IdentityLinkSheet` have no scroll container**, and
   `IdentityLinkSheet` additionally has `.interactiveDismissDisabled()` with
   no in-sheet way out (`InviteViews.swift:30-97,114-198,199`). At large
   Dynamic Type, or with a bigger roster, content can exceed the fixed
   `.medium` detent with nothing to scroll and — on the identity sheet — no
   way to back out at all. **Drift.**

## Systems lens

This is an unusually disciplined codebase for a three-week-old solo build, and
that discipline is visible at the system level, not just in individual files.
The token system (`Palette`/`Spacing`/`Radius`/`Font`/`IconSize`) is close to
universally honored — across all 38 view files, the only raw-literal escapes
found were a handful of small spacing/padding numbers (`AssessmentChip.swift`,
`ConfidenceRow.swift`'s `ProvenanceTag`, `RevealEntrance.swift`) and two raw
`.font(.system(size:))` glyphs (`DetailActivityTimeline.swift:138`,
`SignalMarker.swift:68,73` — the latter via a parallel, hand-rolled
`@ScaledMetric` rather than the sanctioned `Font.glyph*` family, functionally
fine but a second scaling mechanism where one already exists). Zero raw hex
colors were found outside `Design/Theme.swift` itself, and `.glassEffect` is
used in exactly one file (`Design/Glass.swift`) — every other glass surface in
the app goes through `.glassChrome`/`.glassCapsule`, which is precisely the
centralization the design system claims for itself. `.borderedProminent` does
not appear anywhere in the app; the "one primary CTA slot" rule is enforced by
construction, not convention, because there's no competing button style to
reach for.

Where the system breaks down is at the boundary between *shared component*
and *shared pattern*. The token discipline is real, but several row- and
button-*shapes* that repeat three or more times across unrelated files were
never extracted: the secondary-capsule button (four sites in
`ComposerView.swift` alone), the photo-picker button (reimplemented rather
than shared between Settings and Household), the chat-screen scaffold (two
copies, ~150 lines), and the step/blocker row pair inside `TaskDetailView`
itself (one pair unified, one pair not). None of these cost the user anything
today. All of them are the specific failure mode a fast-moving single-file
codebase accumulates: not inconsistent tokens, but inconsistent *structure*
built from consistent tokens — which is harder to see in a diff and easier to
let drift, because each copy still looks correct on its own.

The touch-target story tells the same pattern from a different angle. The app
has a real, well-used primitive for the 44pt floor
(`LayoutMetrics.minimumHitTarget`) and applies it thoroughly to *designed*
controls — chips, glyphs, toolbar icons. It is applied inconsistently to
*emergent* controls — plain text rows and buttons that grew into being
tappable (a step row, a blocker row, a tab pill, an Undo button) without
anyone deciding "this is a button, size it like one." The fix is not eight
separate patches; it's one row-level modifier next to the one that already
exists for chips.

Two dead views (`TaskCardView.swift`, `ConfirmCreationCard.swift`'s
`chipContent`) are the clearest evidence of how fast this repo has moved: both
are leftovers from screens (Today/Inbox, an older card layout) that CLAUDE.md
confirms were deliberately cut, and both were left in place rather than
deleted with the surfaces they served. Neither is currently harmful, but
`TaskCardView` in particular has already begun to diverge from the pattern it
copied (its own due-date formatter, not the centralized `DueLabel`) — which is
exactly the risk of leaving a duplicate alive instead of deleting it at the
same time as its reason for existing.

Concept count is genuinely low and matches the product's stated "calm over
engagement" posture: the whole app surfaces eight top-level nouns to a user
(My/Our Tasks, Activity, Ask, Manage household, Settings, Search, plus the two
Onboarding phases) and exactly two Settings toggles. No internal vocabulary
(`WorkIntent`, `TaskDraft`, `childOf`) was found leaking into user-facing copy
— "Ramble" and "Ask" are the two internal-sounding words that do appear in
copy, and both are deliberate product terms per `docs/capture.md`, not
accidental leaks. The Advisor's "renders nothing on failure" rule and the
composer's structural enforcement of "a revealed interpretation is final" are
both real, verified in code rather than asserted in comments — this app
practices the restraint its own docs preach more often than it doesn't.
