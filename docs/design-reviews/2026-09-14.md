## Scope

Read in full: all 37 files matching `struct \w+: View`/`class \w+: UIViewController` under `Project-Ezra/` (Features/, Design/, ContentView.swift), plus the five `Design/` token files (`Theme.swift`, `Typography.swift`, `LayoutMetrics.swift`, `Glass.swift`, `Motion.swift`) for the inventory pass. ## Inventory

Design tokens live entirely in `Design/`: `Theme.swift` (`Palette` — light/dark-adaptive hex colors, no asset-catalog colors at all; `Spacing`; `Radius`), `Typography.swift` (a `Font` extension whose every token is scaled via `UIFontMetrics`, plus an `IconSize`/`Font.glyph*` pairing built specifically to fix glyphs that used to freeze at accessibility text sizes), `LayoutMetrics.swift` (`hitTarget` = 44pt, `recordGlyphColumn` = 28pt, `tasksHeaderRow` = 32pt, `minimumHitTarget(around:)`), `Glass.swift` (`.glassChrome`/`.glassCapsule` plus two small shared components), `Motion.swift` (spring/animation tokens, a `PressableStyle` family). `Assets.xcassets` holds only `AppIcon` and `AccentColor` — every other color is a hex literal routed through `Palette`, which is the opposite of the usual "no token file" finding: the system is unusually disciplined about *not* using the asset catalog as a second source of truth.

## Cross-cutting

1. **(drift, systems) Destructive-action confirmation is inconsistent across the app, and Settings already has the right answer.** `SettingsView.swift:537-546` wraps its data-clearing actions in a shared `.confirmationDialog`. Three other irreversible-or-hard-to-reverse actions skip it entirely and fire on the first tap: Household's "Remove from household" (`HouseholdRosterView.swift:244`, soft-deletes a person with `member.deletedAt = Date()` at `:296-300`, no confirm, no undo surfaced in this view), both chat surfaces' "Clear conversation" (`TaskAdvisorChatView.swift:129-133`, `HouseholdChatView.swift:89-93`, wired straight to `store.clear(...)`, no confirm, no undo at all), and Task Detail's "Cancel task" (`TaskDetailPager.swift:355-363`, mitigated only by a 4-second `UndoNotice` pill at `:401-411`). One `.confirmationDialog` pattern exists in this codebase and three of its four destructive menu items don't use it.
2. **(drift, systems) Two fully-built components have zero call sites.** `HeldDepthView` (`Features/Components/HeldDepthView.swift:18-70`) — 52 lines, Reduce-Motion-aware, dark-mode-correct, with its own accessibility label — is never instantiated anywhere (`grep -rn "HeldDepthView("` returns nothing); it survives only as a comment in `Design/Glass.swift:14` citing it as "the signature AI tile," and its own header calls it "the CLAUDE.md exemplar for glass-with-a-fallback." `TaskCardView` (`Features/Components/TaskCardView.swift:13-302`) — 302 lines including a hand-rolled swipe-to-complete `DragGesture`, a leading-avatar mode, and blocked-state dimming — is likewise never instantiated; it's referenced only in comments at `Design/Motion.swift:27` and `Features/Components/SignalMarker.swift:9` as if it still renders. Git blame dates both to before the 2026-09-02 Brief/Today cut (`TaskCardView` last touched 2026-07-28, `HeldDepthView` 2026-08-24) — leftovers from a screen that no longer exists, not work in progress. A reader who trusts the comments (including this audit's own first pass) will believe both are live.
3. **(drift) The same "avatar + small action-glyph badge" composition is hand-rolled twice**, each with its own fixed, non-scaling point size instead of a `Font.glyph*` token: `Features/Components/ActivityRow.swift:143-154` (`.font(.system(size: 8, weight: .bold))`) and `Features/Detail/DetailActivityTimeline.swift:132-142` (`.font(.system(size: 7, weight: .bold))`) — same `ZStack`, same `Circle().strokeBorder(Palette.background, lineWidth: 1.5)` border, two copies. This is exactly the pattern `Typography.swift`'s own header comment warns against ("at accessibility text sizes a chip's LABEL grew while the glyph beside it stayed frozen").
4. **(polish) Row-level gesture consistency has one gap**: `TaskRow` gets `.taskSwipeActions` in the main list (`TaskLaneList.swift:211-212`) but not in Search results rendering the identical row (`TaskSearchView.swift:62-89`) — the same component behaves differently depending on which parent mounts it.

## Tasks Home (list, header, deck, search)

Large nav title with a header row (ownership tabs Mine/Everyone/Created, roster-conditional; a filter capsule) above a dense, divider-free row list (`[marker | 28pt status glyph | title | due/resolved-age | avatar]`, min height 52); a horizontally-paged "dependency deck" for chains; Search opens as a sheet reusing `TaskRow`.

1. **Blocking** — The ownership tab pills have no `.minimumHitTarget()` and a 32pt height floor against the app's own 44pt tap-target rule: `TasksHomeView.swift:327-356` (padding at :344 is `isSelected ? Spacing.sm : 0`; frame at :354 uses `LayoutMetrics.tasksHeaderRow` = 32, vs. `LayoutMetrics.hitTarget` = 44 at `LayoutMetrics.swift:20`). Every other interactive control in this file wraps `.minimumHitTarget()`; the tab that switches whose tasks you're viewing doesn't. On the narrow-phone layout the code itself calls out (comment at `TasksHomeView.swift:307`), a tap on "Everyone" can miss.
2. **Blocking** — A dropped Core Data save on a status change is signaled by a haptic alone, with no visible text: `TaskRow.swift:82-86` (comment), `:304-306`, `:322-325` (`.sensoryFeedback(.error, trigger: saveFailed)`, no alert, no inline text). Marking a task done during a failed save leaves the row looking unchanged; the only feedback is a buzz, invisible to VoiceOver and to anyone not attending to haptics, with no retry path offered.
3. **Blocking** — The dependency deck's umbrella-task caption — the only way to open the outcome task from the chain view — has no minimum tap frame: `TaskDeckView.swift:101-123`, no vertical padding on the `HStack`, tap area sized to the text's own line height. Every sibling control in this flow (status glyph, filter, tabs) gets explicit sizing; the one carrying real navigation here doesn't.

## Capture / Ramble

Composer sheet opens directly into `.listening` (orb only, no transcript) → auto-submits after 5s silence or an orb tap → `.understanding` (orb only) → `.confirm` (editable transcript, draft cards, pinned "Create N tasks" bar). `.capture` is the typed escape hatch. Verified against the flow's own stated intent (opens into listening, no live transcript, no intermediate AI truth shown as settled) — holds, no contradictions found.

1. **Drift** — The orb's finish-listening tap bypasses the app's own button/feedback system: `.contentShape(Circle()).onTapGesture { ... }` at `ComposerView.swift:1276-1288`, and the orb is `.accessibilityHidden(true)` (`:1297`), while every sibling control in the same screen (`rambleButton` :1238, `circleControl` :1359, `endVoiceButton` :1385) routes through a `.pressable…` button style. Tapping the orb to end listening early gets no scale/highlight acknowledgment — only the eventual phase change — while the redundant "Done" button one inch below does provide that feedback for the identical action.
2. **Drift** — A convenience escape hatch and the flow's one irreversible, data-committing action wear the identical visual weight: the `accentGradient`-filled 52pt capsule appears at `ComposerView.swift:1225-1243` (Ramble/submit), `:1370-1388` (Done — functionally a duplicate of the orb tap), and `:1805-1819` (Create — the actual commit). Nothing distinguishes "I'm done talking" from "I'm about to create tasks."
3. **Drift** — Control heights are raw literals instead of tokens, contradicting the design system's own "never a raw... spacing" rule: `ComposerView.swift:1235` and `:1382` (both bare `52`), `:2122`/`:2245` (bare `40`), `:2203` (raw `44, 44` instead of `LayoutMetrics.hitTarget`). Three independently-typed `52`s agree today by coincidence, not by a shared token.

## Task Detail

Full-screen page in a horizontal pager: nav bar → title/category/provenance → shape-driven spine → Advisor obligation block if flagged → property chips → description → collapsed Details (provenance + timeline) → pinned footer with one gradient CTA and an Advisor one-liner. Advisor-quiet intent holds: `showsReading: false` at the page's `AdvisorView` call site keeps the reading out of the page body; `accentGradient` appears only on the obligation block's stroke, the doc's own permitted "decision stroke" site.

1. **Drift** — "Cancel task" is `role: .destructive` but fires the mutation on the first tap, with no `.confirmationDialog`; recovery is entirely the 4-second `UndoNotice` pill. `TaskDetailPager.swift:355-363` (fires `task.killAndResurface` immediately), `:401-411` (`offerUndo`, the only safety net).
2. **Drift** — The pinned primary CTA's async-save guard (`.disabled(isPerformingPrimary)`, `TaskDetailView.swift:1405-1406`) has no visible busy state: `PressableStyle.makeBody` (`Motion.swift:299-314`) branches only on `configuration.isPressed`, never on `isEnabled`. A slow save leaves the gradient button looking fully live while taps are silently swallowed.
3. **Polish** — Every cross-referenced task title (dependents `:909`, step rows `:860`/`:1150`, blocker rows `:997`) is hard `.lineLimit(1)` while the task's own title field wraps freely. At larger Dynamic Type sizes a referenced title clips with no way to read the rest short of opening it.

## Chat (Task Advisor + Household Ask)

`NavigationStack` sheet: threaded `ScrollView`+`ScrollViewReader` (not `List`) of bubbled user lines and containerless Ezra lines with cited task rows, a pinned composer. States: pending/`ThinkingLine`, sent, retryable-failed, unavailable-failed, stopped, empty-with-starters. Row-swipe parity holds structurally (`ChatRowGestures` → `taskSwipeActions` shared by both surfaces, `ChatComponents.swift:112-114`) — but behavior around that shared row has drifted, below.

1. **Blocking** — "Clear conversation" is `role: .destructive`, wired directly to `store.clear(...)`, with zero confirmation AND zero undo — the one destructive action in the app with neither safety net. `TaskAdvisorChatView.swift:129-133`, `HouseholdChatView.swift:89-93` (both verified: `Button(role: .destructive) { store.clear(...) }` inside a `Menu`, no dialog, no notice).
2. **Drift** — The two chats diverged on scroll anchoring: task chat always scrolls to bottom on a new message (`TaskAdvisorChatView.swift:216-220`); household chat instead scrolls the *question* to the top when the answer carries citations, specifically so the explanation isn't hidden above the fold (`HouseholdChatView.swift:193-203`). A task-chat answer with several cited rows scrolls past its own explanation — the exact case household chat was written to avoid.
3. **Drift** — Keyboard auto-focus rules diverge: task chat raises the keyboard whenever there's no live Advisor opener, regardless of existing history (`TaskAdvisorChatView.swift:165`); household chat only raises it when the thread is empty (`HouseholdChatView.swift:122`). Reopening a task chat with history but a quiet Advisor steals focus over recent messages — something household chat deliberately doesn't do.

## Activity

Sheet with a day-grouped change-log list (avatar + glyph badge, summary, unread dot, inline Undo); tapping a row pushes a provenance-dump detail screen.

1. **Polish** — The Undo button has no explicit 44pt frame: `ActivityView.swift:164-168` renders as bare styled text, sized to its glyphs, while every comparable control elsewhere (e.g. `SettingsView.swift:443,457,476,521,533`) sets `minHeight: LayoutMetrics.hitTarget` explicitly.
2. **Drift** — `ActivityDetailView` is a developer-grade provenance dump reachable from ordinary product chrome (tap any row) with nothing visually marking it as diagnostic rather than product UI (`ActivityDetailView.swift:39-60`); the file's own header comment (`:7-13`) names the tension but the mitigation is "nobody will tap a row who isn't looking for it."

Not a finding; flagged only because the wording is genuinely ambiguous.)*

## Household / Sharing

Roster card (you-row, member rows with a per-row "…" menu for invite/remove); `InviteLinkSheet` generates/shares a link; `IdentityLinkSheet` is the arriving side's pick-your-name screen.

1. **Blocking** — "Remove from household" is `role: .destructive`, no confirmation, fires on the first tap: `HouseholdRosterView.swift:244` → `remove(member)` at `:296-300` (`member.deletedAt = Date()`, no dialog, no undo surfaced here). Verified directly. This is the same pattern as cross-cutting finding #1, but worth naming again here since it's the single most consequential of the four: the only person-level destructive action in the app.
2. **Drift** — `IdentityLinkSheet` sets `.interactiveDismissDisabled()` (`InviteViews.swift:199`) with no comment explaining why, unlike every other deliberate constraint in this codebase (which is annotated as a matter of house style).
3. **Polish** — `canInvite` correctly gates invitations on `HouseholdSync.isLive` (`HouseholdRosterView.swift:107-110`), but a caretaker who can't invite a given member just sees the menu item silently absent, with no stated reason.

## Onboarding

`.welcome` (name) → `.intro` (paste/type or OCR a screenshot) → `.settling` → `.result` (editable, categorized draft list, commit). Runs full-screen, one-way.

1. **Drift** — No way back from `.intro` to `.welcome` or from `.result` to `.intro` to fix a typo'd name or reconsider pasted text short of committing or restarting. The file's own comments justify the *result* screen's lack of exits but never address the earlier two phases, which share the identical one-way structure.
2. **Polish** — OCR-failure and empty-parse messages (`OnboardingView.swift:247-255`, `:277-283`) are plain `Text` with no accessibility live-region/label, so a failed screenshot read is silent to VoiceOver beyond the text appearing.

## Settings

Profile card, weekly-digest toggle, data-boundary/telemetry card, export/clear-data card (DEBUG diagnostics excluded from user-facing scope).

1. **Drift** — A denied notification permission for the weekly digest produces no visible feedback: the toggle (`SettingsView.swift:202-208`) stays on while the OS silently blocks the actual notification; there's no branch handling the denied case. This screen is otherwise the app's best-behaved destructive-action model (`:537-546`'s shared `.confirmationDialog`) — the gap is real but isolated.

## App shell (RootTabView / ContentView)

No `TabView`: `TasksHomeView()` renders directly under a `ZStack` with the floating capture orb bottom-trailing; exactly four sheets mounted once (composer, Activity, Ask, IdentityLink) — confirmed matching the stated architecture.

1. **Drift** — The file's own header comments (`RootTabView.swift:4-15`, `:26-29`, `:33-34`) repeatedly describe "the SYSTEM tab bar (Brief · Tasks)," but `body` (`:110-169`) contains no `TabView` at all. A contributor reading the header before the code would be misled about what actually ships.

## Systems lens

The design-token layer is genuinely strong and the rare case worth naming plainly: `Palette`/`Spacing`/`Radius`/`Font`/`IconSize`/`LayoutMetrics` are consistently reached for, Dynamic Type is threaded through via `UIFontMetrics` rather than fixed point sizes almost everywhere, and the few `.font(.system(size:))` escapes found (`AvatarView.swift`, `SignalMarker.swift` — proportional to a caller-supplied `size`) are a defensible exception, not drift, since they scale a *computed* dimension rather than freezing a token. The failure mode this audit actually found is not "no system" but **two systems that quietly stopped agreeing with the code**: a design-system component doc-comment (`Glass.swift:14`) that still cites a dead view as the canonical example, and two other files (`Motion.swift:27`, `SignalMarker.swift:9`) that reference `TaskCardView` as if it still renders. Comments that assert liveness for dead code are worse than no comment, because they actively mislead the next read — this is the same failure shape as the stale `RootTabView` header comment above, just at component scope instead of screen scope. Concept count stays tight: six navigation-title strings total (Manage household / Activity / Details / Settings / Ask / Search), no model type name leaks into user-facing copy anywhere sampled. The Advisor's "prominence implies supervision" discipline holds structurally (containerless, `showsReading: false` on the detail page, `accentGradient` reserved for the one permitted decision-stroke site) — the one place the app shows AI "thinking" chrome outside the capture orb is exactly where the product doc says it should. The clearest system-level gap is the destructive-confirmation inconsistency (cross-cutting #1): one correct pattern exists, three call sites don't use it, and none of the three are exotic enough to explain why.

## Top fixes

1. **Standardize destructive-action confirmation.** Household "Remove from household," both chats' "Clear conversation," and Task Detail's "Cancel task" all skip the `.confirmationDialog` pattern Settings already uses correctly. `HouseholdRosterView.swift:244`, `TaskAdvisorChatView.swift:129-133`, `HouseholdChatView.swift:89-93`, `TaskDetailPager.swift:355-363`, `SettingsView.swift:537-546` (the pattern to copy). Severity: blocking.
2. **Fix the sub-44pt tap targets on Tasks Home.** Ownership tab pills and the dependency deck's umbrella caption have no `.minimumHitTarget()`. `TasksHomeView.swift:327-356`, `TaskDeckView.swift:101-123`. Severity: blocking.
3. **Make a dropped task save visible.** Currently signaled by haptic alone. `TaskRow.swift:82-86,304-325`. Severity: blocking.
4. **Delete or relocate ~350 lines of dead, "still-live"-labeled components.** `HeldDepthView` and `TaskCardView` have zero call sites but are cited elsewhere as if they render. `Features/Components/HeldDepthView.swift`, `Features/Components/TaskCardView.swift`, `Design/Glass.swift:14`, `Design/Motion.swift:27`, `Features/Components/SignalMarker.swift:9`. Severity: drift.
5. **Reconcile the two chat surfaces' scroll/focus behavior.** Each was deliberately written to handle a case the other ignores. `TaskAdvisorChatView.swift:165,216-220`, `HouseholdChatView.swift:122,193-203`. Severity: drift.
