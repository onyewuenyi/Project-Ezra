# Decisions — the long form of `CLAUDE.md`

**What this is.** On 2026-09-12 `CLAUDE.md` was 182 KB and loaded into every session. It
had grown back past the size that forced the 2026-09-02 extraction of `capture.md`,
`advisor.md` and `surfaces.md`, and it had stopped obeying its own rule — *that file keeps
the rules; the docs keep the why* — because every rule carried its dated reversals,
measurements and archaeology in the same paragraph. So the split was made mechanically and
losslessly: `CLAUDE.md` became the rulebook (one to three sentences per rule, a pointer
each), and **this file is the full text it was compressed from, verbatim, under the same
headings.** Nothing was deleted; it was moved.

**How to use it.** A rule in `CLAUDE.md` names the file or symbol it binds and, where the
reasoning matters, the section here. Grep this file for the rule's bold lead phrase (the
leads were kept) to find its story. When a rule changes, change it in `CLAUDE.md` and in the
matching paragraph here — the two are one text at two lengths, and a rule that moves in one
and not the other is the drift both files warn about.

**Where this text should end up.** Much of the capture and Advisor reasoning below is
already duplicated, more fully, in `docs/capture.md` and `docs/advisor.md`; the newer
paragraphs (the boundary pass and `-FMPrimitives`, the Kinly layer, the telemetry boundary,
live sync, the Sunday digest, the schema freeze) exist only here. The intended direction is
to fold each into its topical doc one subject at a time and delete it from here, not to let
this file become a second `CLAUDE.md`.

## Posture — research preview, on purpose

**This is a single-developer research and development build, deliberately running on the newest software.** From 2026-09-17 that is iOS 27 GA — Xcode 27.0, macOS 27.0, Foundation Models' year-two APIs, and Firebase's public-preview `GeminiLanguageModel` on a tagged release; until then it was the Xcode 27 betas and a branch-pinned Firebase preview. All *intentional* choices, not risks to be managed down. The point of this project is to explore new platform capabilities early, and the posture does not soften because the platform shipped.

What follows from that, and what an agent working here must not undo:

- **Do not gate a capability on evidence that does not exist yet.** "Ship it once the benchmark proves it" is the wrong default here — turn it on, then measure. Evals (`AdvisorBenchmark`, `-CaptureDiagnostics`, `RambleEvalTests`) exist to *tune* what is running, never to grant permission for it to run.
- **Do not add "wait for GA" caveats.** Preview APIs reshaping before GA is expected and accepted. If an SDK breaks, fix it then.
- **Do not soften a capability to something safer without being asked.** Prefer the strongest available option and let a measurement argue it down.
- Two things this posture does **not** relax, because they protect the user rather than the schedule: **safe defaults for data** (the deterministic tail must always exist, `validated(against:)` still rejects untrusted model output, corrections still never leave the device) and **the guardrails in `docs/` about what the product refuses to do**. Explore capabilities freely; don't quietly change the product's promises.

## Toolchain — non-negotiable

- **Build with Xcode 27 (iOS 27 SDK).** The deployment target is iOS 27.0. Xcode 26 has no iOS 27 SDK and the build fails. Confirm with `xcodebuild -version` (expect 27.x). If it shows 26.x, the active toolchain is wrong: `sudo xcode-select -s /Applications/Xcode.app/Contents/Developer` — the GA Xcode 27.0 (27A266a) replaced the beta at that path on 2026-09-17, and `Xcode-beta.app` no longer exists on this host. **The simulator runs the real on-device model when the host's Apple Intelligence is on**: measured that day on the iOS 27.0 (24A434) runtime, `-FMDiagnostics` reported `host engine: Apple Intelligence · on-device`, served six arms with 0 failures and 0 timeouts, and the candidate arm reached preFirstToken p50 816ms (the unguided floor 372ms). Those are Mac-silicon numbers, not phone numbers — the sim proves the model ANSWERS here, never a device latency.
- Swift language mode is 5.0 (not Swift 6 strict concurrency), but `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` — types are main-actor isolated by default.
- **firebase-ios-sdk is a tagged VERSION, `12.19.2` up to next major (2026-09-17).** Firebase 12.19.0 shipped `GeminiLanguageModel` — the bridge conforming Gemini to `FoundationModels.LanguageModel`, the entire reason the cloud rung can be a `LanguageModelSession` like every other rung — as a public-preview product of its own (`GeminiLanguageModel/` inside the repo), which the `FirebaseAILogic` target depends on under `compiler(>=6.4) && canImport(FoundationModels)`. `GeminiProvider` already called `FirebaseAI.firebaseAI(…).geminiLanguageModel(name:)` and already imported `FirebaseAILogic`, so the app-side change was the package requirement plus one capability: the GA bridge advertises `toolCalling · reasoning · guidedGeneration` and dropped `.vision` from the set the preview had. **History, kept because the lesson generalises:** from 2026-08 the dependency was pinned to the `wwdc26-preview` BRANCH — deliberately, because no tag carried the bridge and the branch was the only place it compiled. The cost accepted was a broken upstream commit with no version to blame, and the rule was "check `Package.resolved`'s pinned commit first." That rule was incomplete: on 2026-09-17 the Xcode 27.0 update (27A266a, FoundationModels module 2.0.68) replaced `Transcript.Segment.custom` with `.attachment(AttachmentSegment)`, and the pinned commit `5d9b338` — which conformed four `Part` types to `Transcript.CustomSegment` under `#if compiler(>=6.4)` — stopped compiling with `'CustomSegment' is not a member type of struct 'FoundationModels.Transcript'` while the pin, the checkout and upstream all still agreed. A preview branch pinned against a moving SDK breaks from EITHER side, and the day it breaks the upstream branch is usually abandoned (Firebase had moved the bridge to `main` and tagged it five weeks earlier; the preview branch was simply never updated). **So: a branch pin is a bridge to the first tag that carries the API, and the tag is taken the moment it exists.** Firebase 13 removes the `FirebaseAI` wrapper library; we import `FirebaseAILogic`, so the up-to-next-major cap holds us at 12.x until that changelog is read on purpose.
- **Host needs macOS Tahoe 26.4+** to run Xcode 27 at all; if Address Sanitizer fails to launch on the iOS 27 simulator, that's a known Xcode 27 beta issue on host toolchains older than **26.5** — update Xcode, not the code. Apple silicon only: Xcode 27 no longer builds Intel/`x86_64` by default (`ld64` is gone; `-ld_classic` is no longer an option).

Tests live in `Project-EzraTests/` (Swift Testing, `@testable import Project_Ezra`) and cover the pure AI/ranking logic — `AutonomyPolicy`, `HeuristicEngine`, `IntentResolver`, `CorrectionProfile`, `TaskRanking`, `BrainSweeps`, the Today pipeline (`TodayQueriesTests`, `CapacityBaselineTests`, `DeterministicPlanTests`, `PlanSanitizeTests`, `PlanRoutingTests`, `TodayPlanStoreTests`), plus the `RambleEvalTests` accuracy harness; add cases there when you touch those.

**Known test-runner flake (environmental, not a code bug):** the whole suite passes (all cases green) but the run occasionally ends `TEST FAILED` via `Restarting after unexpected exit` — a *bare* crash of the test host with **zero** Core Data exceptions in the log, always alongside the iOS 27 simruntime warning `objc[…] Class UIAccessibilityLoaderWebShared is implemented in both WebCore.axbundle and WebKit.axbundle … may cause … mysterious crashes`. That's the Xcode 27 beta simulator's own accessibility-bundle conflict, not our code (diagnosed: the correct single-context test architecture throws no CoreData exceptions; only broken multi-coordinator variants did). If a run flips to failed with no `✘` cases and no `NSInvalidArgumentException`, just re-run (or use a freshly-booted sim).

## Project layout & Xcode gotcha

- The target uses a **PBXFileSystemSynchronizedRootGroup** (`Project-Ezra/`): any `.swift` file added under that folder is compiled automatically. **Do not hand-edit `project.pbxproj` to add/remove files** — just create or delete them. (Editing the pbxproj is only warranted for build settings.)
- Source is feature-organized: `Design/` (design system), `Models/` (Core Data `NSManagedObject` models incl. `PersistenceStack` + pure ranking; `CapacityLog` + `CapacityBaseline` are inert and retire with the Brief), `AI/` (engine layer + the Today plan generators/service), `Features/<Screen>/` (`Brief/`, `Tasks/`, `Capture/`, `Activity/`, `Household/`, `Root/`), `Features/Components/`. Persistence is Core Data via `NSPersistentContainer` (`NSPersistentCloudKitContainer`-ready — flip `PersistenceStack.cloudKitContainerID` + add the iCloud entitlement to enable sync); models are constructed with the `in:` context convenience inits.
- `Item.swift` is a retired template stub — the real model is `Models/TaskItem.swift`.
- Three utility seams worth knowing before you re-invent one: **`AI/SerialGate.swift`** (one-at-a-time execution for a resource that cannot be re-entered — `BriefSession` caches one `LanguageModelSession` per day and Foundation Models rejects a second concurrent `respond`; the rule it enforces is *the stored task must wrap the WORK, not the wait*, and it exposes `peakActive` so a test can assert the invariant rather than infer it from outputs). **`AI/CaptureProvenance.swift`** (the per-capture receipt — route, rung, winning arm, latencies, the full `[TaskDraft]` — as a JSON **file sidecar**, never Core Data, because *a diagnostic must never be able to cost the user their data*; follow that rule for any new diagnostic). **`AI/DeterministicReading.swift`** (rung 0's Advisor reading, so a worthy task is never a labelled empty surface).

## Architecture invariants

- **Four axes, never fused** (`docs/task-model.md`). (1) **Lifecycle** — `TaskStatus` (`.todo → .doing → .done | .canceled`), user-owned. **A `TaskItem` comes into existence at Confirm and never before**: the retired `.inbox` case was a ghost (every creation path confirmed in the same breath), so pre-Confirm state now lives on a parked `Capture` — raw text plus encoded drafts — which is explicitly *not* a task. `AppBrain.commit` IS the confirm; there is no `confirm()` mutation. `status.isLive` replaces the old `== .active` checks. (2) **Type** — `WorkIntent` (action/planning), **INTERNAL and system-owned since 2026-08-11**: no kind chip anywhere, no user-editing path (DEBUG-asserted in `markEdited`); the write chain is engine/backfill → `reclassify` only, its consumers are the Today advisor (`promptOnlyFacts`) and the breakdown bias, and its classifier is evaluated (`RambleEvalTests` kind floor) — trust through evaluation, not correction.workIntentChip`) — and there ONLY. The confirm card no longer renders it at all: the reveal shows the user-relevant consequence ("Needs a plan"), never the classifier, so the axis is internal until the task exists. It is **never nil at creation**: the on-device model classifies it, and off device (heuristic path, Apple Intelligence off/unavailable by region) `IntentResolver.inferredWorkIntent` backfills it lexically. That backfill **never reads `isJudgmentCall`/`needsDecision`**, which would re-fuse axes 2 and 3 (test-enforced by `IntentResolverTests.workIntentIgnoresJudgmentFlag`); its `.action` default is behaviourally identical to nil (same CTA verb, same capability set). Nil remains legal on the model (fixtures, a cleared value). The **Thinking Partner** is unlocked by the `needsDecision` flag OR choice-shaped wording (`DecisionShape`, the one decision lexicon) — never by this axis, which NEVER reads/writes `needsDecision`. **Three cases are retired:** `decision` (2026-08-08 — choosing is a capability the system brings, not a kind of work the user classifies; stored `"decision"` decodes as `.planning` via `WorkIntent.decode`, additively, no wipe), `waiting` duplicated the derived `blocked` flag, and `reference` existed only to be *excluded* — removing it collapsed `countsAsWorkload`, five gates, a bespoke heuristic detector, `MyTasksSectionKind`, and the `"reclassified"` verb. (3) **Attention flags** — Needs Decision (stored `needsDecision`), Blocked/Blocking/Overdue/Stale (derived on read, never stored). (4) **Signals** — `isUrgent`, human-declared, feeding a computed **system score** (`AttentionEngine` → persisted `AttentionMetadata`, 0–100 + contributors) that `TaskRanking` uses only to break ties WITHIN the hard bands. The score is NEVER a badge. **Persist-slow/compute-fast:** it reads only slow inputs (urgent, AI importance, effort shape, graph centrality) and never a fast fact, so "the AI never decides the band" holds by construction. Don't re-fuse these: adding a blocker must not move the status; high confidence must not auto-resolve a judgment call.

- **The row's leading marker is one slot with two residents.** `SignalMarker` renders **Needs Decision** (`decisionAccent`) or **Urgent** (`priorityUrgent`), decision winning when both are set, nothing when neither — the slot means "the one thing most demanding your attention", which is honest about being a composite. **This reverses the old "Needs Decision is detail-only, not on rows" rule, deliberately.** What must NOT appear there is the task's *type*: choice-shaped wording and `needsDecision` (axis 3) are different questions, and one glyph for both teaches the user they're the same thing. Type differentiates in the detail. Today (`TodayTaskRow`/`TaskCardView`) stays marker-free by design.

- **The primary CTA is one slot, or none** (`RecommendedAction` / `recommendedAction(among:in:)`, `docs/task-model.md` axis 1). It is **lifecycle-driven, not obstacle-driven** — the old ladder never surfaced `.doing`, so a `.todo` task read "Mark done" and skipped a state. The tree: resolved → Reopen · unowned → That's mine · **owned by someone else → nil** · blocked → Unblock · `.todo` → Start · `.doing` → Mark done. **The nil arm is the design** — someone else's task isn't yours to advance, so a button there is wrong by construction (and completing it would stamp *you* as attesting their work); its proxy moves live in `TaskMoreMenu`, and the empty slot is reserved for Nudge/Comment once `HouseholdSync.isLive` flips. **The verb never voices the type** — the intent-voiced verbs are all retired (`.planning`'s "Break it down" lied; `.decision`'s "Decide" retired with the type), so `.start` carries no associated value and reads "Start" (or "Resume" on a task with a closed `.doing` visit) — **with ONE deliberate, view-layer carve-out (2026-08-25): on a `.deciding`-shaped page, `.start` reads "Decide"** (`TaskDetailView.ctaTitle`), because there the work IS the choice and "Start" undersells it. The shape is derived from the human-owned flag, never wording, so this cannot re-fuse the type axis; `RecommendedAction` itself is untouched, and `.resolve` stays "Mark done" — it runs `completeAndResurface` and never touches `needsDecision`, so a decided-style label there would report a decision nothing recorded (`resolveDecision()` is the only clearer, owned by the obligation block). **Start does not dismiss the detail**: the button relabels to "Mark done" in place, which is how the lifecycle teaches itself. Only `.resolve` sets `dismissesDetail`. Claim precedes unblock. The fast path for trivial work stays in the **list**, and its shape changed 2026-09-01 to **one channel, one meaning, on every row type — where a row can't support a meaning the channel is ABSENT, never repurposed**: TAP the whole row opens the detail (one target, no holes); LEADING SWIPE performs the task's own `recommendedAction` through `performRecommendedAction` — *the same move the detail's pinned CTA would make*, which is what makes a swipe whose verb varies by row safe, and it is absent exactly when that returns nil (someone else's task, so "not yours to advance" becomes a gesture that isn't there); TRAILING SWIPE cancels (reversible, undo pill), absent on a resolved row; LONG-PRESS opens the full menu. The leading glyph's status menu is RETIRED on the plain row — it was the row's second tap target, and a chain root had a third. **ON A GROUP'S DECK CARD (2026-09-12, `TaskDeckView`) horizontal is NAVIGATION** — swipe left → next task, right → previous, hard edges — so both lifecycle swipes are ABSENT there (the channel means one thing per row type, never two), and the status glyph is the card's explicit completion target (`TaskRow.glyphInteractive`, the same interactive control the container spine's step rows carry; picks route through the same undo-aware seams as the menu). Never a secondary button under the CTA. Swipe outside a `List` is possible only because iOS 27 added `swipeActionsContainer()`; without it this surface would have had to become a `List` and lose the no-divider rhythm, the row backgrounds and the chain card chrome.

  5. **The launch self-heal repairs ONE store, never both (2026-09-20).** There are two stores in one container — the private one, holding every task the person has ever captured, and the CloudKit shared mirror — and `loadPersistentStores` runs its completion handler once PER store description. The self-heal underneath it did not know that: on any error it called `destroyStore`, which deletes every store file at the location, and then reloaded the whole container. So a shared mirror that would not open took the private store with it. That matters because the two stores fail for completely different reasons: the mirror depends on CloudKit's mood, on another person's account, and on a schema deployed by hand in a web console, while the private store depends on nothing but the disk. A repair for the fragile one was a wipe of the irreplaceable one, inside the very mechanism that exists to stop data vanishing silently. `destroyStore(only:)` now removes just the named file — both stores are still COPIED first, because a wider safety net is never the wrong call on a path that unlinks files — the failed description alone is re-added through the coordinator rather than reloading every description including the ones that opened a moment ago, and the `fatalError` is now the PRIVATE store's alone.   4. **A bulk delete happens in the STORE, and the interface is REBUILT, never refreshed (2026-09-19).** The user's own wipe — Settings ▸ "Clear all tasks" and "Reset everything" — crashed the app with SIGSEGV every single time, and had since the button existed. Reported as *"when I click clear all tasks or reset everything the app crashes"*. The mechanism is teardown-after-read, the same fault the test host has worked around since 2026-08-07 (`TestStore`'s parking array and `retainsRegisteredObjects`, ~70 EXC_BAD_ACCESS reports): once a managed object's attributes have been READ, any later teardown of that object — a property snapshot, a refresh to a fault, a delete, a dealloc — retains a value that is no longer a pointer and dies in `objc_retain`. `SettingsView` performs the clear while holding live `@FetchRequest`s for `TaskItem`, `ChangeLogEntry` and `Correction`, so every object it deletes is an object it has read. **Three teardowns reach this path and all three were measured crashing**: the original per-object `context.fetch` + `context.delete` loop (0/6 survival; bisected by entity with a `-ClearStep` seam — deleting every `TaskItem` alone survived, `ChangeLogEntry` was where it died); `mergeChanges(fromRemoteContextSave:)`, the documented companion to a batch delete, which lldb showed calling `deleteObject:` → `_establishEventSnapshotsForObject` → `objc_retain` → EXC_BAD_ACCESS; and `refreshAllObjects()` (1/6). `context.reset()` made it deterministic AND invalidated the identity objects the screen is bound to. **So the deletion happens where no object exists:** `NSBatchDeleteRequest` with `resultType = .resultTypeObjectIDs`, per entity, in the persistent store — legal here only because persistent history tracking is on, which is what lets CloudKit export the deletions. The service now counts the prompt with the model's own `tokenCount(for:)` (a character estimate and the tokenizer disagree by a factor that depends on the text) against `contextSize` minus the fixed overhead — instructions, the guided schema, the 500-token answer budget and a margin, counted once per launch — and walks a ladder, cheapest loss first: drop the related tasks · clip the quote and the reasoning to 240 characters on a word · clip the notes · bare facts. **Only the PROMPT is fitted**: the session key, `validated(against:)` and the evidence read the original facts, because `notes` is in the fingerprint and a clipped notes line would otherwise be a different session and a different "Why this?". The prompt's token count is recorded for `.taskAdvisor` so the diagnostics card can show how close readings run to the window; off-device the facts pass untouched (fitting is a courtesy, not a gate). **A context-overflow catch matches `AppBrain.errorLabel`, never a case** (`InquiryService.isContextOverflow`): the chat's rebuild caught only the deprecated `GenerationError.exceededContextWindowSize`, and the 27.0 model throws `LanguageModelError.contextSizeExceeded`, so on the phone an overflowing thread failed every turn until the person cleared it. **The kickoff line passes `KickoffService.validated`**: "never invent a phone number, URL or address" was prompt-only, and a step carrying a digit run of five or more, a web address or an email the facts never held is now dropped whole — silence was always the fallback, and a plausible wrong number is worse than none. `KickoffFacts` gained the person's own capture words ("They said: …", clipped to 200 characters, omitted when they only repeat the title — the detail that names the real first move usually lives there) and the windowed abandoned-start count, with an instruction to make the first move smaller when the obvious one already failed. The page warms a kickoff spare (`InquiryService.prewarmSpare`/`takeSpare`) while Start is the CTA and the tap would generate — not deciding, no stored next step — so the prefill happens before the button is pressed rather than under the person's thumb. **The reading's list fields are bounded at the decoder** (`.maximumCount(4)` on options, `.maximumCount(5)` on steps, `.range(15...120)` on a step's minutes): a fifth option or a sixth step is structurally impossible rather than generated from the answer budget and clamped away. Upper bounds only — a decoder MINIMUM would force two options onto every `advise` and `nothing` reading, the opposite of sharper silence — and the validator still clamps, trusting the guide no more than the prompt.
- **The Advisor's router asks for a REASONING BUDGET, not a model** (`AI/ReasoningBudget.swift`, v5). The question is *"how much cognition does this judgment deserve?"* — `ReasoningBudget` (`none`/`shallow`/`deep`) — and rung selection merely IMPLEMENTS the answer. This replaced a router that asked "is this hard enough to pay for", which is a procurement question dressed as a product one: it starts from the price list and works backwards, so the answer is always a percentage somebody chose. **Ezra decides the budget, never the model** (a model asked how hard to think about itself has an unbounded appetite), and the mapping is swappable without touching policy — when a cheaper rung starts matching the ceiling, `rung(for:)` changes and the budget assignments don't. `depthReason` carries the three hypotheses (`.decision` — framing options is the reasoning the local model lacks · `.multiStep` — blockers + open steps ≥ 2, a graph to hold rather than a fact, so ONE blocker deliberately isn't enough · **`.repeatedlyAbandoned` — `TaskAdvisorFacts.abandonedStarts >= 2`, CLOSED `.doing` visits on the task's own timeline, i.e. how many times the person picked this up and put it back down**). **The third one could not fire for ten days** (fixed 2026-09-12): it read `deferralCount`, whose only writer was the Brief's day-rollover, and the Brief was cut 2026-09-02 — so a router documented everywhere as three hypotheses was measurably two, and `-AdvisorBenchmark` exists precisely to FALSIFY those three. The hypothesis was never wrong; its evidence had been deleted, so the input moved and the reason was renamed with it. Floor 2 rather than 3 because the acts differ in cost: a deferral is one tap, an abandoned start is a declared start and an abandoned one — the first is an interruption, the second is a pattern. **`abandonedStarts` is in the FINGERPRINT** (the two counters beside it are prompt-only because they tick with a clock): without it "picked up, then put back down" hashes identically to the state BEFORE the attempt, and the Advisor serves back the very reading the attempt just disproved. `ReasoningBudgetTests.everyDepthReasonIsReachable` is the test that would have caught it — **a depth reason no input can produce is not a hypothesis** — and three `AdvisorDiagnostics` fixtures now abandon starts so the benchmark measures three. **The router was the SMALL half.** `StallDetector.isStalled` has two signals, either sufficient — repeated avoidance and silence — and the avoidance arm read the same dead counter, so since 2026-09-02 the ONLY route to "stalled" was neglect by SILENCE: a person actively bouncing off a task was invisible to the sensor built to catch exactly that, and the whole diagnosis ladder behind it never opened for them. The `.dying` headline had the same dead branch, so a task started and dropped three times was told *"This has gone quiet"* — the opposite of true. Both now read `TaskItem.recentAbandonedStarts(within:now:)`, **windowed** (a lifetime count would pin the diagnosis forever, which is what `deferralCount`'s consecutive-and-cleared design existed to prevent) and **silent while the task is `.doing`** (the open visit is not an abandonment; starting it silences the diagnosis for as long as the person is working — the dismissability `touchHuman` used to give). `TaskAdvisorFacts` carries the windowed count so the router inherits both properties, and the evidence line is guarded against saying "No progress in N days" about a task picked up three times. **`StallDiagnosis.headline` takes both counts as REQUIRED parameters** — a default is how the branch would die a second time, and that is now the THIRD instance of this exact failure (`ChatAdvisorLine.citedTasks`, `triage`'s `route:`): *a capability decided by a default parameter is a capability nobody is deciding about*. What hid it: the stall tests set `deferralCount` directly, so they exercised a field the app could no longer write — `AbandonedStartsTests` asserts through `status` transitions instead. `TaskRanking.deferralPenalty` is now DELETED rather than deferred (see the ranking bullet — removing a term multiplied by a permanent zero changes no ranking, and leaving it was a loaded gun aimed at the wrong signal); its two tests were repointed at the live down-pull, having been asserting on a field the app cannot write. **`InertSignalTests` is the guard against the whole class**: a curated table of fields the app can no longer write, an allowlist per field with a stated reason, and a mirror check so the allowlist cannot rot. A LIST, not a derivation — "which fields have no writer" needs a real index, and a half-working detector is one more instrument nobody can trust. It failed twice on its first run and both were worth having: it matched PROSE (four files whose only mention was a comment explaining the field is dead — `PrivateCaptureEngineTests` records the identical lesson for its cloud grep, so comments are stripped now: *prose may NAME a dead field, code may not read one*), and then it caught the two files still WRITING it, **both fixtures** — including `EvalCorpus`, the dogfooding seed, whose one "stalled by avoidance" task had been seeding an unreachable state so the on-device walkthrough could not surface that diagnosis at all. **A fixture describing a state the app cannot reach is worse than no fixture: it makes the surface look covered.** Reasoning: `docs/advisor.md`. It is called only AFTER the gate opened and the cache missed, so it never decides *whether* anything happens. Depth is **not length** — see the guardrail below.

- **Routing is DISCOVERED, not decreed** (`AI/AdvisorBenchmark.swift`, `-AdvisorBenchmark`). The gold-standard-first method: the strongest reachable rung establishes the CEILING on the hard corpus, and cheaper rungs **earn** cases by matching it — move equality plus abstention equality, deliberately NOT text similarity (scoring prose would reward the model that writes more, which is the exact failure the depth guardrail exists to prevent). **The routing percentage is an OUTPUT, printed as one**: never "cloud should be 10%", always "these N cases measurably need depth". `depthReason`'s three reasons are therefore falsifiable hypotheses — the report names **`OVER-CLAIMED`** (claimed deep, cheap rung matched anyway → narrow the band) and **`UNDER-CLAIMED`** (routed shallow, diverged from the ceiling → widen it; rarer and worse, because over-claiming costs money while under-claiming costs the product's promise). Answers are MODAL across repeats, sharing `-AdvisorRepeats` with the judgment eval — the eval already returned 5/8, 6/8, 7/8, 6/8 on byte-identical binaries, so comparing one sample per rung would attribute coin flips to capability. It shares `AdvisorDiagnostics.fixtures` on purpose: one corpus, two questions (*does the active path agree with a human?* vs *which rung is enough?*); two corpora would drift and the neglected one would be the one nobody was watching. **The cost target is not minimum cloud spend — it is maximum reduction in required attention per dollar of reasoning.** If deep reasoning writes better prose but buys no progression, don't pay.

- **Deep judgments run OFF the open-moment** (`TaskAdvisorStore.precompute`, Challenge 9). The Advisor is the one deep-thinking surface with no cover: Ramble hides behind the orb, the Brief behind the Recap, and the Advisor's user is standing in the task detail looking at the task. An in-place 30-second thinking state would make it the first surface where the user waits while watching — and would collide with the shipped decision that the Advisor's loading state is invisible. The architecture already solved it: because a judgment is cached against the facts fingerprint, **it doesn't have to be computed while the user watches — it has to be right when they look.** Escalation signals fire generation in the background, it validates and caches, and the reveal is instant. **`BriefSequenceModel.primeAdvisorForPlannedWork` is the first signal** — the Brief's chosen actions are the day's highest-precision prediction of what the user is about to open, and priming only those (never the whole candidate set) keeps a speculative pass over sixty tasks from becoming the runaway the cap exists to catch. Speculative work is capped three ways: `.shallow` judgments are skipped entirely (no wait worth removing), a degraded-to-on-device deep read is skipped (same reason), and `CloudBudget.allowsPrecompute` gives it **half** the daily ceiling so a bet on a task being opened can never starve a certainty that one already was. **Presence-time deep still runs** (bounded at 25s, salvaging down a rung on timeout) but is no longer *marked*: `.loading` renders identically at every rung, so a presence-time deep read is an invisible bounded wait into which the reading settles — and the floor guarantees the wait can only ever end in content or true silence, never an error string.

- **Generated is not offered; SEEN is offered.** Precompute's metric-integrity half, and easy to get wrong in a way that quietly destroys the north star: `offered` is the denominator of acted/offered, dismissed/offered, and the honesty denominator for silence. Counting a precomputed judgment at generation time would fill that denominator with readings no human ever saw, and every ratio built on it would drift downward for reasons unrelated to quality. So a speculative judgment parks its move in `Entry.pendingOffer` and is counted on the first user-facing look.

- **One dumb daily cap, and deliberately not a governor** (`CloudBudget`, same file). `dailyCallCap` (**500**) is a runaway backstop sized well above a projected heavy day, not a ration — and it is **loud in DEBUG when it degrades**, because an eval that silently stops exercising the rung it is evaluating reports the cap's opinion as the model's; it reads `IntelligenceLedger.cloudCallsToday` and **degrades to Rung 2 silently**. The silence is a product decision, not a shortcut: telling a user "you have used your AI budget" converts an invisible cost control into an anxiety and an engagement hook in one move, and what they actually get is a real reading from a cheaper rung. The proposed eligibility → recency → rate governor stays UNBUILT until the counters show a real distribution problem — the capture-deadline precedent, applied to spend. If `CloudBudget.statusLine` is never seen approaching the ceiling, the cap is correctly inert and that is the answer we want.

- **Meter first, cap second, govern on evidence** (`AI/IntelligenceLedger.swift`). **The number that matters is cloud calls per user per day AFTER routing, not AI interactions per day** — 25 Advisor encounters resolving as 15 facts/cache + 8 on-device + 2 cloud is 25 intelligent experiences for two paid generations, and a metric counting "interactions" would report 25 and imply a bill that doesn't exist. The ledger counts `IntelligenceRung` (facts · memory · onDevice · cloud) × `IntelligenceWorkload` (ramble · advisor · brief · sweeps), plus **`cloudCallsToday`** (day-rollover on WRITE; reads stay pure so a footer nobody looked at can't discard yesterday's count). Local-only, never transmitted, same charter as `ModelMetrics` — which it does NOT replace: that answers *did the model work*, this answers *how often did we have to ask one*. It is written **where the routing decision lands, not where a model returns**, because the gate skip and the cache hit are the two outcomes with no call attached and the two the economics turn on (`TaskAdvisorStore.ensure` IS the Advisor's rung ladder; `CaptureRoute.rung`; `PlanTier.rung`). Sweeps record `.onDevice` and **must never reach the cloud rung** — background work nobody is waiting on has no business costing money. This exists so the budget governor is built on measurements rather than argument (the capture-deadline precedent); the daily cap is Phase 3 and reads `cloudCallsToday`.

## Two-engine AI

`AI/AIEngine.swift` defines the seam; `FoundationModelsEngine` (real on-device LLM, iOS 27) and `HeuristicEngine` (deterministic fallback) both conform and emit `[TaskIntent]` via `triage(rawText:context:onPartial:)`. `AppBrain` selects the engine at launch via `SystemLanguageModel.default.availability` and degrades to the heuristic on failure. **The simulator is NO LONGER guaranteed to be the heuristic path** — verified 2026-07-26 on Xcode 27 / iOS 27.0 sim, where the Inbox diagnostics footer reads `Apple Intelligence · on-device`, i.e. `availability == .available` and the sim runs the REAL on-device model. (It follows the host Mac's Apple Intelligence, so it varies by machine.) Two consequences: never assume a sim run exercised the heuristic — read the footer; and the sim can no longer verify off-device/absent-card behaviour, which now needs a device (or host) with Apple Intelligence off. **Unit tests are unaffected** — `onDeviceAvailable()` still hard-returns false under XCTest. Keep both engines behaviorally consistent — the shared derivation lives in `AutonomyPolicy.tier` + `IntentResolver` (including `applyRules`, the learned-correction half both engines get for free).

The ramble pipeline:
- **`TriageContext`** carries personal context per call: `personalization` (top-N learned corrections as instruction lines, built by `CorrectionProfile`), `roster` (value snapshots backing `ResolvePersonTool` — the tool attaches only when a roster exists; mind the beta tool-over-calling caveat below), and `candidates` — the **capture-graph candidate package** (`ContextRetrieval` ranks the open set against the capture: NLEmbedding + lexical + category + recency, cap 12; the `[uuid] title — facts` package is the ONLY valid ids the model may cite for duplicate/child/blocks). **Candidates RIDE THE CHAIN (audit A1)**: retrieval runs concurrently with generation, never ahead of it — the first parse of a burst prompts candidate-blind (proposals are refinements, not prerequisites), each parse's retrieval returns in its `TriageRun` and becomes the NEXT parse's prompt package, the final resolve of every parse sees prepared ∪ fresh, and a single-shot on-device capture gets ONE bounded enrichment re-parse (`suggestsEnrichment`) so duplicate detection still lands. Capture sessions are pooled (`CaptureSessionPool`, single-use, fingerprinted on instructions+roster, prewarmed with the REAL instruction prefix + prompt head — `ModelWarmup`'s anonymous session never covered it); a continuous session stays deferred. The resolver tiers the model's claims into `EdgeProposal`s **by destructiveness, not uniformly** (the auto-accept invariant): `duplicateOf` (a merge destroys data) keeps ≥0.85 accepted / 0.5–0.85 undecided / <0.5 suppressed; `childOf` (additive, reversible) is auto-accepted at ≥0.5 (`.undecided` is duplicate-only). Previously rejected pairings are dropped at the resolver via the suppression set (passed through `TriageContext.suppressions`). At commit an accepted duplicate **merges** (no new task, reversible "merged" entry that Undo resurrects), a rejected proposal writes `SuppressionRecord`s, an accepted child becomes a reversible `.parent` link. **The heuristic path lacks proposals + workIntent by design** (Apple Intelligence is assumed present; those features are simply absent in the sim, which exercises the heuristic).
- **INSTANT CAPTURE — the deterministic read renders first, the model upgrades it in place.** `AppBrain.provisionalDrafts` (no model, no Core Data, no await: `Segmentation` → `HeuristicEngine.intent` → `IntentResolver` → `proposeOwners`, deliberately with NO open tasks and NO candidates) paints cards on every text change, leading-edge coalesced at 80ms. The model parse keeps its rolling cadence and upgrades those cards via `DraftMerge` **Pass C**, which matches a model retitle against the CLAUSE the provisional card was cut from (`TaskDraft.provisionalSource`, optional so parked payloads still decode; `isProvisional` is derived from it) using stemmed containment — word overlap between the two TITLES is under the retitle floor, so Passes A/B structurally miss. `mergeProvisional` is additive-only (a provisional pass can never downgrade a model card) and `RemovedDraftSet` remembers source clauses so a deleted card can't resurrect under a rewritten title. A completed parse only drops cards it actually read (`keepingUnmatched: textMoved`). Time-to-first-card, its producer, the provisional pass's cost and the commit's are all in the DEBUG footer.
- **Streaming is internal.** On device `onPartial` receives resolved partial candidates from `streamResponse` snapshots mid-generation — and **the user never sees them**. The product rule is **model reasoning streams internally; the user receives ONE final interpretation**. Streaming is still exploited for latency, salvage at the deadline, and metrics; it is simply never rendered as user truth. (The rolling cadence this bullet used to describe — a 400ms debounce, a 1.2s max-wait, `parseEpoch`, `scheduleTriage`/`startParse` — is gone, along with those functions.) Mid-session park writes are throttled (~2s, `force` on dismiss).
- **Low confidence is a visual state** (dimmed + "?" on the confirm card), never a held queue.
- **Eval harness — the floors live in the APP target, not the test** (`AI/RambleEvalSet.swift`: fixtures + scoring body + **`RambleEval.Floors`**). `RambleEvalTests` and the `-RambleEval` device seam both read `Floors.standard`, so every arm is held to the SAME numbers by the same code. They used to be `#expect` literals inside the test, which meant only CI could fail them — and CI exercises the deterministic path, because the Foundation Models path only exists on hardware. The floors were held by the FALLBACK while the front door went unmeasured, and an unstructured spoken blob failed to segment on device with every number green. The test is now ONE assertion over `Report.failures(against:)` plus a guard pinning the field count, because an enumerated list of eight `#expect`s is a place for a field to be measured and quietly left unheld. **`-RambleEval` runs the free arms; the cloud arm is OPT-IN behind `-WithCloud`** (heuristic always; the on-device tripwire arm when there is one; cloud only when BOTH configured and flagged — configured is not authorized, one sweep is one billable call per case, and without the flag a throwing quota-guard provider occupies `CloudModel.provider` for the run so a leaked call throws instead of billing; each arm's summary line prints `providerCalls` from the ledger delta as the receipt), each printing a per-field PASS/FAIL table plus a `settled p90` latency row — the baseline a cloud arm must beat has to be measured on the same hardware in the same run, never inherited from CI. **Every model arm proves a model ANSWERED**: the seam takes a `ModelMetrics` delta across the run and reports an arm that served **fewer than 90% of its calls** as DEGRADED rather than as a pass — a RATIO, not a zero test, because an arm serving 2 of 52 printed "ALL FLOORS HELD" with numbers identical to the fallback's; the banner also names the recorded error, so it can say WHY rather than only how often — see the availability-vs-catalog trap below, which this seam hit on its very first run. Extend the fixture set when capture behavior changes, and re-calibrate floors only downward from observed numbers.

**Running on a physical device (iOS 27) with a launch arg:**
- Launch arguments are **only passed when Xcode launches the app via Run (⌘R)** — never on Build (⌘B), and never when you tap the app icon on the phone. Set the arg in the **shared** scheme: *Edit Scheme ▸ Run ▸ Arguments ▸ Arguments Passed On Launch* (tick the checkbox), pick the iPhone as the destination, then ⌘R.
- The Run action is **Debug** by default, so any `#if DEBUG` affordance is compiled in on device runs — e.g. the **plan-tier readout** (`plan: on-device N · pcc N · rules N · last Xms`) in the `SettingsView` diagnostics card that shows which Today-plan tier actually ran. It is stripped from Release/Archive.
- **The cloud rung is inert until Firebase is configured:** `GeminiProvider.isAvailable` is `FirebaseApp.app() != nil`, so the rung activates when `AppDelegate` calls `FirebaseApp.configure()` at launch and stays dormant everywhere it doesn't — notably the **unit-test host, which deliberately skips configuration**, so a suite can never issue live billable Gemini calls while pretending to test routing. `GoogleService-Info.plist` needs no pbxproj entry: it sits inside the synchronized root group and is bundled automatically. **App Check's CLIENT half is wired (2026-09-11, WS0); the CONSOLE half is not, and the deadline is hard: 2026-11-02.** `AI/AppCheckSetup.swift` installs the provider factory from `AppDelegate` **before `FirebaseApp.configure()`** — afterwards is accepted silently, leaves the default in place, and fails at the first token request with nothing wrong in the code you are reading — inside the `isHostingUnitTests` guard, with App Attest + a DeviceCheck fallback on device (`AppAttestProviderFactory`, ours, because Firebase's returns nil on hardware without App Attest and would leave those devices with NO provider) and `AppCheckDebugProviderFactory` on the SIMULATOR, fenced on **`#if targetEnvironment(simulator)`, never `#if DEBUG`** — a device run is a Debug run, and the phone is what must prove App Attest. `GeminiProvider` passes `useLimitedUseAppCheckTokens: true` (a fresh single-use token per call; the strongest option, argued down only by a measurement). `AppCheckSetupTests` greps both silent traps; `AppCheckSetup.statusLine()` counts down in the DEBUG diagnostics card, because a deadline living only in a header comment is a deadline nobody is counting. **What is left is not code:** enable the **App Attest capability** on the App ID and only then add `com.apple.developer.devicecheck.appattest-environment` to `Project_Ezra.entitlements` — adding the entitlement first fails code signing outright (*"Provisioning profile … doesn't include the App Attest capability"*, verified 2026-09-11) and breaks the device build this app is dogfooded on, which is why the entitlement is deliberately absent and `AppAttestProviderFactory` falls through to **DeviceCheck**: no entitlement needed, a valid App Check provider, survives enforcement, so the un-upgraded state is weaker but working rather than broken. Then register the simulator's printed debug token in the console (it is a credential — never committed, never logged), prove ONE attested call serves on device, then turn console enforcement on. That order matters: enforcing first blocks a working app with no local way to tell whether the client half was ever right. After the date, an unattested request is refused while `GeminiProvider.isAvailable` still answers true, so the failure arrives looking like a network problem.
- **Historical (PCC, removed):** the ancestor of the rule above was `PrivateCloudComputeLanguageModel`, which *traps* (uncatchable) the instant it's constructed without the managed `com.apple.developer.private-cloud-compute` entitlement — gated behind a compile-time `PCCEntitlement.isGranted`. PCC is no longer used and both types are deleted; the "never construct the model to answer `isAvailable`" rule it taught is now a documented requirement of `CloudModelProvider`, binding on every provider.

## Workflow

- **Two ways onto `main`, by who is committing.** The owner's local sessions commit directly to `main` and push — one developer, no review to wait for. Cloud/background Claude sessions (the code-review, dead-code and design-audit routines) cannot be watched while they work, so they get a `claude/<name>` branch and open a PR; the owner reads the diff and merges it on GitHub — with no CI, the PR IS the review, and it is the only place a bad autonomous commit can be caught before it is on `main`. The cost is divergence: a merge on GitHub puts a merge commit on `origin/main` that local `main` never sees, and a local session that keeps committing widens the gap silently (2026-09-17: 21 unpushed local commits over 2 remote ones before anyone noticed; the same session found 9 dangling `claude/*` branches, 5 of them already merged). So **every local session starts with `git fetch && git status`**, and a diverged `main` is reconciled with `git rebase origin/main` — the local commits replay over the merged PR and history stays linear; a merge commit from the local side would make `main` read like two teams. A merged `claude/*` branch is deleted on the remote; an OPEN PR's branch is left alone, because the design-audit routine opens docs-only PRs that wait for the owner's read, and deleting the branch would close the PR.
