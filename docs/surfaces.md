# Surfaces — navigation, My Tasks, the task detail, the Brief

Extracted verbatim from `CLAUDE.md` on 2026-09-02, when that file crossed its size
limit. **CLAUDE.md keeps the invariants; this file keeps the reasoning, the measured
constants and the archaeology behind them** — the reverted custom bottom bar, the

Read it before changing shell navigation, the record surface or the detail pager.

## The shell after 2026-09-02 — one surface, two verbs

The paragraph below this section is **historical**: it describes the system tab bar with
the orb parked beside it, the measured constants that placement needed, and the Brief and
Ask tabs. All of that is gone. What stands:

- **`RootTabView` shows `TasksHomeView` directly.** No `TabView`. The Brief was cut (two
  equal pillars — Ramble/Capture and the Advisor), and the Ask TAB lasted one day: a tab
  is a place you go to talk, which was the condition of the scoped-conversation fence
  closest to failing (`prev-docs/product-guardrails.md`). Ask is now a **sheet** summoned
  from the Tasks header's `text.bubble` — the same glyph the task pager wears — so asking
  is one gesture at every scope (F-12).
- **The orb is bottom-trailing with plain padding.** With no bar to align to, the derived
  offset (`overlayBaseFromBottom + diameter/2 − barCentreFromBottom`), the measured
  62.0/52.2/34.0pt constants, and `tabBarMinimizeBehavior(.never)` are retired. The
  diameter stays 62pt (it reads as one object with the orb inside it). It hides under
  the keyboard and pauses when covered (`barOrbPaused`, now including the Ask sheet).
- **Three sheets, one mount each:** the composer (`\.openCapture` / `\.resumeCapture`),
  Activity (`\.openActivity`), Ask (`\.openAsk`). The last surface whose only mount lived
  inside another surface's conditional container was silently deleted for three weeks;
  the shell owns them so that cannot recur.
- **Long-press on the orb is gone** with Private Capture's second door (F-03). Privacy is
  a posture chip in the composer's capture bar, persisted, and said in `DataBoundary`.
- **`-InitialTab` is a no-op**; `-AskHousehold` / `-HouseholdChatFixture` present the Ask
  sheet; `-OpenPrivateCapture` is gone.
- **What Tasks gained:** the Ask bubble in its toolbar, and `ParkedCapturesRow` under the
  header (F-04) — unfinished captures findable without a nudge.

## Historical — the system tab bar and the orb beside it (2026-08-18 → 2026-09-02)


- **Navigation is the SYSTEM tab bar plus one app-owned control beside it — the loop is the navigation** (product shape v2, 2026-08-18; the Brief cut and the orb button, 2026-08-29). `RootTabView`: **Brief** (0, `BriefHomeView` wrapping `BriefView` + `BriefSequenceModel`) and **Tasks** (1, `TasksHomeView`) in the OS's own tab bar, with the circular Capture orb (`captureOrbButton`) parked bottom-trailing in the SAME ROW as the bar's capsule — Linear's agent-button placement, which the two-tab collapse finally leaves room for. Measured on iPhone 17 Pro: the two-tab capsule is 188pt wide, leaving 107pt of free trailing space. **The OS owns the bar** — rendering, selection, safe area, accessibility — and the app owns exactly ONE control; any change requiring modification of the native bar's visual hierarchy is the wrong approach. **`tabBarMinimizeBehavior(.never)` is a load-bearing invariant**, not cosmetic: the orb is pinned beside the bar by an offset measured against it, so a bar that minimizes on scroll would slide out from under it mid-gesture. The button's diameter is set to the bar capsule's MEASURED height (62pt) so the two are the same size, and `captureOrbVerticalAdjustment` is **derived, never stored** — `overlayBaseFromBottom + diameter/2 − barCentreFromBottom` — because it moves with the diameter, and a hardcoded value left behind by a resize would drift the button off centre by half the delta, invisibly to every test. The inputs are measured and device-independent (identical on 17 Pro and 17 Pro Max): bar height 62.0pt, centre 52.2pt, overlay base 34.0pt. The correction exists because the floating bar draws INTO the bottom safe area — its capsule bottom sits below the 34pt home-indicator edge the overlay aligns to — so an overlay resting on that line is above the bar's centre. **Measure at a background-delta of ≥8**: a lower threshold reads soft edges and once put 57.7/50.0 into this file. **A fully custom bottom bar** (Brief · Capture · Tasks in one hand-rolled glass capsule, with `toolbarVisibility(.hidden, for: .tabBar)` and its own `safeAreaInset`) **was built and REVERTED the same day** — it cost the OS's rendering and safe-area management, and required `contentMargins` workarounds in `TaskLaneList` because a shell `safeAreaInset` does not reach a `ScrollView` nested in a tab's `NavigationStack`. Never a third tab, and never that bar again. **The BRIEF is currently OFF** (`BriefFeature.isEnabled`, 2026-08-29) while the product narrows to Capture + Advisor: the tab stays as a placeholder, `.disabled` so the OS renders it dimmed and unselectable (`UITab.enabled`'s own contract; verified on device-class sim — and there is NO `TabContent.accessibilityHidden`, so VoiceOver still announces it, with "dimmed" appended, which is the better behaviour anyway), `initialSelection` clamps the floor to Tasks so nothing can strand on it (pure + injectable, both arms in `RootTabSelectionTests` — the `SyncGateTests` rule that a gate's other side must have RUN before it ships), the tab's body is swapped for an empty one so the generation chain stays cold, `BriefingReminder` stops scheduling and cancels its existing horizon at launch, and Settings hides the briefing card. What went inert with it — read `BriefFeature`'s header before assuming a number is broken: `deferralCount`/`carriedOverCount` (so `ReasoningBudget.repeatDeferred` never fires and **`-AdvisorBenchmark` now describes a TWO-reason depth router**), `CapacityLog`, and `RequiredAttention.orientation` (which reports `—`, not a perfect score — nil `plannedTaskIDs`, because "unmeasurable" and "nothing was missed" are opposite findings). The Advisor's precompute was Brief-fed too and IS re-homed rather than dropped: `TaskRow.applyDirect` (a lifecycle move means the facts changed) and `TaskDetailPager` (the peers one swipe away — a better predictor than the Brief's planned actions, since the pager is holding the ordered list). **The Inbox and Household tabs were CUT — surfaces cut, systems relocated, and the relocation is the load-bearing half.** (a) The trust surface survives as **`ActivityView`** (`Features/Activity/`, renamed from `InboxView`): the same change-log feed with avatars, action badges, unread dots and action-aware Undo — including the merged-pair entries that have no other home — now a **sheet the SHELL owns**, mounted exactly once in `RootTabView` and opened through `\.openActivity` from both the Tasks "…" menu and the Brief's held-depth tile. One mount point is deliberate: the last surface whose only mount lived inside another surface's conditional container was silently deleted for three weeks (`MyTasksHeader`). Its **unread TAB BADGE died with the tab and must not return** — a feed that mostly narrates what you already did asking to be visited is exactly the engagement shape the guardrails refuse; the per-row unread dots survive, because they answer "what's new since I looked" for someone who already chose to look. Its DEBUG diagnostics footer was **deleted, not moved**: `SettingsView.diagnosticsCard` already carried a strict superset. (b) Multiplayer survives as **substrate** — the roster, born-owned tasks, creator-vs-owner, the publish boundary at Confirm and `HouseholdSync.isLive` all stay in the model; `HouseholdRosterView` stays reachable from the Tasks "…" menu; `HouseholdView` (the mission-control dashboard) was **deleted** as a cut surface, while `HouseholdEngine` stays as tested computation Phase 5 rebuilds on. Three record-surface refinements (2026-08-26c): **rows carry WHEN** — a compact trailing due label ("2d over" in the overdue token · "Today" · a weekday inside the week · a short date beyond), only when a date exists, only on live rows, because position explains which row outranks which but cannot say when; **the `SignalMarker` column is reserved on the record surface** (`reservesSpace: true` — one shared explicit frame for glyph and clear, so alignment holds by construction; zero-footprint marks made marked rows push their titles right and the left edge went ragged); and **the resolution ledger caps inline** (`MyTasksSlices.resolvedInlineCap` = 5 per resolved section, live sections NEVER capped, a "Show all N" row flips the STATUS FILTER — the documented isolation path — rather than growing a second expansion mechanism; capped is what renders, so the pager's peer contract holds unchanged). It is true now.* Tapping a task opens the **full-screen Linear-style detail**, whose body is **shape-driven (2026-08-25)**: `Models/TaskShape.swift` derives `deciding / waiting / container / action` from facts alone (flag → blockers → steps → residual; wording NEVER picks a shape, `allCases.count == 4` test-pinned, and every input is already in the Advisor fingerprint so the page can only reshape when the reading changes — `TaskShapeTests`). - **Seven detail-page refinements (2026-09-04), each a rule:** **WHEN is one vocabulary** — `Models/DueLabel.swift` is the only place due text is derived; the row reads `.compact` ("3d over" · "Today" · "Fri" · "Sep 12"), the detail chip reads `.full` ("3 days overdue" · "Today" · "Tomorrow" · "Friday" · "Fri, Sep 12") in the `overdue` token with `calendar.badge.exclamationmark`, and only LIVE dated work earns a label (a resolved task's due is a plain date — "overdue" on finished work is a scold about the past; `DueLabelTests`). **The page states WHERE the task is in its life** — `TaskTimeline.caption` under the title: "Started 2 hours ago" (the CURRENT visit, never the summed dwell) · "Done yesterday" · "Canceled 3 days ago" · nothing for a plain to-do; the status chip shows the state, the caption shows the time, and "took 3d" stays a receipt under Details. **Return in the title means done** — `TaskDetailView.titleAfterReturn` collapses the break and drops focus (a task title is one line of intent), and a keyboard Done (conditional on focus, so only the edited page contributes it) ends a notes edit honestly. **The inline date picker is an expansion, not a mode** — opens from "Pick a date…" WITHOUT stamping today onto an undated task, closes on pick, carries a Done for the person who chose nothing. **The undo pill renders on the ACTIVE page above the pinned bar** (applied before the `safeAreaInset`, so it never covers the next page's CTA) while staying pager state, and `taskDetailSheet(_:peers:handOffNotice:)` hands a still-showing pill to the presenting surface when the cover closes — resolving the ONLY task you opened used to be the one resolution with no way back. **Resolution earns `.success`**; every other tap keeps the soft impact, never both on one tap. **A related task opened from the page pages through its siblings** — steps through steps, dependents through dependents, blockers through blockers (`relatedPeers`); a cited task still opens alone.

## The grouping proposal on My Tasks (2026-09-17)

- **What it is.** The 2026-09-12 deck pass left one thing owed: "the AI proposal ('Group them?') — the model naming membership". `AI/GroupingSweep.swift` is that, on the iOS 27 on-device model, in the `DuplicateSweep` shape: a deterministic prefilter (loose open tasks — no umbrella, not waiting — that share a significant word of four letters or more, clustered by union-find with rejected sibling pairs cut from the graph first; clusters of 2–5, best-linked first, five per run, three judged), a guided-generation judge (`GroupJudgment`: belongsTogether · confidence · outcomeTitle · memberTitles) behind `ModelRun`'s background deadline, and a validator that is the trust boundary — every member title must be one the model was shown (one invented title rejects the whole judgment; a group with a phantom member is a wrong group, not a smaller one), at least two members, a 1–6 word title that is not itself a member, confidence at the `childOf` tier (0.5).
- **It proposes; it never writes.** A group is structure, and the deck view's whole argument is that structure the person did not ask for is a cost. So the sweep's output is a `GroupProposal` value in `GroupProposals.shared` (in memory for this launch) and ONE quiet row at the top of My Tasks under the parked-captures row (`GroupProposalRow`) — the same register: no colour, no count, no notification, gone when there is nothing to ask. Tap → the members and three answers. **Group them** writes the umbrella and its `.parent` edges exactly as the confirm card's group does (`GroupingSweep.apply`: commonest category, the owner who holds most steps, edges `.inferred(confidence:)`), as one reversible `"grouped"` entry — the existing undo arm unlinks the steps and removes an untouched umbrella — with the Undo pill. **Not these** writes a `siblingGroup` suppression per member pair (a new `SuppressionKind`, symmetric like a duplicate's) AND one reversible `"rejectedGroup"` trail entry for the whole set — a veto with no way back is the undo-completeness rule broken; its undo arm lifts every pair at once — so the sweep never asks that question again unless the person takes the no back. **Not now** hides the member set for this launch. A proposal whose members the household has moved past (one resolved or grouped by hand) simply stops showing.
- **Bare chains are candidates first.** The screenshot that opened the pass showed a bare chain's deck captioned *RENEW PASSPORT → BOOK FLIG…* — the arrow story, truncated at phone width. `GroupingSweep.chainClusters` hands every umbrella-less chain (≥2 members, no rejected pair) to the same judge ahead of the word clusters (`candidates(in:snapshots:suppressions:)`); the chain's shape already says "one outcome", the judge says what to call it, and accepting writes the umbrella the deck was built to caption. Once named, the chain leaves the candidate set.
- **Where it runs.** `runMaintenanceSweepsIfDue` — hourly, foreground, beside the duplicate sweep, on-device only, metered under `.sweeps`, absent off-device. `ModelFeature.groupingSweep` is its metrics row.
- **Measured before shipped.** `-GroupingSweepEval` runs eight labeled clusters (four one-outcome, four word-sharing non-groups) through the judge the product uses and prints FALSE ACCEPT (the critical error: a non-group the person is asked about), recall, and latency. `-SeedGroupProposal` puts the row on screen without a model. Tests: `GroupingSweepTests` (prefilter, validator, accept → one reversible entry → undo, reject → suppressions the prefilter honours).
- **First numbers (2026-09-17, sim iPhone18,1 · iOS 27.0 26A428 · on-device).** `-GroupingSweepEval`: served 8/8, FALSE ACCEPT 0/4, recall 4/4, p50 1119 ms, p90 2384 ms — every one-outcome cluster accepted at 0.90–0.95 with all members grounded and a plain title ("Lagos trip", "Kitchen renovation", "Moving preparation"), every word-sharing pair declined at 0.10–0.25. On a fresh install with `-SeedFlowFixtures` the LIVE sweep ran at launch and the row read *Group as “Wedding planning”? · 2 tasks* before the seed seam could fire — the first proposal came from the product path, not the fixture.
- **The first false accept, caught by the store printout.** The eval's "store:" section lists what the sweep would ask about on THIS store, and on the flow fixtures the first live proposal had been *Group as "Wedding planning"? · 2 tasks* over "Choose the wedding caterer" and "Confirm caterer for the reunion" — two different events sharing a word, the critical error in production on the first launch. Both that pair and "Renew the car insurance / Renew car registration" are now labeled non-groups, and the judge's instructions say that two different occasions are two outcomes even when they share a word. Re-measured: served 10/10, FALSE ACCEPT 0/6, recall 4/4, p50 1545 ms — the caterer pair declines at 0.40, only 0.10 under the tier, so it is the pair to watch when the runtime moves; every real group still accepts at 0.92–0.95. With chains first, the live row on the same store now reads *Group as "Trip preparation"? · 3 tasks* — the passport chain, named.
